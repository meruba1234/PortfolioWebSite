SMB / CIFS / UNC 共有アクセス — smbprotocol 直叩き vs OS マウント

背景

Linux サーバーや Docker コンテナから、Windows のファイル共有（\\server\share）を読み書きしたい場面はよくある。たとえば「NAS 上の共有フォルダに置かれた Excel を Linux のバッチが取り込む」「コンテナ内のジョブが共有フォルダへ出力する」といったケースだ。

ここで最初に迷うのが「マウントすべきか、それともコードから直接叩くべきか」という選択。用語（SMB / CIFS / UNC）を整理したうえで、Linux 側の 3 つのアクセス方式を比較していく。

用語整理: SMB / CIFS / UNC

まず言葉を揃えておく。この 3 つはよく混同されるが、指しているレイヤーが違う。

用語何を指すか
SMB (Server Message Block)Windows のファイル共有・プリンタ共有を実現するプロトコル。現行は SMB2/SMB3。
CIFS (Common Internet File System)SMB の旧称・古い方言（SMB1 相当）。Linux では歴史的経緯で今も「cifs」という名前がドライバ名などに残る。
UNC (Universal Naming Convention)\\server\share\path というパスの書き方。プロトコルではなく表記ルール。

ポイントは「CIFS ≒ 昔の SMB」「UNC はパスの書式であってプロトコルではない」という点。 Linux の mount -t cifs というコマンドは名前こそ cifs だが、中身は SMB2/SMB3 で通信している（バージョンは vers= オプションで指定できる）。

UNC パスは Windows 独自の書式なので、Linux 側で扱うときは方式によって読み替えが必要になる。たとえば \\nas01\share\data\report.xlsx は、ライブラリ経由なら smb://nas01/share/data/report.xlsx のように書き直す。

Linux から Windows 共有を触る 3 方式

大きく分けて 3 系統ある。A/B は「OS やコンテナに共有をマウントして、ローカルのパスのように見せる」方式。C は「マウントせず、ライブラリが TCP で直接 SMB を喋る」方式。

A: OS カーネルの CIFS マウント

mount -t cifs で共有を /mnt/... に見せる。恒久化するなら /etc/fstab に書く。

# 一時的にマウント
mount -t cifs //nas01/share /mnt/share \
  -o username=guest,password=,vers=3.0

# fstab に書いて永続化する場合（認証はcredentialsファイルに逃がすのが定石）
# //nas01/share  /mnt/share  cifs  credentials=/etc/smb-cred,vers=3.0  0  0

マウント後は /mnt/share/data/report.xlsx のように普通のローカルパスとして読み書きできる。アプリ側は共有を意識しなくてよいのが利点。

B: Docker volume の cifs マウント

Docker の volume ドライバで cifs を使い、コンテナに共有をマウントする。

# docker-compose.yml の例
volumes:
  share_vol:
    driver: local
    driver_opts:
      type: cifs
      o: "username=guest,password=,vers=3.0"
      device: "//nas01/share"

services:
  job:
    volumes:
      - share_vol:/mnt/share

コンテナ内からは A と同じくローカルパスに見える。ただし認証情報を compose ファイルに書くことになり、ホスト OS の cifs カーネルモジュールにも依存する。

C: Python の smbprotocol / smbclient で直接叩く

マウントを一切せず、Python ライブラリが TCP(445) で SMB を直接喋る。UNC を smb://... に読み替えてアクセスする。

import smbclient

# 認証情報を先に設定（AD なし NAS は guest でいけることが多い）
smbclient.ClientConfig(username="guest", password="")

# UNC \\nas01\share\data\report.xlsx を smb:// に読み替えて開く
with smbclient.open_file(r"\\nas01\share\data\report.xlsx", mode="rb") as f:
    data = f.read()

smbclient は組み込みの open() に近い API を提供し、低レベルな smbprotocol の上に乗っている。 OS にもコンテナ設定にも手を入れず、アプリのコードだけで完結するのが最大の特徴。

3 方式の比較

観点A: OS mountB: Docker mountC: smbprotocol
マウント要否要要不要
認証情報の置き場所fstab / credentials ファイルcompose ファイルアプリのコード / Secret
OS・カーネル依存あり (cifs モジュール)あり (ホストの cifs)なし
速度速い速いやや遅い
疎結合・可搬性低 (OS 設定に紐づく)中高
パスローカルパスに見えるローカルパスに見えるUNC を都度指定

「マウントを一切使わない」を完全に満たすのは C だけ。 A/B は高速だが、認証情報を fstab や compose に書く必要があり、OS や権限まわりに依存する。デプロイ先の環境が変わると設定を作り直すことになりやすい。

一方 smbprotocol（C）は多少遅いものの、認証情報をアプリ側（Secret 管理など）から渡せて疎結合。 Docker / Linux でもそのまま動く可搬性があり、「コードを持っていけばどこでも動く」状態を作りやすい。

guest 認証について

Active Directory（ドメイン）が無い NAS では、guest 認証で読み書きできることがある。簡易な TeraStation 系 NAS などが典型で、ユーザー管理をしていない共有に対してはこれが刺さる。

smbclient の場合、通信の前に ClientConfig で資格情報を設定しておく。

import smbclient

# guest はユーザー名 "guest" + 空パスワード、が通ることが多い
smbclient.ClientConfig(username="guest", password="")

もちろんセキュリティ的には推奨されないが、AD の無い閉じた社内 LAN の NAS では実運用でよく使われる。逆に AD 参加の共有では、ドメインユーザーの資格情報（DOMAIN\user）が必要になる。

透過ラッパーの設計

実装上のコツは、パスの種類によってバックエンドを自動で振り分けるラッパーを用意すること。

  • パスが UNC（\\ で始まる）なら → smbprotocol / smbclient で開く
  • パスが ローカルパス なら → 標準ライブラリ（open() など）で開く

こうしておくと、呼び出し側は「共有かローカルか」を意識せずに同じ関数を使える。ローカルでの開発時はローカルパス、本番の Linux/Docker では UNC、とパスを差し替えるだけで動く。

import os
import smbclient

def open_any(path, mode="rb"):
    # UNC パスなら SMB 経由、ローカルパスなら標準の open
    if path.startswith("\\\\") or path.startswith("//"):
        return smbclient.open_file(path, mode=mode)
    return open(path, mode=mode)

注意: UNC パスの分解は自前ヘルパーで

ひとつ落とし穴がある。UNC パスは Linux の os.path ではセパレータの扱いが違って壊れる。 Linux の os.path はセパレータを / として扱うため、\\server\share\... のような \ 区切りの UNC を os.path.dirname() などに渡すと期待どおりに分解できない。

そのため、UNC パスの「サーバー名」「共有名」「サブパス」への分解は、os.path に頼らず自前のヘルパーで行うのが安全。（この UNC パス分解の詳細は別ノートで扱う。）

まとめ

  • Windows のファイル共有は SMB（旧称 CIFS）プロトコルで提供され、UNC（\\server\share\path）でアクセスする。UNC はパスの書式であってプロトコルではない。
  • Linux から使う方式は 3 系統。A: OS の CIFS マウント / B: Docker volume の cifs マウント / C: smbprotocol での直叩き。
  • 「マウントを使わない」を完全に満たすのは C のみ。A/B は速いが認証を fstab/compose に書き、OS・権限に依存する。C は多少遅いが、認証をコード（Secret 等）から渡せて疎結合・可搬。
  • AD の無い NAS は guest 認証で読み書きできることがある。ClientConfig(username=..., password=...) を通信前に設定しておく。
  • 実装は UNC ならsmbprotocol、ローカルなら標準ライブラリと透過的に振り分けるラッパーが便利。ただし UNC はセパレータ違いで os.path が壊れるので、パス分解は自前ヘルパーにする。
