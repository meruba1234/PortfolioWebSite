インフラ

ジョブ基盤の scheduler と worker の分離 — 「予定は作られるが実行されない」の切り分け

背景

ジョブ自動化基盤を運用していると、「ジョブはちゃんと予定に入っているのに、いつまで経っても動かない」という状況に出くわす。ダッシュボードを見ると実行予定（run）はきれいに並んでいる。スケジュールの設定ミスにも見えない。なのに実行時刻を過ぎても状態が変わらず、ただ溜まっていく。

このとき「スケジュールが壊れた」と考えて設定をいじり始めると、たいてい遠回りになる。この症状のほとんどは、スケジュールを作る側ではなく実行する側の問題だからだ。それを理解するには、多くのジョブ基盤が内部で 2 つの役割に分かれていることを知っておくとよい。

scheduler と worker は別物

ジョブ実行基盤（Prefect / Airflow のような製品や、広く見れば cron や CI ランナーも）は、ざっくり次の 2 つの役割に分かれている。

  • scheduler（予定を作る側）
  • 「このジョブを、次はいつ走らせるか」を計算する。
  • その結果を「実行予定（Scheduled state の run）」として登録する。
  • ここまでが仕事。実際にジョブ本体のコードを走らせることはしない。
  • worker（予定を拾って実行する側）
  • キュー（Work Pool / ワークキュー）を購読し、Scheduled になった run を拾い上げる。
  • 拾った run のジョブ本体を、自分のプロセス／マシン上で実際に実行する。
  • 実行結果（成功・失敗）を基盤に書き戻す。

重要なのは、この 2 つはネットワーク越しに疎結合であることが多いという点だ。scheduler は中央のサーバー上に、worker は別のマシンやコンテナ上に、というように物理的に離れて動く。両者は「キューにある予定」を介してだけつながっている。

[scheduler] --(予定を登録)--> [キュー / Work Pool] <--(予定を購読・実行)-- [worker]
   予定を作るだけ                中継地点                    実際に走らせる

だから片方が生きていても、もう片方が死んでいればジョブは進まない。特に scheduler が正常でも worker が落ちていれば、予定は作られ続けるが誰も実行しない、という状態が起きる。

溜まる症状の読み方

「予定は作られるが実行されない」の典型的なサインはこうだ。

  • run が Scheduled（実行待ち）状態のまま、いつまでも次の状態（Running / Completed）に進まない。
  • run の開始時刻（start）が空（None）のまま。＝「まだ誰も走らせ始めていない」。
  • 時間が経つほど、実行されない予定がキューにどんどん積み上がっていく。

この「Scheduled のまま start=None が溜まる」という並び方を見たら、まず疑うべきは worker が起動していない／キューを購読できていない ことだ。scheduler は健気に予定を作り続けているので、予定の数はむしろ増える。これはスケジュール設定が壊れている兆候ではなく、実行部隊が不在の兆候である。

逆に、run が Running で止まっている・Crashed や Failed になっている場合は worker は動いている（拾えている）ので、原因はジョブ本体のコードや実行環境側にある。「拾われていない」のか「拾われた後にこけた」のかで切り分け先がまったく違う。

切り分けの手順

  1. まず worker プロセスが生きているかを、scheduler とは独立に確認する。
  • scheduler（中央サーバー）の画面が正常に見えることは、worker の生死を何も保証しない。別物なので別々に確認する。
  • worker が動いているホスト側でプロセスの生存を見る（プロセス一覧、コンテナの起動状態、worker のハートビート／最終ポーリング時刻など）。
  1. run の状態と start の有無を見る。
  • Scheduled + start=None が溜まる → worker 不在を強く疑う（上記の通り）。
  • Running のまま固まる／Crashed → worker は動いている。ジョブ本体・実行環境を疑う。
  1. worker がどのキュー（Work Pool）を購読しているかを確認する。
  • worker は生きていても、ジョブが投入されるキューと別のキューを購読していれば永遠に拾わない。
  • Pool 名・キュー名の食い違いは「worker は Running なのに特定ジョブだけ動かない」という形で出る。
  1. worker を復帰させ、溜まった予定が拾われて start が入るかを見る。

補足として、この Pool／キューの仕組みは障害切り分けだけでなく設計にも使える。同じ基盤に対して、中央側とは別に特定ホスト上にも worker を立て、ジョブを Pool 名で振り分けられる。「このジョブはこのマシンで動かしたい」（そのマシンにしかない資源やアプリを使う等）というとき、対応する Pool を購読する worker をそのホストに置けばよい。

コード反映のタイミング

worker が「いつジョブ本体のコードを読むか」も、運用でよく混乱する点なので押さえておく。構成によって反映のされ方が違う。

  • worker が実行のたびに最新コードを取得する構成（例: 実行直前にリポジトリを pull してから走らせる）
  • ジョブ本体のコードを直しても、worker 自体の再起動は不要。次の実行時に新しいコードが読まれる。
  • worker が起動時に読んだコードを使い続ける構成（pull しない／イメージに焼き込む等）
  • コードを直して push しても、worker を入れ替え／再起動しない限り反映されない。「直したのに変わらない」の典型。

そして、どちらの構成であっても共通して言えるのは、実行中の run や、実行が始まる直前の run には変更は反映されないということ。反映されるのは早くても次回スケジュール分からだと考えておく。急ぎで直したいときは「今動いている run には効かない」を前提に、次回に確実に乗せることを狙う。

一般化

ここで見た切り分けは Prefect などの特定製品に限った話ではない。「予定を作る側」と「実際に実行する側」が分かれている基盤には、広く同じ考え方が通じる。

  • cron — crontab（予定の定義）は生きていても、実行を担う cron デーモンが止まっていれば何も走らない。
  • CI ランナー — パイプラインはキューに積まれる（予定）が、ランナー（実行機）がオフライン／別ラベルを待っていればジョブは pending のまま溜まる。
  • メッセージキューのワーカー — プロデューサ（投入側）が元気でも、コンシューマ（ワーカー）が落ちていればメッセージが処理されず滞留する。

いずれも症状は同じ形をとる。「投入・予定は正常、でも消化されず溜まっていく」。そのときの初手は毎回同じで、予定を作る側とは独立に、実行する側（worker / ランナー / コンシューマ / デーモン）が生きているかを確認すること。さらに「生きているのに拾わない」なら、購読先のキュー／ラベル／Pool の食い違いを疑う。

まとめ

  • ジョブ基盤は「予定を作る scheduler」と「予定を拾って走らせる worker」に分かれ、両者はキューを介した疎結合であることが多い。
  • run が Scheduled のまま start=None で溜まるのは、scheduler ではなく worker が不在／別キューを購読 のサイン。
  • 切り分けの初手は「worker が生きているか」を scheduler とは独立に確認すること。次に「拾われていない」のか「拾われた後にこけた」のかを状態で分ける。
  • コードの反映タイミングは構成次第（実行毎に pull するか否か）。ただし共通して、実行中／直前の run には効かず、反映は次回スケジュールから。
  • これは cron・CI ランナー・メッセージキューにも通じる普遍的な切り分け方。「投入は正常、消化されず溜まる」を見たら、まず実行側の生死を疑う。
