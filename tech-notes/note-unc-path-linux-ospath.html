プログラミング

Windows の UNC パスは Linux 上の os.path で壊れる

背景

Windows で書いたコードを、そのまま Linux コンテナ（Docker 等）へ移して動かすことはよくある。このとき、共有フォルダを指す UNC パス（\\server\share\dir\file.csv のような形式）を os.path 系の関数で分解している箇所が、例外を投げずに黙って壊れることがある。

「同じコードなのに Windows では正しく動いていた」ため気付きにくく、 basename が丸ごとのパス文字列を返す、splitext が拡張子を切り出せない、といったおかしな挙動として現れる。原因は UNC パス自体ではなく、os.path が OS 依存であることにある。

os.path はなぜ OS 依存なのか

os.path は「実行中の OS に合わせたパス操作」を提供するモジュールだ。 Python 起動時に、その OS 用の実装（Windows なら ntpath、Linux/macOS なら posixpath）が os.path として束ねられる。つまり os.path.basename の中身は、実行環境によって別物になる。

  • Windows 上: セパレータとして \ と / の両方を区切りと見なす
  • Linux 上: セパレータは / だけ。\ はただの普通の文字扱い

この差が、UNC パスを Linux で扱ったときに効いてくる。

症状

Linux 上では \（バックスラッシュ）が区切りとして認識されないため、 \\server\share\dir\file.csv は「区切りが 1 つも無い、単なる 1 個の塊」と判断される。

import os

p = r"\\server\share\dir\file.csv"

# Windows で実行した場合（ntpath）
os.path.basename(p)   # -> 'file.csv'
os.path.dirname(p)    # -> '\\server\share\dir'

# Linux で実行した場合（posixpath）
os.path.basename(p)   # -> '\\server\share\dir\file.csv'  ← 丸ごと返る
os.path.dirname(p)    # -> ''                              ← 空になる

例外は出ない。ただ「間違った文字列」が返るだけなので、後続処理（ファイル名でのマッチング、出力名の組み立て等）が静かにずれていく。

対処1: PureWindowsPath で「Windows パスとして」分解する

実行 OS が何であっても、pathlib.PureWindowsPath を使えば Windows のパス規則で分解できる。ファイルシステムには触らない純粋な文字列操作クラスなので、 Linux 上でも安全に UNC を分解できる。

from pathlib import PureWindowsPath

p = r"\\server\share\dir\file.csv"

PureWindowsPath(p).name    # -> 'file.csv'     （OS 非依存）
PureWindowsPath(p).stem    # -> 'file'
PureWindowsPath(p).suffix  # -> '.csv'
PureWindowsPath(p).parent  # -> PureWindowsPath('//server/share/dir')

逆に、どの環境でも POSIX パスとして扱いたいなら PurePosixPath を使う。ポイントは「実行 OS に判断を委ねる os.path をやめ、パス方言を明示するクラスに切り替える」こと。

対処2: セパレータ非依存の自前ヘルパー

pathlib を挟みたくない場合や、/ と \ が混在したパスを丸めて扱いたい場合は、両方のセパレータで分割する小さなヘルパーを用意する手もある。

def unc_basename(path: str) -> str:
    """`/` と `\\` の両方を区切りと見なして末尾要素を返す。"""
    # 末尾の区切りを無視しつつ、最後の区切り以降を取り出す
    normalized = path.replace("\\", "/").rstrip("/")
    return normalized.rsplit("/", 1)[-1]

unc_basename(r"\\server\share\dir\file.csv")  # -> 'file.csv'
unc_basename("/mnt/share/dir/file.csv")       # -> 'file.csv'

自前実装は挙動を完全に把握できる反面、エッジケース（ドライブレター、末尾区切り、連続区切りなど）を自分で面倒見る必要がある。基本は PureWindowsPath を第一候補にしたい。

splitext の注意

os.path.splitext は「末尾の .拡張子 だけ」を切り出す。そのため、ドットを含むディレクトリ名がパス途中にあると、意図しない切り出しをしうる。

import os

os.path.splitext("archive.2026/report")
# -> ('archive', '.2026/report')  ← ディレクトリ側のドットを拡張子と誤認

UNC が Linux で 1 塊になっている状態でこれを通すと、被害がさらに読みにくくなる。拡張子判定は「分解してファイル名を確定させてから」行うのが安全で、 PureWindowsPath(p).suffix のように名前部分に閉じた API を使うと事故りにくい。

実アクセスは別問題

ここまでは全て「パス文字列の分解」の話で、実際にファイルを開けるかどうかとは別レイヤーだ。

  • Windows: 標準 open(r"\\server\share\file.csv") で UNC を直接開ける
  • Linux: UNC をそのまま open() してもアクセスできない。CIFS マウント経由でローカルパス化するか、 smbprotocol 等のライブラリで SMB を叩く必要がある（詳細は別ノート参照）

つまり「パス分解を PureWindowsPath で直した」だけでは、Linux で実ファイルを読み書きできるようにはならない。分解（文字列）とアクセス（I/O）を切り分けて考えること。

まとめ

  • os.path は実行 OS に追従する。Linux では \ が区切りにならず、UNC パスの分解が黙って壊れる。
  • 症状は例外でなく「誤った文字列が返る」ので気付きにくい。
  • パスの方言を固定したいなら PureWindowsPath（または PurePosixPath）を使う。これが第一候補。
  • どうしても自前で処理するなら / と \ の両方で分割するヘルパーを用意する。
  • splitext は末尾ドット依存で誤動作しうるので、名前を確定してから拡張子を扱う。
  • 文字列の分解と実ファイルへのアクセスは別問題。Linux での UNC 実アクセスは CIFS/smbprotocol が要る。
