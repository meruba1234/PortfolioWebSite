インフラ

ゾンビ化したジョブ実行を止める二重ガード（実行側 timeout ＋ 監視側 automation）

背景

ワークフローエンジンやジョブ基盤で自動化を運用していると、ジョブの1回の実行（run）が「Running（実行中）」のまま延々と終わらず居座る現象に出くわす。実際にはもう処理は動いていないのに、状態だけが更新されず「実行中」に見える。これがいわゆる「ゾンビ化した run」だ。放置すると、次のスケジュール実行が始まっても前の実行が生きている扱いになり、同じ処理が二重に走ったり、資源（CPU・メモリ・I/O・DBコネクション）を食い合ったりする。

なぜこうなるのか、そしてどう止めるのかを整理しておく。

本文

なぜゾンビ化するのか

  • 分散ジョブ基盤では、実行を実際に走らせるのは worker（実行プロセス） で、状態を管理するのは サーバ（オーケストレータ） と役割が分かれている。
  • worker が実行の途中で落ちたり再起動されたりすると、その run の「終わった／失敗した」という最終状態をサーバに報告できないまま消える。
  • サーバから見ると、最後に受け取った状態が Running のままなので、いつまでも実行中として残り続ける。これがゾンビ化の正体。
  • 典型的なトリガーは デプロイ。新しいコードを配る際に worker を再起動すると、ちょうどその時走っていた run が道連れになる。深夜バッチ中のメンテ、コンテナの入れ替え、OOM Kill なども同じ結果を招く。
  • ポイントは「実行主体（worker）は落ちうる」という前提。落ちること自体は防ぎきれないので、落ちた後の後始末を仕組みで用意する。

防御その1: 実行側ガード（ジョブ自身の timeout）

  • ジョブ定義そのものにタイムアウトを設定する（例: timeout_seconds のようなパラメータ）。
  • 「このジョブが N 秒を超えたら、自分自身を打ち切る」という自爆スイッチをジョブに埋め込むイメージ。
  • 通常はこれで十分。想定より長引いた実行が、自分の判断で Failed / Cancelled に落ちてくれる。
  • ただし弱点がある。実行側が自壊できる状態にあることが前提だ。プロセスが応答不能になっていたり、外部 I/O（ネットワーク・ファイル共有・DB）で無限に待たされていたりすると、タイムアウトの判定コード自体が動かず、自爆スイッチが押されない。

防御その2: 監視側ガード（サーバ側の automation ルール）

  • そこで、実行主体の外側から強制的に止める仕組みを重ねる。
  • サーバ側（オーケストレータ）の自動化ルールとして「ある run が N 分以上 Running のままなら、強制的に Cancel する」を設定する。
  • これは worker のプロセスが生きていようが死んでいようが関係なく、サーバが状態を見て判断するので、実行側が自壊できないケースの最後の砦になる。
  • 監視側は「状態が古いまま更新されていない」という外形だけで判断できるのが強み。

なぜ二重にするのか

  • 実行側 timeout だけだと、プロセスが応答不能なゾンビを取りこぼす（自爆スイッチが押せない）。
  • 監視側 automation だけだと、強制 Cancel まで N 分待つ必要があり、その間は資源を握られる。また監視ルールは全体に一律なので、ジョブごとの細かい時間設計には向かない。
  • 両方あると、まず実行側が自分の裁量で早めに畳み、それが効かない異常系だけを監視側がまとめて刈り取る、という役割分担になる。片方だけでは必ず漏れる穴を、もう片方が塞ぐ。

紛らわしい挙動: Crash 後の自動再投入

  • 一部の基盤では、Crash した run が同一の run ID のまま後刻に自動で再投入（retry）されることがある。
  • このとき UI 上の「開始時刻」が過去の最初の起動時刻を指したままに見えることがあり、「なぜこんな昔から動きっぱなしなのか」と混乱しやすい。実際には途中で落ちて、後から同じ ID で再開されている。
  • さらに厄介なのは、再投入のタイミングが他のジョブと重なると、ディスク／ネットワーク I/O が飽和し、それが引き金で別のジョブも遅延・失敗する、という連鎖故障が起きうる点。「1個のゾンビ」で終わらず、資源競合で被害が広がる。

一般化

  • この二重ガードの考え方は特定製品に限らない。「実行主体が落ちうる」あらゆる自動実行基盤に通じる。
  • cron: スクリプト側に自前の timeout（timeout コマンド等）を持たせつつ、監視で長時間プロセスを検出して kill する。
  • CI/CD: ジョブ単位の timeout 設定 ＋ パイプライン全体の上限。
  • ワークフローエンジン全般: タスクの timeout ＋ 実行時間ベースの自動キャンセルルール。
  • 共通の原則は「実行側で自律的に畳む」＋「監視側で外から刈り取る」を両輪で持つこと。hung（ハングした）ジョブ対策の定石として覚えておくとよい。

まとめ

  • worker がデプロイ等で再起動されると、report できなかった run が Running のまま残る（ゾンビ化）。放置は資源の二重消費を招く。
  • 対策は二段構え。実行側にジョブ自身の timeout を持たせ、監視側にサーバの自動 Cancel ルールを重ねる。
  • 実行側は普段の主役だが、応答不能だと自壊できない。監視側はそれを外から刈り取る最後の砦。だから両方いる。
  • Crash 後に同一 ID で自動再投入されると開始時刻が過去に見えて混乱し、他ジョブと重なると I/O 飽和の連鎖故障を招くことがある。
  • 「実行主体が落ちうる」基盤（cron・CI・各種ワークフローエンジン）すべてに効く、汎用の hung ジョブ対策である。
