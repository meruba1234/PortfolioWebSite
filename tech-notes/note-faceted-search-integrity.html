Web技術

ファセット検索の整合性 — 「選択肢にあるのに選ぶと0件」を防ぐ

背景

商品一覧や検索画面で、カテゴリ・メーカー・担当者などの絞り込み（ファセット検索）をよく使う。このとき困るのが「絞り込みの選択肢としてリストに出ているのに、実際に選ぶと結果が 0 件になる」という現象だ。ユーザーからすれば「あるって書いてあったのに、選んだら何もない」わけで、UI への信頼が一気に崩れる。連動ドロップダウン（営業所を選ぶと担当者の候補が変わる、など）でも「担当者を選んだ瞬間に空になる」といった破綻が起きやすい。なぜこうなるのか、どう防ぐのかを整理しておく。

不整合が起きる仕組み

ファセット検索の UI には、実は 2 つの別々の計算が同居している。

  • 選択肢（facets）を生成する母集合 — 「カテゴリの選択肢として何を並べるか」を決めるためのデータ集合。
  • 結果を絞り込む条件 — 実際にユーザーが選んだ条件で行を絞り込む処理。

この 2 つが同じデータを見ていれば整合するが、別々のタイミング・別々の範囲で計算されるとズレる。選択肢は「全商品」から作ったのに、結果は「在庫あり かつ カテゴリ=飲料」で絞っている、といった状態だと、「在庫のないメーカー」も選択肢に残ってしまい、選ぶと 0 件になる。

固定選択肢の罠

いちばんよくある原因が、選択肢を初回に 1 回だけ取得して固定してしまうパターンだ。

  • 画面を開いた瞬間に「全カテゴリ」「全メーカー」を取ってきてドロップダウンに詰める。
  • その後ユーザーが別の条件（例: 在庫あり、期間、営業所）を変えても、選択肢は最初のまま追従しない。
  • 結果として、古くて広すぎる選択肢が残り続ける。
  • 現在の絞り込みでは 1 件も該当しないメーカーが、堂々とリストに並んでいる。

「選択肢は静的なマスタ、結果は動的なクエリ」という思い込みが根っこにある。実際にはファセットの選択肢も、現在の絞り込み状態に依存する動的な値だ。

連動ドロップダウン

連動ドロップダウン（カスケード選択）は、この問題がとりわけ表面化しやすい。

  • 例: 「営業所」を選ぶと「担当者」の候補が絞られる、という 2 段構え。
  • 担当者の候補を、営業所とは無関係に「全担当者」から作ってしまうと、選んだ営業所に所属しない担当者まで候補に出て、選ぶと 0 件になる。
  • 正しくは、上位の選択で絞り込まれた現在のデータから、下位の候補を動的に再計算する。
  • 上位を変えたら、下位の選択肢を作り直し、いま無効になった選択（前の営業所の担当者）はリセットする。

「上流の条件が変わったら、下流の選択肢と選択値の両方を作り直す」を徹底しないと、いつか必ず破綻する。

対策（facets 再計算 / 0件を出さない）

不整合を根絶するには、選択肢そのものを結果と同じ土俵で計算する。

  • 選択肢を絞り込み後の集合から再計算する — 「全件」ではなく「いま結果に含まれている行」からカテゴリ・メーカーを集計して選択肢を作る。こうすれば、選択肢と結果が常に同じデータ由来になり、原理的にズレない。
  • 0 件になる選択肢を出さない — 現在の絞り込みで該当が 0 件になる選択肢は、そもそもリストに載せない。
  • または、グレーアウトして件数を添える — 「飲料 (12)」「日用品 (0)」のように件数を併記し、0 件はクリック不可にする。存在自体は見せつつ、選んでも 0 件という体験は避けられる。どれを選ぶかは「選択肢が消えると混乱するか」次第。

いずれも本質は同じで、選択肢は現在の絞り込み状態の関数であると捉えること。

コストのトレードオフ

選択肢を毎回作り直すのは、当然ながら計算コストがかかる。

  • 絞り込みのたびに全ファセットを集計し直すと、その分の処理が増える。
  • データ件数が小さければクライアント側で全件から再計算する。手元に全データがあるので、絞り込みも facets 集計もブラウザ内で完結でき、サーバ往復もいらない。
  • データ件数が大きければサーバ側で集計する。全件をクライアントに送るのは非現実的なので、絞り込み条件を渡して、結果と facets の件数をまとめてサーバで計算して返す。
  • これは「クライアントでフィルタするか、サーバでフィルタするか」という判断とまったく同じ軸。件数と応答速度を見て決める。
  • 大きなデータでコストが気になるなら、facets 集計結果をキャッシュする、更新頻度を落とす、といった中間策もある。

まとめ

  • ファセット検索の不整合は、選択肢を作る母集合と結果を絞る条件がズレることで起きる。
  • 典型的な罠は「選択肢を初回に固定して他条件に追従させない」こと。連動ドロップダウンで特に露見する。
  • 根本対策は、選択肢を現在の絞り込み後の集合から再計算すること。0 件の選択肢は出さない、あるいはグレーアウト＋件数表示にする。
  • 再計算コストはデータ件数で判断し、小さければクライアント側、大きければサーバ側で集計する。
  • 「選択肢は静的なマスタ」ではなく「現在の絞り込み状態の関数」と捉えるのが肝。
