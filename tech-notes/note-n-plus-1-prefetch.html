N+1 クエリ問題と prefetch（バッチ取得）による解消

背景

一覧を表示する画面や帳票を作ると、最初は速いのに、データが増えるにつれて「なんだか表示が遅くなってきた」という現象によく出会う。件数が 10 件のときは一瞬なのに、1000 件になると数十秒待たされる、というやつ。

その多くは、コードのロジックが悪いのではなく DB への問い合わせ（クエリ）の投げ方 が原因になっている。代表格が N+1 クエリ問題。

このノートは、N+1 とは何か、なぜ遅くなるのか、そして prefetch（先にまとめて取る） でどう解消するかを整理しておくもの。

N+1 クエリ問題とは

まず「クエリ」とは、DB に対して「このデータをちょうだい」とお願いする 1 回の問い合わせのこと。 DB は別の場所（別プロセスやネットワークの向こう）にいるので、この問い合わせ 1 回ごとに 往復の待ち時間 がかかる。1 回あたりは数ミリ秒でも、回数が積もると効いてくる。

N+1 問題は、次のような書き方で起きる。

1) 一覧をまとめて取る          ← ここで 1 回
   例: 「今日の受注一覧」を取得（100 件返ってきた）

2) その 100 件を 1 件ずつループして、
   行ごとに関連データを 1 回ずつ取りに行く   ← ここで 100 回
   例: 各受注の「得意先名」を得意先マスタから引く

擬似コードで書くとこうなる。

orders = db.query("SELECT * FROM 受注 WHERE 日付 = ?", today)   # ← 1 回

for order in orders:                     # 100 件ぶんループ
    customer = db.query(                  # ← ループのたびに 1 回ずつ！
        "SELECT 名前 FROM 得意先 WHERE 得意先CD = ?",
        order.得意先CD,
    )
    print(order.番号, customer.名前)

最初の一覧取得で 1 回、そのあと行数（N 件）ぶんだけループ内で N 回。合わせて N + 1 回 のクエリが飛ぶ。だから「N+1 問題」と呼ばれる。

100 件なら 101 回、1000 件なら 1001 回。件数に比例してクエリ回数が増える のがポイント。

なぜ遅いのか

1 回のクエリ自体はごく軽い。問題は 回数 と、1 回ごとの 往復待ち時間。

DB は手元のメモリにあるわけではなく、問い合わせるたびに「お願いを送る → DB が処理する → 結果が返ってくる」の往復が発生する。この往復が 1000 回積み重なると、1 回あたりが数ミリ秒でも合計で数十秒に膨らむ。

実際に、あるバッチ処理でこの N+1 を解消したところ

  • 解消前: 40.58 秒
  • 解消後: 5.59 秒（約 7.3 倍 高速化）

という改善が出た。処理内容（計算ロジック）は一切変えず、 クエリの投げ方を変えただけ でこれだけ差が出る。

ループの中で毎回 DB を叩いていないか、というのは真っ先に疑うべきポイント。

解消: prefetch（先にまとめて取る）

考え方はシンプル。ループに入る前に、必要なデータを 1〜2 回のクエリでまとめて取ってしまう。そしてメモリ上の辞書（キーで一発で引ける表）に load しておき、ループの中では DB ではなく その辞書を引く ようにする。

手順は 3 段階。

  1. まず一覧を取り、必要なキーの集合 を集める（例: 出てきた得意先CD を全部）
  2. そのキーをまとめて WHERE key IN (?, ?, ...) で 1 回のクエリ で取得する
  3. 結果を辞書に load し、ループ内では辞書から引く（もう DB は叩かない）
orders = db.query("SELECT * FROM 受注 WHERE 日付 = ?", today)   # ← 1 回

# 1) 必要なキー（得意先CD）を重複なく集める
cd_list = {order.得意先CD for order in orders}

# 2) まとめて 1 回で取得する（IN でキーを列挙）
rows = db.query(
    "SELECT 得意先CD, 名前 FROM 得意先 WHERE 得意先CD IN (?, ?, ...)",
    cd_list,
)

# 3) キーで一発で引ける辞書にしておく
customer_map = {row.得意先CD: row.名前 for row in rows}

for order in orders:                       # ループ内は DB を叩かない
    名前 = customer_map[order.得意先CD]     # ← メモリ上の辞書を引くだけ
    print(order.番号, 名前)

これで、クエリ回数は N+1 回 → 2 回（一覧 1 回 + まとめ取り 1 回）に激減する。件数が 100 でも 1000 でも、クエリ回数は 2 回のまま変わらない。ここが効く。

IN (?, ?, ...) は「このリストのどれかに一致する行を全部ちょうだい」という書き方。往復 1 回で必要な分をごっそり取ってこられる。

メモ: IN に渡すキーが極端に多い場合（数千〜）は、DB 側の上限に当たることがある。そのときは 1000 件ずつなど、適度なまとまりに分割して数回に分ければよい。それでも「件数ぶん」ではなく「まとまりの数ぶん」なので、N+1 よりはるかに少ない。

2 段引きも 1 回に統合できる

「あるキーで引いて、その結果を使ってさらに引く」という 2 段引き も N+1 の一種。これも IN を使えば 1 回にまとめられることが多い。

さらに、「指定した順番どおりに並べて返してほしい」場合は、 ORDER BY CASE で並び順を指定すると、並べ替えのためにもう一度アプリ側で回す手間も省ける。

SELECT 商品CD, 名前
FROM   商品
WHERE  商品CD IN (?, ?, ?)
ORDER BY CASE 商品CD           -- 渡した順に並べて返す
           WHEN ? THEN 1
           WHEN ? THEN 2
           WHEN ? THEN 3
         END

「1 件ずつ順番に引いていた」処理を、IN + ORDER BY CASE の 1 クエリ に畳み込むイメージ。

ORM でも同じ問題が起きる

SQL を直接書かず、ORM（オブジェクトとテーブルを対応づけて、コードから DB を扱う仕組み）を使っていても、N+1 は同じように起きる。むしろ ORM だと「関連データにアクセスした瞬間、裏で自動的にクエリが飛ぶ」ため、 ループ内でうっかり N+1 を踏んでいることに気づきにくい。

for order in orders:
    print(order.customer.name)   # ← .customer に触れた瞬間、裏でクエリが 1 回飛ぶ

これを避けるための仕組みが、たいていの ORM に用意されている（呼び方はフレームワークごとに違う）。

  • JOIN でまとめて取る系（例: Django の select_related） … 一覧と関連データを 1 回のクエリで JOIN して取ってくる
  • 別クエリでまとめ取りする系（例: Django の prefetch_related、Laravel の with()） … 関連データを IN を使った別の 1 回のクエリでまとめて取り、ORM が対応づけてくれる

やっていることは、さっきの手作業の prefetch と本質的に同じ。 「ループ前にまとめて取る」を ORM がやってくれる だけ。

見分け方

N+1 は「なんとなく遅い」で片付けず、SQL ログを見れば一発で分かる。

多くの DB クライアントや ORM には、実際に発行したクエリを出力する機能がある。それを眺めて、

SELECT 名前 FROM 得意先 WHERE 得意先CD = 101
SELECT 名前 FROM 得意先 WHERE 得意先CD = 102
SELECT 名前 FROM 得意先 WHERE 得意先CD = 103
...（延々と件数ぶん続く）...

のように、ほぼ同じ形のクエリが件数ぶん連続して並んでいたら N+1 を疑う。値（101, 102, ...）だけが違って、形は全部同じ、というのが典型的なサイン。

「表示が件数に比例して遅くなる」現象とセットで、まずここを確認するとよい。

まとめ

  • N+1 クエリ問題 = 一覧を 1 回引いたあと、行ごとに関連データを 1 クエリずつ引くと、合計 N + 1 回 のクエリが飛ぶアンチパターン。件数に比例して遅くなる。
  • 遅い原因はロジックではなく DB 往復の回数。実測で 40.58 秒 → 5.59 秒（約 7.3 倍） の改善例もある。
  • 解消は prefetch（先にまとめて取る）。必要なキーを集めて WHERE key IN (?, ...) で 1〜2 回のクエリで一括取得し、メモリ上の辞書 に load してループ内はそこを引く。
  • 2 段引き も IN (?, ...) + ORDER BY CASE で 1 クエリに統合できることが多い。
  • ORM でも同じ問題が起きる。select_related（JOIN）/ prefetch_related・with()（別クエリでまとめ取得）等の仕組みで回避する（呼び方はフレームワークごとに違う）。
  • 見分け方: SQL ログにほぼ同じクエリが件数分連続して並んでいたら N+1 を疑う。
