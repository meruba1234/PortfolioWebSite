データベース

SQLite の UPSERT（ON CONFLICT）で冪等に蓄積する・PRAGMA でスキーマ調査

背景

定期的に同じデータソースを読み込んで、その結果を SQLite に貯めていく、という処理はよくある。たとえば「毎朝スナップショットを取り込んで蓄積テーブルに足していく」ようなバッチ。

このとき困るのが 同じデータを何度も流し込んでしまう ケース。バッチが二重起動したり、手動で再実行したり、前回と重複する範囲を含んでいたり。素直に INSERT するだけだと、そのたびに同じ内容の行がどんどん増えて、テーブルが膨らみ、あとで集計するときに二重計上してしまう。

やりたいのは「何度流し込んでも結果が同じ（冪等）」な蓄積。同じキーのデータは重複させず、既存行を更新するだけにしたい。これを実現するのが UPSERT（ON CONFLICT）。

このノートは、UPSERT の書き方、メタ列で履歴を取る工夫、実行順序の落とし穴、そしてスキーマ調査やロック対策まわりを整理しておくもの。

UPSERT（INSERT ... ON CONFLICT DO UPDATE）の書き方

UPSERT は「UPdate + inSERT」の合成語で、「キーが無ければ INSERT、既にあれば UPDATE」を 1 文でやってくれる。

前提として、テーブルに 主キー（PK）か UNIQUE 制約 があること。「同じキー」を判定する基準がこの制約になる。

CREATE TABLE items (
    item_key  TEXT PRIMARY KEY,   -- ここが競合判定のキー
    name      TEXT,
    price     INTEGER
);

このテーブルに冪等に流し込むには、こう書く。

INSERT INTO items (item_key, name, price)
VALUES (?, ?, ?)
ON CONFLICT(item_key) DO UPDATE SET
    name  = excluded.name,
    price = excluded.price;

ポイントは 2 つ。

  • ON CONFLICT(item_key) … item_key が既存行とぶつかったら、後半の UPDATE に切り替わる。
  • excluded.xxx … いま INSERT しようとして「はじかれた（excluded）」新しい値を指す特別な名前。つまり「新しく来た値で上書きする」という意味になる。

Python から呼ぶとこうなる。

import sqlite3

conn = sqlite3.connect("store.db")
conn.execute(
    """
    INSERT INTO items (item_key, name, price)
    VALUES (?, ?, ?)
    ON CONFLICT(item_key) DO UPDATE SET
        name  = excluded.name,
        price = excluded.price
    """,
    ("A-001", "りんご", 120),
)
conn.commit()

これで、同じ item_key="A-001" を何回流し込んでも、行は 1 本のまま。 2 回目以降は中身が更新されるだけ。テーブルの行数はキーの母数で頭打ちになる。入力が重複していても安心して流せる、というのが UPSERT の効きどころ。

メタ列で「いつから存在するか」の履歴を取る

UPSERT のうまみは「重複しない」だけではない。 メタ列（データそのものではなく、記録の履歴を表す列）を持たせると、「このキーはいつ初めて現れて、最後に確認できたのはいつか」が分かるようになる。

よく使うのは次の 3 つ。

  • first_seen … 初めて登場した日時（INSERT 時だけセット、以降は変えない）
  • last_seen … 最後に確認できた日時（流すたびに更新）
  • count … 登場回数（流すたびに +1）
CREATE TABLE items (
    item_key   TEXT PRIMARY KEY,
    name       TEXT,
    price      INTEGER,
    first_seen TEXT,
    last_seen  TEXT,
    seen_count INTEGER
);
INSERT INTO items (item_key, name, price, first_seen, last_seen, seen_count)
VALUES (?, ?, ?, :now, :now, 1)
ON CONFLICT(item_key) DO UPDATE SET
    name       = excluded.name,
    price      = excluded.price,
    last_seen  = excluded.last_seen,       -- 最終確認日時は更新する
    seen_count = items.seen_count + 1;     -- 既存の値に +1
    -- first_seen は SET に含めない → INSERT 時の値のまま保持される

ここでのコツは、first_seen を UPDATE 側（SET）に書かないこと。 UPSERT の UPDATE で触らなかった列は、既存の値がそのまま残る。だから「初出日時」は最初に入った値のまま凍結され、last_seen だけが動いていく。

seen_count = items.seen_count + 1 のように、 テーブル名.列名 で既存行の現在値を参照できるのも覚えておくと便利。（excluded.xxx が「新しく来た値」、items.xxx が「今 DB にある値」。）

こうしておくと、蓄積テーブルがそのまま「登場履歴の台帳」になる。「この項目はいつからあるか」「もう来なくなった項目はどれか（last_seen が古い）」があとから追える。

ハマりどころ: UPSERT の実行順序で権威データを潰す

一番やらかしやすいのがこれ。 複数の経路から同じテーブルに UPSERT するとき、その実行順序を誤ると、後から流した「緩い」UPSERT が、先に確定させた「権威ある」データを上書きしてしまう。

たとえばこういう状況。

  • 経路 A: 人が確認して「確定」フラグを立てた、信頼できるマスタ更新
  • 経路 B: 自動取り込みの、まだ確定していない暫定データ

もし経路 A のあとに経路 B が同じキーを素朴に UPSERT すると、 確定フラグまで暫定値で塗り替えてしまう。せっかく人が確定させたのに台無し。

-- 危険な例: 全列を無条件に上書きしてしまう
INSERT INTO items (item_key, price, is_confirmed)
VALUES (?, ?, 0)                       -- 暫定なので is_confirmed=0 で来る
ON CONFLICT(item_key) DO UPDATE SET
    price        = excluded.price,
    is_confirmed = excluded.is_confirmed;  -- ← 確定(1)を 0 に戻してしまう！

守り方は 2 つ。

(1) 更新対象カラムを絞る … 緩い経路の UPSERT では、権威ある列（確定フラグ等）を SET に含めない。触らなければ既存値が残る。

ON CONFLICT(item_key) DO UPDATE SET
    price = excluded.price;
    -- is_confirmed は SET に入れない → 確定フラグは保護される

(2) 条件付き更新（WHERE で守る） … ON CONFLICT ... DO UPDATE には WHERE を付けられる。条件を満たすときだけ更新するようにして、古い・弱いデータで新しい・強いデータを潰さないようにする。

INSERT INTO items (item_key, price, updated_at)
VALUES (?, ?, ?)
ON CONFLICT(item_key) DO UPDATE SET
    price      = excluded.price,
    updated_at = excluded.updated_at
WHERE excluded.updated_at > items.updated_at;   -- 新しいときだけ更新

WHERE excluded.updated_at > items.updated_at は「新しく来たデータの日時が、今ある行の日時より新しいときだけ更新する」の意味。順序が前後して古いデータが遅れて届いても、新しい値を守れる。

教訓としては、「誰でも書ける緩い経路」と「権威ある確定経路」が同じテーブルを触るなら、 UPSERT は無条件全上書きにしない。列を絞るか、条件で守る。

スキーマ調査: PRAGMA と sqlite_master

UPSERT を書くには、まず どの列が PK / UNIQUE なのかを正確に知る必要がある。 ON CONFLICT(...) に指定するキーが制約と合っていないとエラーになるからだ。既存 DB を触るときは、想像で書かずにスキーマを確認する。

列の一覧・型・PK を見る: PRAGMA table_info(テーブル名)

PRAGMA table_info(items);

各列について次が返る。

返る列意味
cid列の通し番号
name列名
type宣言された型（TEXT / INTEGER 等）
notnullNOT NULL なら 1
dflt_valueデフォルト値
pk主キーなら 1 以上（複合キーだと順番が入る）

pk が 1 以上の列を見れば、ON CONFLICT(...) に何を書けばいいか分かる。

CREATE 文をそのまま見る: sqlite_master テーブル

PRAGMA では読み取りにくい UNIQUE 制約や複合キーも、 元の CREATE 文を丸ごと見れば確実。SQLite は定義を sqlite_master に保持している。

SELECT sql FROM sqlite_master WHERE name = 'items';

これで CREATE TABLE items ( ... PRIMARY KEY ... UNIQUE ... ) が定義したときの文字列そのままで返ってくる。制約まわりを一次情報で確認したいときはこれが最強。

Python から一覧を見るなら、PRAGMA table_list や SELECT name FROM sqlite_master WHERE type='table' でテーブル名の一覧も取れる。

timeout とロック対策

SQLite は 1 ファイルを複数の接続で触れるが、書き込みは基本 1 本ずつ。別の接続が書き込み中だと database is locked エラーが出ることがある。バッチと手動実行が重なった、みたいなときに踏みやすい。

対策として、接続時に ロック待ちの上限（timeout） を設定できる。

conn = sqlite3.connect("store.db", timeout=10)   # 最大 10 秒はロック解放を待つ

timeout=10 は「ロックされていても、すぐ諦めずに最大 10 秒は解放を待つ」設定。一瞬のロックならこれで自然に待ってやり過ごせる。デフォルトは 5 秒と短めなので、書き込みが混みそうなバッチでは明示しておくと安定する。

あわせてメモリ効率の話も。大きなテーブルを扱うとき、全件読んでからアプリ側で絞るのは非効率。最初から WHERE で対象キーに絞って読めば、DB もメモリも軽くなる。

# 良い: 必要なキーだけ DB 側で絞って取る
rows = conn.execute(
    "SELECT * FROM items WHERE item_key IN (?, ?, ?)",
    keys,
).fetchall()

「全部 load してから Python で filter」より、「SQL の WHERE で絞ってから load」のほうが、通信量もメモリも小さく済む。

UNIQUE 制約違反が出たときの切り分け

蓄積処理を書いていると UNIQUE constraint failed に出くわすことがある。このとき、つい「分割処理の境目（バッチとバッチのつなぎ目）で重複したのかな」と疑いたくなるが、まず疑うべきは「同一入力データの中の重複」。

つまり、今まさに流し込もうとしている 1 回ぶんのデータの中に、既に同じキーが 2 つ以上入っていないか。ここが原因なことが多い。

# 投入前に、入力データ内でキーが重複していないか確かめる
from collections import Counter

dup = [k for k, n in Counter(r["item_key"] for r in records).items() if n > 1]
if dup:
    print("入力データ内で重複しているキー:", dup)

境界（前回ぶんとの重なり）は UPSERT の ON CONFLICT がそもそも吸収してくれるので、実は問題になりにくい。それでも UNIQUE 違反が出るということは、 1 回の投入の内側で既にキーがダブっているケースが疑わしい。入力の作り方（重複除去の漏れ、結合の取りこぼし）を見直すのが近道。

まとめ

  • UPSERT（INSERT ... ON CONFLICT(pk) DO UPDATE SET ...）を使うと、同じキーを何度流し込んでも重複行を作らず既存行を更新できる（冪等な蓄積）。テーブルの行数はキーの母数で頭打ちになる。
  • メタ列（first_seen / last_seen / seen_count）を持たせると、「いつから存在し、最後にいつ確認できたか」の履歴が取れる。 first_seen は SET に含めないことで初出値を凍結できる。
  • 実行順序の罠: 緩い経路の UPSERT が、確定済みの権威データを上書きしないよう、 更新カラムを絞る か 条件付き更新（WHERE excluded.x > table.x） で守る。
  • スキーマ調査: PRAGMA table_info(テーブル名) で列・型・PK を確認、 SELECT sql FROM sqlite_master WHERE name='テーブル名' で CREATE 文（制約含む）を確認。
  • ロック対策: sqlite3.connect(path, timeout=10) で待ち時間の上限を設定。大きなテーブルは全読せず WHERE で対象キーに絞ってから読む。
  • UNIQUE 違反が出たら、分割の境界より先に 同一入力データ内の重複 を疑う。
