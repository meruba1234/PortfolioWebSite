業務で調べた内容を、後から読み直すために自分用にまとめた学習ノートです。社内固有の情報（サーバー名・IPアドレス・取引先名・社内システム名）は含めていません。公開にあたって内容を再確認していますが、個人の理解を整理したものであり、記述の正確性を保証するものではありません。

セキュリティ

認証情報の扱いと改ざん検知 — Secret / 環境変数注入 / sha256 マニフェスト

背景

自動化ジョブやバッチ処理を書いていると、必ず 2 つの問題にぶつかる。

  1. 認証情報をどこに持つか — DB パスワード、API キー、アクセストークンといった機密を、コードや設定ファイルに書けば動くのは動く。だがそのファイルはリポジトリに入り、バックアップされ、画面共有で映り、退職者の PC にも残る。平文で持った瞬間に「漏れうる場所」が指数的に増える。
  2. 生成したファイルが途中で改ざん・破損していないか — 集計結果や送信用データを作って後段の処理に渡すとき、その中身が「自分が作った時のまま」である保証がない。誰か（あるいは別のプロセス）が書き換えても、そのまま流れてしまう。

この 2 つは別々の話に見えるが、根っこは同じ「信頼できない前提で守りを設計する」という発想でつながっている。以下、認証情報の持ち方から改ざん検知まで順に整理する。

1. 認証情報はコードや設定ファイルに平文で書かない

まずこれが大原則。悪い例。

# 絶対にやってはいけない
DB_USER = "app_user"
DB_PASSWORD = "P@ssw0rd123"   # ソースに直書き
API_KEY = "sk-live-abcdef..."  # 設定ファイルに直書きも同じく NG

平文で書くと、

  • Git 履歴に永久に残る（後から消しても履歴を漁れば出てくる）
  • ファイルを読める人 = 秘密を読める人、になり権限分離ができない
  • ローテーション（定期的な入れ替え）のたびにコード修正・再デプロイが必要

正しくは、Secret ストア（各種のシークレット管理機能。クラウドの Secrets Manager、Vault、CI/CD のシークレット、ジョブ基盤のシークレットブロックなど何でもよい）に置く。そして実行時に取り出して使う。

2. 機密は Secret、非機密は通常の設定値（Variable 等）で使い分ける

ありがちな失敗が「何でもかんでも Secret に入れる」こと。Secret ストアは取り回しに手間がかかる（監査ログ、権限、値のマスキング等）ので、機密でない値まで入れると運用が重くなり、かえって「どれが本当に守るべき秘密か」が見えなくなる。

判断はシンプルに、漏れたら困るか で分ける。

種類例置き場所
機密パスワード、API キー、トークン、秘密鍵Secret ストア
非機密ホスト名、URL、ポート、機能フラグ、対象年月通常の設定値（Variable / 環境変数 / config ファイル）

ホスト名や URL は漏れても直接の被害は小さく、むしろ運用でよく参照・変更するので、普通の設定として扱うほうが実務的。「機密でない値まで Secret にするのは過剰」と覚えておく。

3. スクリプトは「特定の環境変数を要求する」契約にする

Secret ストアから取り出した値を、スクリプトへどう渡すか。ここで 環境変数への注入 が効いてくる。

スクリプト側は「この環境変数が入っている前提で動く」という契約だけ持つ。値がどこから来たか（Secret か、手で export したか）は知らない。

import os

# スクリプトは env を読むだけ。出どころは関知しない
db_user = os.environ["DB_USER"]
db_password = os.environ["DB_PASSWORD"]

conn = connect(user=db_user, password=db_password, host=os.environ["DB_HOST"])

こうしておくと、同じコードのまま実行方法を切り替えられる。

本番 — ジョブ基盤が Secret を取り出し、環境変数へ展開してからスクリプトを起動する（イメージ）。

# 基盤側が Secret ストアから解決して注入するイメージ
export DB_PASSWORD="$(secret-get db/password)"
export DB_USER="$(secret-get db/user)"
export DB_HOST="db.internal.example"
python job.py

手動実行・デバッグ — 自分で env をセットするだけ。コードは 1 行も変えない。

export DB_USER=app_user
export DB_PASSWORD=****      # 手元で一時的に
export DB_HOST=db.internal.example
python job.py

「秘密の解決」と「スクリプト本体」が分離されているのがポイント。スクリプトはテスト可能なままで、秘密の受け渡しは実行環境に委ねられる。

4. 生成物の改ざん・破損は sha256 マニフェストで検知する

認証情報の話から視点を変えて、今度は作ったファイルが後段で無事かという整合性の話。

定番の手法が、生成時に各ファイルの sha256（内容から計算されるハッシュ値。中身が 1 バイトでも変われば全く違う値になる）を manifest（目録）ファイルに記録しておくこと。後段で再計算して突き合わせれば、改ざん・破損を検知できる。

生成側。

import hashlib, json
from pathlib import Path

def sha256_of(path: Path) -> str:
    h = hashlib.sha256()
    h.update(path.read_bytes())
    return h.hexdigest()

manifest = {
    "batch_id": "20260709_1200",
    "files": {
        "output/data.csv":    sha256_of(Path("output/data.csv")),
        "output/summary.xlsx": sha256_of(Path("output/summary.xlsx")),
    },
}
Path("output/manifest.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2), encoding="utf-8"
)

検証側（後段の処理やアップロード直前）。

manifest = json.loads(Path("output/manifest.json").read_text(encoding="utf-8"))
for rel_path, expected in manifest["files"].items():
    actual = sha256_of(Path(rel_path))
    if actual != expected:
        raise RuntimeError(f"改ざん/破損の疑い: {rel_path}")

ハッシュが一致しなければ「作った時と違う」ことが確実に分かる。ネットワーク転送中のビット化け、ディスク破損、意図しない上書き、悪意ある改変——原因を問わず「同一でない」事実を掴める。

これは秘密保持の代わりではなく、別の層の守りであることに注意。sha256 は「変わっていないこと」を保証するが、「誰が書いたか」までは保証しない（それが必要なら署名や HMAC の領域）。あくまで defense in depth の一層として置く。

5. 運用のハマりどころ — 正当な編集時は manifest 側も同時更新する

sha256 マニフェストを入れると、逆に運用でハマる典型がある。

正当な理由でファイルを直接直したのに「改ざん」と誤検知される。

たとえば、生成後に「この 1 行だけ手で直したい」という正当な修正をすると、ファイルの中身が変わる → ハッシュが変わる → manifest の記録と食い違う → 検証が「改ざん」と叫ぶ。仕組みは正しく働いているのに、人間の運用が追いついていない状態。

対処はシンプルで、正当にファイルを編集したら manifest 側のハッシュも同時に更新する。中身と記録は常にペアで動かす。

# 正当に編集したら、記録も同時に更新する
p = Path("output/data.csv")
# ... 中身を直す ...
manifest["files"]["output/data.csv"] = sha256_of(p)
save(manifest)   # 片方だけ変えて放置しない

さらに注意したいのが、識別子を多重に結びつけている場合。実運用では「バッチ ID = フォルダ名 = manifest 内の ID」のように、同じ識別子を複数箇所に持たせて紐付けることがある。整合性は上がるが、その分片方だけ変えると全体が壊れる。

batch_20260709_1200/          ← フォルダ名
  manifest.json               ← { "batch_id": "20260709_1200", ... }

フォルダをリネームしたら manifest 内の batch_id も直す。逆も同じ。「ここを変えたら、連動しているどこを直す必要があるか」を常にセットで意識する。これは sha256 に限らず、冗長に持たせた識別子はすべて同期義務が生まれるという一般則。

6. まとめ — 多層防御（defense in depth）

一連の話を貫くのは、1 つの対策に頼らず、複数の層で守りを重ねるという考え方（defense in depth / 多層防御）。

  • 秘密を平文で持たない（Secret ストア） … 漏洩の起点を減らす層
  • 機密と非機密を分ける … 守るべきものを絞り、運用を軽くする層
  • 環境変数注入の契約 … 秘密の受け渡しをコードから分離する層
  • sha256 マニフェスト … 中身が変わっていないことを検知する層

どれか 1 つが破られても、次の層が残る。逆に言えば、どれも単独では万能でない。sha256 は秘密を隠さないし、Secret ストアは改ざんを検知しない。役割の違う守りを層として重ねることで、初めて実務に耐える堅さになる。

そして最後に運用の教訓。層を増やすほど「正当な変更のときに全部の層を揃えて更新する」責任も増える。仕組みだけ入れて運用が追いつかないと、誤検知や不整合で自分の首を絞める。守りの仕組みと、それを維持する手順は必ずセットで設計する。
