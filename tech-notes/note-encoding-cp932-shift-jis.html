プログラミング

CP932 と Shift_JIS の違い・日本語ファイルの文字化け対処

背景

日本語の Windows で作られた CSV やテキストファイルをプログラムで読もうとして、文字化けに悩まされた経験は誰にでもある。とりあえず shift_jis を指定してみたら一部の文字だけ例外で落ちたり、コンソールに出したら全部化けて見えたのにファイル自体は壊れていなかったり、という「一見同じに見えるけど原因が違う」トラブルが起きやすい。

このノートは、そういう「日本語ファイルの文字化け」を切り分けるための土台を整理しておくものである。特に押さえたいのは次の3点。

  • Shift_JIS と CP932 は同じではない（似ているが別物）
  • エンコーディングは自動判定に頼らず明示するのが安全
  • 「化けている」問題には、データが壊れている場合と、表示だけの場合の2種類がある

具体的な社名や案件は伏せ、一般的な例（\\server\share や「会社の基幹システム」など）で説明する。

Shift_JIS と CP932 の関係

まず用語を整理する。

呼び名実体補足
Shift_JISJIS 規格ベースの日本語エンコーディング「素の」Shift_JIS。収録文字が狭い
CP932Microsoft が拡張した Windows 版 Shift_JIS機種依存文字・全角空白などを追加。別名 Windows-31J, MS932

ポイントは、CP932 は Shift_JIS の上位互換的な拡張だということ。日本語 Windows のメモ帳や Excel、そして多くの「会社の基幹システム」が吐き出す CSV・テキストは、UTF-8 ではなく 実質 CP932 であることが非常に多い。

ここで落とし穴になるのが、Python の codec 名の扱いである。

raw = b"\x81\x40"  # CP932 における全角空白　のバイト列

raw.decode("shift_jis")  # 文字によっては UnicodeDecodeError で落ちる
raw.decode("cp932")      # 正しく読める

shift_jis codec は「素の Shift_JIS」に近い範囲しか受け付けないため、Windows 由来のデータに含まれる拡張文字（全角空白 　、丸数字、一部の記号など）で例外になることがある。Windows が作ったファイルを読むなら、迷わず cp932 を指定するのが正解。

なぜ「自動判定」に頼ってはいけないか

文字コードを推定してくれるライブラリ（chardet など）や、エディタの自動判別は便利だが、業務データの読み書きでは推定を信用しない方がよい。理由は2つ。

  1. 推定は外れる。特に行数が少ない・英数字が多いファイルは、CP932 なのに別のコードと誤判定されることがある。
  2. 既存システムとバイト単位で一致させたい場面がある。たとえば基幹システムが出力したファイルを読み、加工して、また同じシステムに取り込ませる場合、エンコーディングを1文字でも取り違えると、見た目が同じでもバイト列が変わり、取り込み側で弾かれたり別の文字に化けたりする。ここでの取り違えは致命傷になりやすい。

安全なパターンは「バイト列でそのまま読んで、明示的に decode する」こと。

# 推奨: バイナリで読んで、エンコーディングを明示する
with open(path, "rb") as f:
    raw = f.read()
text = raw.decode("cp932")   # 何のコードで読んだか、コードに残る

# 書き戻すときも明示する（相手が CP932 を期待しているなら）
with open(out_path, "wb") as f:
    f.write(text.encode("cp932"))

open(path, encoding="cp932") と直接指定してもよいが、いずれにせよ「どのエンコーディングで読んだか」をコード上に明示するのが肝心で、環境やライブラリ任せの自動判定にしないことが要点である。

「文字化けに見える」問題は2種類ある

ここが一番ハマるところ。「画面に変な文字が出ている」とき、原因は大きく2つに分かれる。

種類何が起きているかデータの状態
(a) 実データが壊れている誤ったエンコーディングで decode/encode してしまったファイル・文字列そのものが破損
(b) 表示だけの問題データは正常。コンソール（端末）の表示エンコードが合っていないだけデータは無傷

(b) は特に紛らわしい。データは正しく読めているのに、それを print() したときにターミナルの表示エンコードが違うせいで化けて見えるだけ、というケースがよくある。この場合ファイルを別の正しいツールで開けば普通に読める。

切り分け方

見た目に振り回されず、中身の実体を確認する。有効なのが repr() と、実際のコードポイント（U+XXXX）を見ることである。

s = "取"
print(s)          # 端末次第で化けて見えることがある（あてにならない）
print(repr(s))    # 'を' → '取' のように実体が見える
print(hex(ord(s[0])))  # 0x53d6  ← U+53D6 = 「取」

# バイト列で持っているなら、まず生バイトを見る
print(raw[:20])   # b'\x8e\xe6...' のように生の姿を確認できる

たとえば文字列が内部的に U+53D6（「取」）を正しく保持していると確認できれば、データは壊れていない。あとは表示側（端末のコードページや出力先のエンコード）を直せばよい、と判断できる。逆に repr() の時点で意図しないコードポイントや �（置換文字）が出ていれば、それは (a) の実データ破損なので、読み込み時のエンコーディング指定にさかのぼって直す必要がある。

表示が化けている ≠ データが壊れている。この区別を最初につけるだけで、無駄に読み込み処理を書き直す事故を防げる。

関連する別テーマ（このノートの範囲外）

混同しやすいが、別の話として切り分けておく。

  • Unicode NFKC 正規化: 全角と半角、合成済み文字と結合文字など、「見た目が近い別コードの表記揺れ」を吸収する処理。文字コード変換とは目的が違う（照合・検索のための正規化）。別テーマとして扱う。
  • 改行コード CRLF / LF: Windows と Unix の改行差の問題。文字化けと同時に遭遇しがちだが原因は別。詳細は別ノート git-line-endings-crlf-lf.md を参照。

まとめ

覚え方として、次の3つを押さえておけば大きく外さない。

  1. Windows の日本語ファイルは cp932 で読む。shift_jis は拡張文字で落ちる（全角空白 　 が踏み絵）。CP932 = 拡張された Shift_JIS、と覚える。
  2. 自動判定に頼らず、バイトで読んで明示 decode。既存システムとバイト一致させたいときほど、取り違えは致命傷。
  3. 「化けて見える」ときは、まず repr() とコードポイント。データ破損 (a) か、表示だけ (b) かを切り分ける。表示が化けていてもデータは無事なことがある。
