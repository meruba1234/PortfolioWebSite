データ突合名寄せ設計

異種データの突合・名寄せの設計（安定キー・合成キー分解・正規化・貪欲マッチの限界）

背景

別々に育った 2 つのシステムのデータを突き合わせたい、という場面は多い。たとえば「外部サービスから届く明細（PDF や CSV）」と「自社の販売管理 DB の売上明細」が同じ取引を指しているか確認したい、といったケースだ。

理想は両者に共通の一意キー（伝票番号など）があって JOIN 一発で済むこと。しかし現実にはそんなキーは無く、あっても桁数や表記が食い違う。

外部データ:  取引先=「株式会社○○商店」 商品=87654321(8桁) 納品日=2026/07/01 金額=12,000
自社DB:      得意先CD=1001         商品CD=654321(6桁)  納品日=20260701  金額=12000

「同じ取引なのに素直に結合できない」——この状況をどう設計で越えるか、を整理する。突合ツールを作るときに毎回悩むポイントなので、原則としてまとめておく。

結合キーは「変化しにくいフィールド」を選ぶ

まず、何をキーにして両者を紐付けるかを決める。ここで表記ゆれのあるフィールドを選ぶと最初から破綻する。

  • 部署名・会社名・商品名などの名称系フィールドは結合キーに向かない。「株式会社○○商店」「(株)○○商店」「○○商店」が同じ相手を指す、といった表記ゆれが必ず出る。
  • 氏名（人物）やコード（得意先CD・商品CD）など、運用上変化しにくいフィールドでマッチする。コードは付け替えが稀で、名称のような揺れが少ない。

名称は最終的な照合結果の表示には使うが、紐付けの判定には使わない。これが名寄せ設計の第一原則。

合成キーの分解と、規則の裏取り

レガシー DB には「1 カラムに複数の意味を桁位置で詰めたコード」がよくある。

担当CD = 1203
  ├ 上2桁 "12" = 課コード
  └ 下2桁 "03" = 課内の担当者番号

こういう合成キーは、そのままでは相手テーブルの「課マスタ」や「担当者マスタ」と結合できない。桁位置で分解してからでないと引けない。

分解規則を推測したら、必ず複数サンプルで裏取りする。危険なのは、たまたま別キー同士が同値で「引けてしまう」偶然があること。

1件だけ見て「担当CD の下2桁 = 担当者番号」と決めつける
  → 実は下2桁が別の意味で、たまたま担当者番号と一致していただけ、というワナ

1 サンプルで「引けた」ことは規則の証明にならない。何件かで一貫して成立するか、規則が崩れる境界（桁あふれ・特殊値）は無いかを確認する。

正規化は突合する両側で対称に適用する

桁数や書式が食い違うキーは、正規化して揃える。よくあるのが「8 桁コードの下 6 桁を取る」「日付の区切り文字を除く」といった変換。

このとき鉄則なのが、両方のテーブルに同じ規則を適用すること。片側だけ正規化すると、キーが揃わず全件不一致という派手な事故になる。

def normalize_shohin_cd(code: str) -> str:
    """商品CDを突合キーに正規化する。両テーブルで必ず同じ関数を通す。"""
    s = str(code).strip()
    # 8桁で来る側は下6桁を取る。元から6桁ならそのまま。
    if len(s) >= 8:
        s = s[-6:]
    return s.zfill(6)   # 桁数を固定して揃える
# NG: 外部データ側だけ正規化して、DB側は生のまま突合 → 全件ミスマッチ
left_key  = normalize_shohin_cd(row_ext["商品CD"])
right_key = row_db["商品CD"]            # ← 揃わない

# OK: 両側を同じ関数に通す
left_key  = normalize_shohin_cd(row_ext["商品CD"])
right_key = normalize_shohin_cd(row_db["商品CD"])

設計上の注意点。

  • 桁数可変を想定する。常に 8 桁とは限らず 6 桁や 7 桁が混ざることがある。「下 6 桁を取る」は 8 桁前提のコードで、6 桁のものに適用すると崩れないか確認する。
  • 特殊プレフィックス（区分を表す先頭記号、集約用の予約コードなど）は正規化の対象外にするか、除外する。
  • 名称の表記ゆれ吸収（全角半角・大文字小文字など）は NFKC 正規化の領域なので、別ノートの Unicode 正規化と併用する。役割が違う 2 種類の正規化を混同しない。

貪欲マッチの限界

キーを揃えても、同一キーの候補が複数あると紐付けの一意性が崩れる。同じ商品・同じ日に複数明細があると、「どの明細とどの明細が対か」が確定しない。

素朴な実装は、左の 1 件を取って右の候補リストから先頭を消費する貪欲マッチになる。これは順序に依存し、本来一致できた組が「未マッチ」に取り残されることがある。

左: A(100) B(100)
右: X(100) Y(100)

貪欲: A→X を確定 → B は残りの Y と対に
  結果として B-Y の対が正しかったのに、A-Y / B-X が正解だったケースを取りこぼす

重要なのは、合計金額や「差異の有無」には影響しないことが多い点。 100+100 は 200 のままなので照合の合否判定は変わらない。だが「どの明細に紐付くか」は前後する。明細単位のトレースが要る用途では問題になる。

対処の指針。

  • 合否や差額の総量だけ見たいなら、貪欲でも実害は出にくい。割り切ってよい。
  • どの行とどの行が対かを厳密に確定したいなら、貪欲をやめて 割当問題（マッチング／二部グラフの最適割当）として解く。コスト（金額差や日付差）を最小化する組合せを全体最適で求める。

「合計は合うのにペアリングが直感と違う」と言われたら、たいてい貪欲マッチが原因。

データ不整合はツール側で直さない

突合していると、マスタ側の都合で結合が空になることがある。典型は欠番——退職者の担当者レコードが削除され、明細に残る担当CDがどのマスタ行にも当たらない、といったもの。

これはデータ側の問題であって、突合ツール側では直せないし、直すべきでもない。

  • ツールがマスタを補完・書き換えて「無理やり引ける」ようにするのは筋が悪い。データの真実を歪めることになる。
  • マッチ失敗した明細はスキップして記録し、全体の処理は止めない設計にする。 1 件の欠番で突合全体がクラッシュするのは避ける。
for row in details:
    master = master_map.get(row.tantou_cd)
    if master is None:
        # 欠番など。ツール側で捏造せず、未解決として残して次へ
        unresolved.append(row)
        continue
    matched.append((row, master))

# 未解決は「データ側で要確認」として報告する。ツールは真実を歪めない。

責務の切り分けが肝心で、ツールは「照らし合わせる」ところまでを受け持ち、 マスタの正しさはデータ側の責任として分離する。

まとめ

  • 結合キーは表記ゆれのある名称でなく、変化しにくいコード・氏名を選ぶ。
  • 桁詰めされた合成キーは分解が要る。規則は複数サンプルで裏取りし、偶然の一致に騙されない。
  • 桁揃えなどの正規化は両側で対称に。片側だけだと全件不一致。桁数可変・特殊プレフィックスに注意。
  • 同一キーが複数あると貪欲マッチは取りこぼす。合計は合ってもペアリングは狂う。厳密さが要るなら割当問題として解く。
  • マスタ欠番などの不整合はツールで直さない。失敗はスキップして記録し、全体を止めない。
