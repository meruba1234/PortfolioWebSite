プログラミング

累積・差分処理の冪等性バグ（再検知の繰り返し・集約漏れ）

背景

「毎回、既存データを読み込んで、そこに新しい結果を追記する」タイプの処理を書いていると、実行するたびに件数や理由（reasons）が少しずつ膨れ上がっていく、という現象に出くわすことがある。

たとえば「異常な受注を検知して一覧に貯めていく」ような処理。1回目は3件、2回目は6件、3回目は9件…と、実際には何も起きていないのに検知件数だけが増え続ける。あるいは、1件の伝票に対して「新規取引」「数量が多い」といった検知理由が、実行回数ぶんだけ重複して並んでしまう。

これらはたいてい 冪等性（べきとうせい）が壊れている ことが原因だ。累積型・追記型の処理で特に踏みやすいので、パターンとして整理しておく。

冪等性とは

冪等性とは、同じ処理を何度実行しても結果が同じになる という性質のこと。

  • 冪等な処理: 「この鍵に値 5 を代入する」→ 何回やっても値は 5。
  • 冪等でない処理: 「この鍵に 5 を足す」→ 1回目は 5、2回目は 10、3回目は 15…と増え続ける。

累積処理や差分処理は「前回の状態に今回の結果を足し込む」構造なので、うっかりすると後者になりやすい。「このバッチは1日に何度流れても大丈夫か？」を常に自問するとよい。

典型バグ1: 「読み込む → 再検知 → 追記」で件数・理由が膨れる

一番多いのがこれ。毎回こういう流れで処理する。

  1. 既存の結果ファイルを読み込む
  2. 元データを再検知する
  3. 検知結果を既存に 追記 する

このとき、同じキー（伝票番号など）が毎回「新規」として判定され、そのたびに append されると、同じものが何個も並んでしまう。

# アンチパターン: リストへ append する経路に重複ガードがない
results = load_existing()          # 既存の検知結果（リスト）
for row in detect(source_data):    # 再検知（毎回同じキーが出てくる）
    results.append(row)            # ← 重複ガードなし。実行のたび増殖する
save(results)

results が dict（キー→値） なら、同じキーへの代入は上書きになるので重複しない。これは冪等。

# dict なら上書きされるので冪等
results = load_existing()          # {伝票番号: 検知結果}
for key, row in detect(source_data):
    results[key] = row             # 同じ key なら上書き。何回流しても同じ
save(results)

問題は リストに append する経路 や、理由（reasons）をリストに足していく経路。ここには必ず重複ガードを入れる。

# reasons を足すときも既存を見てからにする
if reason not in record["reasons"]:
    record["reasons"].append(reason)

ポイントは「追記する前に、それが既にあるか確認する」。キーで持てるものはリストではなく dict / set で持つと、そもそも重複しにくい設計になる。

典型バグ2: iterrows は明細行ごとに複数回まわる（集約漏れ）

pandas で df.iterrows() を回すとき、その DataFrame が 明細行 の粒度だと、1件の伝票に対してループが複数回まわる。

伝票のつもりでループしているのに、実際は「伝票 × 明細行数」ぶん回ってしまい、同じ伝票の結果を何個も生成してしまう。

# アンチパターン: 明細行の DataFrame をそのまま回す
for _, row in df.iterrows():       # 1伝票に明細が3行あれば3回まわる
    detected.append(make_card(row))  # 同じ伝票のカードが3枚できる

表示したい単位が「伝票単位」なら、ループの前に その単位へ集約 しておく。

# 伝票単位に集約してから回す
grouped = (
    df.groupby("伝票番号")
      .agg({"金額": "sum", "商品CD": "first"})
      .reset_index()
)
for _, row in grouped.iterrows():   # 1伝票につき1回
    detected.append(make_card(row))

あるいは、キー列で重複排除してから回す。

unique = df.drop_duplicates(subset="伝票番号")

「今このループは、どの粒度で回っているのか？（明細か、伝票か、取引先か）」を常に意識する。粒度の取り違えは、件数がきれいに整数倍でズレるのが特徴。

母集合の取り違え: 検知側と表示側で違う DataFrame を見ている

検知（判定）に使う DataFrame と、画面に表示する値を計算する DataFrame が違うと、数字が食い違う。

  • 検知側: 全期間を集計した DataFrame（平均や標準偏差を出すため広く取る）
  • 表示側: 直近だけを抽出したあとの DataFrame

同じ「平均」でも、母集合が「全期間」か「抽出後」かで値が変わる。検知では異常と判定されたのに、画面に出す平均値は別の母集合で計算していて、見る人が「この数字だと異常に見えないが？」と混乱する。

対策は、どの母集合（母数）を見ているかを変数名やコメントで明示する こと。

df_all = load_full_history()        # 全期間: 統計量（平均・標準偏差）算出用
df_recent = df_all[df_all["納品日"] >= cutoff]  # 直近抽出: 表示・判定対象

mean_all = df_all["数量"].mean()    # 判定の基準はこちら
# 表示にも判定と同じ母集合の値を使う（df_recent の平均を出さない）

「どちらの数字が正なのか」を先に決めて、検知と表示で同じ母集合を参照させる。

過去分は修復スクリプトで直す（コード修正だけでは戻らない）

一番忘れがちな点。バグの原因を突き止めてコードを直しても、既に膨れてしまった過去のデータはそのまま残る。

累積型の処理は「前回の状態」を引き継ぐので、汚れた状態がずっと入力として使われ続ける。コード修正はあくまで「今後、新たに汚れないようにする」だけ。

だから、別途 掃除（修復）スクリプト を1回だけ流して、過去分を正しい状態に直す必要がある。

# 過去分の掃除: reasons の重複を除去し、キー重複をまとめる
data = load_existing()
for key, record in data.items():
    # 重複した reasons を順序を保ったまま一意化
    record["reasons"] = list(dict.fromkeys(record["reasons"]))
save(data)

修復スクリプトは、

  • 実行前に必ずバックアップを取る
  • 何を直したか（件数・対象キー）をログに出す
  • できれば「1回流しても2回流しても同じ結果になる」＝これ自体も冪等に作る

とよい。冪等な修復スクリプトなら、途中で失敗しても安心して再実行できる。

まとめ

  • 冪等性 = 同じ処理を何度実行しても結果が同じになる性質。累積・追記型の処理はこれを壊しやすい。
  • 追記の重複: リストへ append する経路・reasons を足す経路には必ず重複ガードを入れる。キーで持てるものは dict / set にすると設計から重複しにくくなる。
  • iterrows の集約漏れ: 明細行の DataFrame は伝票 × 明細行数ぶん回る。表示単位で groupby / drop_duplicates してから回す。件数が整数倍でズレたら粒度を疑う。
  • 母集合の取り違え: 検知側（全期間集計）と表示側（抽出後）で違う DataFrame を見ると値がズレる。どの母数を見ているか明示し、判定と表示で揃える。
  • 過去分は修復スクリプト: コード修正は「今後汚さない」だけ。既に膨れたデータは別途、冪等な掃除スクリプトで直す。バックアップとログを忘れずに。
