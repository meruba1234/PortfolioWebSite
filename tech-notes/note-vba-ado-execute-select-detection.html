データベース

VBA/ADO の conn.Execute が Recordset を返す＝SELECT の見分け方

背景

古い業務アプリは VBA（Excel/Access マクロ）から ADO 経由で DB にアクセスしていることが多い。こういうレガシー VBA を Python などに移植したり、読み取り専用ユーザーで動かせないか検討したりするとき、まず知りたいのは このアプリは DB を書き換えているのか、それとも読むだけなのか という一点だ。

これはコメントや仕様書ではなく、コードの実挙動で裏取りしたい。仕様書が「参照専用」と書いていても、どこかで UPDATE を投げていたら意味がない。逆に、コードのすべてが読み取りだと確認できれば、「このアプリは読み取り専用ユーザーで動く＝編集権限のパスワードは不要」と根拠を持って言える。

その判定に効くのが、ADO の conn.Execute の 戻り値の受け方 を見る、という小技だ。

Execute の戻り値で SELECT かを見分ける

ADO の Connection.Execute(sql) は、SQL の種類によって戻り値が変わる。

  • SELECT は 結果セット（Recordset）を返す。だから戻り値を受けるために Set rs = conn.Execute(sql) の形になる。
  • INSERT / UPDATE / DELETE は結果セットを返さない。だから戻り値を受けず、conn.Execute sql の形（Set なし・カッコなしの文形式）で書かれる。
' SELECT — 結果を Recordset で受ける（読み取り）
Dim rs As ADODB.Recordset
Set rs = conn.Execute("SELECT 得意先CD, 得意先名 FROM M_得意先")
Do Until rs.EOF
    Debug.Print rs.Fields("得意先名").Value
    rs.MoveNext
Loop

' UPDATE — 戻り値を受けない（書き込み）
conn.Execute "UPDATE M_得意先 SET 住所 = '東京' WHERE 得意先CD = 100"

Set rs = が付いているかどうかが、そのまま「読んでいるか／書いているか」のシグナルになる、というわけだ。VBA では戻り値を使う呼び出しはカッコ付き、使わない呼び出しはカッコなしの文形式になる文法の都合も、この見分けを後押ししてくれる。

全箇所を洗い出して「読み取り専用」を証明する

この見分け方が本当に力を発揮するのは、1 箇所ではなく コード中の全 Execute を洗ったとき だ。

grep で \.Execute を全部拾い、それぞれが Set rs = conn.Execute(...) の形（＝ SELECT）になっているかを確認する。もし全箇所が Recordset 受けなら、このアプリは DB を一度も書き換えていないと言える。1 つでも Set なしの conn.Execute があれば、そこが書き込みの疑いポイントなので中身の SQL を確認する。

# 全 Execute 箇所を洗い出す（PowerShell / ripgrep）
rg -n "\.Execute" .\src\

洗い出しの結果がすべて SELECT だったら、これは強い証拠になる。「仕様書にそう書いてあるから」ではなく、「コードのすべての DB アクセスが読み取りだと確認したから」読み取り専用と結論できる。

権限最小化（least privilege）の根拠にする

この裏取りは、権限最小化の判断に直結する。

DB アカウントには必要最小限の権限だけを与えるのが原則（least privilege）だ。アプリが読むだけなら、SELECT だけを許可した読み取り専用ユーザーで動かせばいい。そうすれば、万一コードがバグっても DB 側が書き込みを物理的に弾いてくれる。

「このアプリは読み取り専用ユーザーで動かせるか？」という問いに、Execute の全数調査は コードの実挙動という一次情報 で答えを出せる。編集権限つきのアカウントやそのパスワードを使い回す必要がなくなり、事故の芽をひとつ潰せる。

ADO の基礎と Recordset.Open の注意

前提として、ADO の主要オブジェクトの役割を押さえておく。

オブジェクト役割
ConnectionDB への接続。conn.Execute で SQL を投げる入口
RecordsetSELECT の結果セット。行を 1 件ずつ辿る（MoveNext / EOF）
Commandパラメータ付き SQL やストアドを実行する。cmd.Execute も同様に戻り値で判別できる

ここで 注意点 がひとつある。DB アクセスは conn.Execute だけとは限らない。Recordset を先に作って rs.Open(sql, conn) で開くパターンもある。

' Recordset.Open 経由の SELECT — こちらも読み取り
Dim rs As ADODB.Recordset
Set rs = New ADODB.Recordset
rs.Open "SELECT * FROM M_商品", conn, adOpenStatic, adLockReadOnly

つまり洗い出しでは \.Execute だけでなく \.Open も見る必要がある。Recordset.Open は基本 SELECT だが、adLockReadOnly 以外のロックモード（adLockOptimistic など）を指定して rs.Update で書き戻す使い方もありうるので、ロック指定と .Update の有無まで確認すると確実だ。Execute と Open の両輪で網羅する、と覚えておく。

移植時の使い所

レガシー VBA を Python などに移すとき、最初にやるべきは このアプリが DB を書き換えているかの判定 だ。

  • 全 Execute / Open を洗って、すべて読み取りだと分かれば、移植先も読み取り専用ユーザーで組める。接続情報も参照専用アカウントで済む。
  • 書き込み箇所が見つかれば、そこがトランザクション・整合性・ロールバックを設計する必要のある要注意ポイントとして最初から浮かび上がる。

「まずコードから DB への影響範囲を確定させる」という下ごしらえが、移植の安全設計の出発点になる。Execute の戻り値という小さなシグナルが、その第一歩を支えてくれる。

まとめ

  • ADO で Set rs = conn.Execute(sql)（戻り値を Recordset で受ける）は SELECT（読み取り）。conn.Execute sql（戻り値なし）は INSERT/UPDATE/DELETE の疑い。
  • 全 Execute 箇所を洗って、すべてが Recordset 受けなら そのコードは読み取り専用ユーザーで動くと根拠を持って言える。
  • 洗い出しでは Recordset.Open 経由の DB アクセスも見る（ロックモードと .Update の有無まで確認すると確実）。
  • コードの実挙動で裏取りできると、権限最小化の判断や移植の安全設計を、仕様書任せにせず一次情報で進められる。
