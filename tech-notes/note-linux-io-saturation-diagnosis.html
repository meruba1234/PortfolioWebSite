インフラ

Linux の「詰まり」診断 — D state / iowait / swap による I/O 飽和

背景

「サーバが妙に重い。応答が返ってこない処理がある」——けれど top を見ると CPU 使用率（us + sy）はガラ空き、ロードアベレージだけが異様に高い。こういう状況で「CPU が足りない」「DB がロックしている」と決め打ちすると原因を外す。

CPU が空いているのにプロセスが進まないとき、真っ先に疑うべきは ディスク I/O の飽和 だ。プロセスは計算しているのではなく、ストレージからのデータ到着を「待たされて」動けなくなっている。この状態のサインが、プロセスの D state と、システム全体の iowait である。

以下、D state の意味 → 確認コマンド → swap と I/O 飽和がなぜ連鎖するか → 対処 → 終了処理に失敗した残骸プロセスの見分け方、の順に整理する。

D state（uninterruptible sleep）とは

ps や top でプロセスの状態コードが D になっているのは、割り込み不可能なスリープ (uninterruptible sleep) の状態だ。

主なプロセス state コードを並べると次のとおり。

state意味ざっくり
RRunning / Runnable実行中、または実行待ち行列にいる
SInterruptible sleep何かのイベント待ち。シグナルで起こせる（通常の待機）
DUninterruptible sleepカーネル内の I/O 完了待ち。シグナルでも起こせない
ZZombie終了したが親が回収 (wait) していない
TStoppedジョブ制御で停止中

D が重要なのは、たいてい ストレージ I/O の完了待ちだからだ。プロセスはカーネルに「このページを読んでくれ」と頼み、ディスクからデータが返ってくるまで文字どおり身動きが取れない。kill -9 すら効かない（起こせないので死ねない）のはこのためだ。

wchan で待ち箇所を確認する

そのプロセスが「カーネルのどの関数で寝ているか」は wchan (wait channel) でわかる。

$ ps -eo pid,stat,wchan:32,comm
  PID STAT WCHAN                            COMMAND
 4821 D    folio_wait_bit_common            some_worker
 4822 D    folio_wait_bit_common            some_worker
 1200 S    ep_poll                          nginx

folio_wait_bit_common（旧カーネルでは wait_on_page_bit 等）は、ページキャッシュ上のページの I/O が終わるのを待っているという意味だ。つまりこのプロセスは「ディスクが遅い / 詰まっている」から止まっている。CPU 100% でもなければ DB のロック競合でもない。ストレージが律速だというサインだ。

単一プロセスだけ見るなら /proc から直接読める。

$ cat /proc/4821/wchan
folio_wait_bit_common

ポイント: D state のプロセスが並んでいて wchan が I/O 待ち系なら、犯人はアプリのロジックではなくストレージ層。「アプリを再起動」ではなく「ディスクの負荷」を見に行く。

裏取り — iowait を測る

D state は「個々のプロセスが I/O 待ち」というミクロの証拠。次にシステム全体で I/O が飽和しているかをマクロで裏取りする。見るべき指標は 3 つ。

1. top の wa（iowait）

%Cpu(s):  3.1 us,  1.2 sy,  0.0 ni, 12.4 id, 83.0 wa,  0.3 hi,  0.0 si

wa（iowait）は、CPU がヒマ (idle) なのに、I/O の完了待ちで先に進めない時間の割合だ。上の例のように wa が 80% 超で us/sy が数 % なら、CPU は余っているのにディスク待ちで詰まっている典型。id（idle）ではなく wa に張り付くのがミソ。

2. iostat -x の %util

デバイスごとの飽和度を見るなら iostat（sysstat パッケージ）が決定打。

$ iostat -x 1
Device   r/s    w/s   rkB/s   wkB/s  await  aqu-sz  %util
sda    412.0   88.0  52736.0  1408.0  38.20    9.85  99.7
  • %util … そのデバイスが I/O を処理していた時間の割合。99〜100% ならほぼ飽和（これ以上流しても捌けない）。
  • await … 1 リクエストあたりの平均応答時間 (ms)。大きいほど遅い。
  • aqu-sz … 平均キュー長。リクエストが行列を作って待っている。

%util が張り付いていれば、ディスクが物理的に処理能力の上限に達している。

3. vmstat の b と wa

全体傾向をざっと掴むなら vmstat。

$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- --system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  8 512000  81000  2000 400000  120  480  9800   140  900 1500  3  2 11 84  0
  • b … uninterruptible sleep (= D state) にいるプロセス数。ここが常に大きいと I/O 待ちのプロセスが溜まっている。
  • wa … iowait（top と同じ意味）。
  • si / so … swap in / swap out（後述、ここが動いていると要注意）。

3 つとも同じ方向を指す（wa 高い・%util 飽和・b 多い）なら、診断は「I/O 飽和」で確定に近い。

swap が I/O 飽和を連鎖させる仕組み

「なぜ急にディスクが詰まったのか」の裏に swap が絡んでいることが多い。ここが本質的にいやらしいポイントだ。

メモリの奪い合い → ページの追い出し

物理メモリ (RAM) が足りなくなると、カーネルは当面使っていないメモリページを swap 領域（ディスク上）に退避 (swap out) して空きを作る。

たとえば RSS が巨大なプロセス（大きなデータを抱えた DB プロセスなど） が RAM を握ると、他の（無関係な）プロセスのページが押し出されて swap に追い出される。

追い出されたページの読み戻しがディスク I/O を生む

問題はここから。swap に追い出されたページに再びアクセスすると、カーネルはそれを ディスクから読み戻す (swap in) 必要がある。メモリアクセスのつもりが、裏でディスク I/O に化ける。

  • swap in / out はそれ自体がディスク I/O。→ ディスクの帯域を食う。
  • ディスクが混むと、swap と無関係な通常の read/write まで待たされる。
  • その結果、メモリを奪われた側だけでなく、まったく別の軽い処理まで I/O 待ちで固まる。

これが 連鎖遅延 だ。「1 つの重いプロセスがメモリを食う」→「他プロセスが swap に落ちる」→「読み戻しでディスクが飽和」→「システム全体が D state で詰まる」。犯人（メモリを食ったプロセス）と被害者（固まった無関係な処理）が別なので、被害者側だけ見ると原因がわからない。

[重い DB プロセス: 大 RSS]  ── RAM を占有 ──▶  他プロセスのページが swap out
                                                   │
                              再アクセス ◀─────────┘
                                   │ swap in（ディスク read）
                                   ▼
                          ディスク %util 飽和
                                   │
                                   ▼
              無関係な処理まで I/O 待ち (D state) で固まる ← 連鎖遅延

vmstat の si/so が継続的に動いている、free -h で Swap の used が増え続けている、といった兆候があれば swap 起因を疑う。

$ free -h
              total        used        free      shared  buff/cache   available
Mem:            15Gi        13Gi       200Mi        50Mi       1.8Gi       800Mi
Swap:          4.0Gi       3.2Gi       800Mi

available が枯渇し Swap used が積み上がっていれば、メモリ不足 → swap → I/O 飽和のシナリオに乗っている可能性が高い。

対処候補

原因（誰が RAM を食い、何が I/O を飽和させているか）を掴んだうえで、状況に応じて選ぶ。

対処内容効くケース
スケジュールをずらす重いバッチ同士・重い処理と DB の高負荷時間帯が重ならないよう時間を分散する特定時刻に I/O 競合が集中している
vm.swappiness を下げるページをどれだけ積極的に swap out するかの傾向値 (0〜100)。下げるとスワップアウトを抑え、なるべく RAM に留めるまだ RAM に余地があるのに早々に swap している
メモリを増やす物理 RAM を増設する。根本解決恒常的にメモリが足りず swap 常用になっている

vm.swappiness の確認と一時変更:

$ cat /proc/sys/vm/vm.swappiness        # 現在値（多くのディストリで既定 60）
60
$ sudo sysctl vm.swappiness=10          # 一時的に下げる（再起動で戻る）

恒久化するなら /etc/sysctl.d/*.conf に vm.swappiness = 10 を記述する。

注意: swappiness を下げるのは「swap を使う原因（メモリ不足）」の対症療法。RAM が本当に足りていないなら、下げすぎると今度は OOM Killer が走る。根本はメモリ増設やメモリを食う処理の見直し。

補足 — 残骸プロセスの見分け方

I/O 診断でプロセス一覧を眺めていると、たまに RSS が極端に小さい（数十 KB） とか、メモリ表示が N/A になっているプロセスに出くわす。これは正常稼働ではなく、終了処理に失敗した残骸（孤立プロセスやゾンビ） の可能性がある。

  • ゾンビ (Z) … 実体は終了済み。プロセステーブルにエントリだけ残っている。親が wait() で回収していないため成仏できない状態。メモリはほぼ消費していない（だから RSS が異様に小さい / N/A）。CPU も食わない。
  • 孤立 (orphan) … 親が先に死に、init/systemd (PID 1) に引き取られたプロセス。こちらは通常再回収されるが、中途半端な状態で残ることがある。

見分け方の例:

$ ps -eo pid,ppid,stat,rss,comm
  PID  PPID STAT   RSS COMMAND
 7788     1 Z        0 old_worker <defunct>   ← rss=0, STAT=Z, <defunct> がゾンビの目印

STAT に Z、コマンド名に <defunct>、RSS が 0 なら典型的なゾンビ。ゾンビ自体はリソースをほぼ食わないので直接の I/O 犯人ではないが、大量に溜まっているなら「親プロセスが子を回収できていない = どこかで終了処理が壊れている」というサイン。I/O 飽和の真犯人を探す前に、まず「このプロセスは生きて働いているのか、死にきれない残骸か」を切り分けておくと、無駄な調査を減らせる。

まとめ

  • CPU が空いているのにサーバが重いなら、まず I/O 飽和 を疑う。CPU 不足や DB ロックと決め打ちしない。
  • プロセスの D state（uninterruptible sleep） で wchan が folio_wait_bit_common 等になっているのは、カーネルのストレージ I/O 完了待ちで動けないサイン。
  • 裏取りは 3 点セット: top の wa（iowait） が高い / iostat -x の %util が 99〜100% / vmstat の b（blocked） が多い。ps -eo pid,stat,wchan,comm や cat /proc/<pid>/wchan で待ち箇所を特定。
  • swap は I/O を連鎖させる。大 RSS のプロセスが RAM を握る → 他プロセスのページが swap out → 読み戻しでディスク I/O 発生 → 無関係な処理まで I/O 待ちで固まる。犯人と被害者が別なのがやっかい。
  • 対処は スケジュールをずらす / vm.swappiness を下げる / メモリを増やす。swappiness を下げるのは対症療法で、根本はメモリ不足の解消。
  • RSS が極端に小さい / メモリ N/A のプロセスは残骸（ゾンビ・孤立）の疑い。働いているプロセスと死にきれないプロセスを切り分けてから真犯人を追う。
