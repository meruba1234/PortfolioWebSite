プログラミング

短いIDの照合と正規表現の落とし穴（部分一致の誤ヒット・findall の順序）

背景

伝票番号や商品コードなど、桁数の少ない ID 同士を突き合わせる処理はよくある。「片方のデータに現れた ID を、もう片方のテキストや DB カラムから探して一致を判定する」というシンプルな照合だ。ところが、この「探す」を素朴に実装すると、

  • 本当は別物なのに一致したと誤判定される（誤ヒット）
  • 本当は同じなのに見つからない（ヒット漏れ）

という両方向のバグが起きる。とくに ID が短い（4桁程度）と、より長い数字列の一部にたまたま含まれてしまったり、相手側の書式（ハイフンやスペース入り）とズレて拾えなかったりする。ここでは、その落とし穴と対策を順に整理する。

部分一致は危険 — 短いIDは長い数字列に埋もれる

SQL の LIKE '%1234%' や Python の '1234' in s は「部分文字列として含まれるか」を見る。短い ID だと、まったく無関係な長い数字列の中に偶然含まれてしまう。

target = "1234"

# 誤ヒット: 別の伝票番号 12345678 の中に 1234 が含まれる
"1234" in "12345678"   # True （本当は別の番号なのに一致してしまう）
"1234" in "0012340056" # True （途中に紛れ込んでいるだけ）

逆に、相手側の書式が違うと今度はヒット漏れする。

# ヒット漏れ: 接頭辞やスペースが入ると単純一致では拾えない
"1234" in "INF-1234"   # True （これはたまたま拾えるが…）
"1234" in "12 34"      # False （スペースが混入すると取りこぼす）

部分一致は「緩すぎて誤ヒット」しつつ「書式差には脆くて漏れる」という、一番厄介な外し方をする。

対策1: 正規表現の境界で前後が数字でないことを保証する

「その ID の前後が数字でないこと」を後読み (?<!\d) と先読み (?!\d) で保証すると、長い数字列への埋もれ込みを弾ける。

import re

pattern = r"(?<!\d)1234(?!\d)"

bool(re.search(pattern, "12345678"))   # False （前後が数字なので不一致）
bool(re.search(pattern, "伝票 1234 の件")) # True  （独立した 1234 として一致）
bool(re.search(pattern, "No.1234-05"))  # True  （前後が数字でなければOK）

\b（単語境界）でも似たことはできるが、\b は「単語文字（英数字・アンダースコア）との境目」なので、ABC1234 のように英字が隣接するケースを弾けない。「前後が数字でないこと」を厳密に言いたいなら (?<!\d)…(?!\d) の方が意図に忠実。

対策2: 桁数の下限を設ける

そもそも短すぎる ID は照合キーとして信頼できない。「5桁未満は照合に使わない」といった下限を設けるだけで、偶然一致の母数を大きく減らせる。

def is_usable_key(code: str) -> bool:
    digits = re.sub(r"\D", "", code)  # 数字以外を除去
    return len(digits) >= 5           # 5桁未満はキーにしない

短い ID しか無い場合は、ID 単独ではなく「日付＋ID」「取引先＋商品コード」のように複合キーにして識別性を上げる、という設計判断もここで検討する。

対策3: 突合の前に両側を正規化してから完全一致で比べる

一番の本質的対策は、「探す（部分一致）」のをやめて「そろえて（正規化して）完全一致で比べる」に切り替えること。区切り記号・空白を除去し、必要なら桁数をゼロ埋めでそろえてから比較する。

def normalize_code(code: str) -> str:
    # 区切り記号・空白・接頭辞を除去して数字だけにし、桁数をそろえる
    digits = re.sub(r"\D", "", code)   # "INF-1234" -> "1234", "12 34" -> "1234"
    return digits.zfill(8)             # 8桁ゼロ埋めで書式を統一

normalize_code("INF-1234") == normalize_code("00001234")  # True
normalize_code("1234")     == normalize_code("12345678")  # False （別物と正しく判定）

こうすると「INF-1234」も「12 34」も「00001234」も同じキーに落ち、かつ長い番号との誤ヒットも起きない。誤ヒットと漏れの両方を同時に潰せるのが強み。

findall の順序の罠 — result[0] は「最初に出た値」であって「正解」ではない

複数マッチを拾う re.findall は、文書内に出現した順でリストを返す。「たぶん先頭が目的の値だろう」と result[0] を採ると、たまたま先に出てきた無関係な数字を掴むことがある。

text = "受付 9999 / 伝票番号 1234 / 数量 12"

nums = re.findall(r"(?<!\d)\d+(?!\d)", text)
# ['9999', '1234', '12']  ← あくまで出現順。先頭 = 正解ではない

nums[0]  # '9999' （受付番号であって、欲しい伝票番号ではない）

ここで「[0] を [1] にすればいい」と位置で対処するのは対症療法で、テキストの体裁が変わった瞬間に崩れる。正しくは採用ロジック側を明示する。

# ラベルの直後の値だけを狙う（優先順位・フィルタを採用ロジックに書く）
m = re.search(r"伝票番号\s*(?<!\d)(\d+)(?!\d)", text)
denpyo = m.group(1) if m else None   # '1234'

期待と違う要素が選ばれるときは、抽出の並び順を疑う前に、「どれを採るか」の判断（ラベル一致・桁数・優先順位）を書いていない＝採用ロジック側のバグ、と考えるのが正しい切り分けだ。

まとめ

  • 短い ID の照合で LIKE '%…%' や in の部分一致は、長い数字列への埋もれ込みで誤ヒットし、書式差で漏れる。両方向に外す。
  • 境界 (?<!\d)…(?!\d) で前後が数字でないことを保証すると、埋もれ込みを弾ける。\b より意図に忠実。
  • 桁数の下限（例: 5桁未満はキーにしない）で偶然一致の母数を減らす。短ければ複合キー化も検討。
  • 本質対策は「探す」をやめて「正規化して完全一致」。区切り・空白除去＋桁数そろえで、誤ヒットと漏れを同時に潰せる。
  • re.findall は出現順で返る。result[0] は「最初の値」であって「正解」ではない。ズレたら抽出順ではなく採用ロジック（ラベル・優先順位・フィルタ）側を疑う。
