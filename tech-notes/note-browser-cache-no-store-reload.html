Web技術

ブラウザキャッシュと no-store / ハードリロード — 「直したのに反映されない」

背景

Web アプリを修正してデプロイした。サーバ上のファイルは確かに新しくなっている。なのにブラウザで開くと、以前のままの画面が表示される。CSS の色が変わっていない、直したはずのボタンが古いラベルのまま、追加した要素がどこにもない——。

「デプロイに失敗したのか」「ビルドがおかしいのか」と疑いたくなるが、多くの場合、原因は ブラウザが古いファイルをキャッシュ（保持）している だけだ。このズレの正体と、正しい切り分け方・対処法をまとめる。

「no-store を返しているのに古いまま」はなぜ起きるか

HTTP には、レスポンスをキャッシュしてよいかどうかを指示する Cache-Control ヘッダがある。

Cache-Control: no-store

no-store は「このレスポンスは一切保存するな」という強い指示だ。これを返していれば毎回サーバから取り直すはず——と思いがちだが、現実にはズレが残る。

  • ヘッダの適用対象と実際にブラウザが握っているものが食い違う。例: HTML には no-store を付けたが、そこから読み込む CSS/JS には付いておらず、そちらが古いまま使われる。
  • 既にブラウザのキャッシュに入っていた古いレスポンスが、ヘッダ変更後も「まだ有効」と判断されて再利用される。
  • Service Worker やプロキシなど、ブラウザとサーバの間にある別のキャッシュ層が古いものを返している。

つまり no-store を付けたつもりでも、「今この画面に見えているもの」がどこ由来なのかを確認しないと、原因を取り違える。

切り分け: サーバが古いのか、ブラウザが古いのか

まずやるべきは サーバが実際に何を返しているか を、ブラウザの表示とは別ルートで直接確認することだ。

方法1: DevTools の Network タブでレスポンス本文を見る。

  1. F12 で DevTools を開く
  2. Network タブを開いた状態でページを再読み込み
  3. 対象のリクエスト（HTML や CSS）を選び、Response タブで中身を確認
  4. 直したはずの要素・文言がその本文に入っているかを見る

方法2: ブラウザを介さず curl で生のレスポンスを取る。

# ヘッダと本文の両方を確認（-i でヘッダ込み表示）
curl -i https://example.com/app/

# ヘッダだけ見たいとき
curl -I https://example.com/app/

# 目的の文言が本文に含まれるか（Windows の Git Bash でも動く）
curl -s https://example.com/app/ | grep "新しいボタンのラベル"

判定は単純だ。

  • レスポンス本文に 新しい内容が入っている → サーバは正しい。画面が古いのは ブラウザ（またはその手前）のキャッシュ。次章の対処へ。
  • レスポンス本文が まだ古い → サーバ側の問題。デプロイ未反映、ビルド漏れ、配信先ディレクトリ違いなどを疑う。

「画面が古い」だけで判断せず、必ずレスポンスの実体を見るのが鉄則。

対処: ハードリロードと Disable cache

サーバは正しいと分かったら、ブラウザにキャッシュを捨てさせて取り直させる。

  • ハードリロード（スーパーリロード）: Ctrl+F5（多くのブラウザ）。キャッシュを無視してサーバから取り直す。Mac 系は Cmd+Shift+R。
  • DevTools の Disable cache: DevTools を開き、Network タブの「Disable cache」にチェック。DevTools を開いている間だけ キャッシュを無効化する。開発中はこれを付けっぱなしにしておくと、毎回ハードリロードしなくて済む。

これで直れば、原因はキャッシュだったと確定できる。ただしこれは「自分の手元」の一時対処にすぎない。ユーザー全員がハードリロードしてくれるわけではないので、恒久対策が別途要る。

恒久対策: キャッシュバスティング（ファイル名にハッシュ）

配布先のユーザーに毎回ハードリロードを強いるのは非現実的だ。静的アセット（CSS/JS/画像）は ファイル名にハッシュを含める のが定石。内容が変わればファイル名が変わり、URL 自体が別物になるので、ブラウザは「見たことのない URL」として確実に取り直す。これをキャッシュバスティングと呼ぶ。

<!-- 更新のたびに URL が変わらない: 古いキャッシュが再利用されやすい -->
<link rel="stylesheet" href="/static/app.css">

<!-- 内容が変わると名前も変わる: 別 URL になり必ず再取得される -->
<link rel="stylesheet" href="/static/app.9f3c1a2b.css">
  • 多くのビルドツール（バンドラ）は、この「内容ハッシュ付きファイル名」を自動生成する。
  • HTML 側はキャッシュさせず（毎回取り直す）、 HTML が参照する CSS/JS はハッシュ付きで長期キャッシュ、という組み合わせが基本形。 HTML は毎回最新を取り、その中の URL が変わることで新しいアセットへ切り替わる。
  • 簡易的に app.css?v=20260709 のようなクエリ文字列でバージョンを変える手もあるが、ファイル名ハッシュのほうが確実で扱いやすい。

補足: 非 ASCII を URL に載せるときはエンコード

デバッグでクエリやパスに日本語などの非 ASCII を含めることがある。 URL に直接そのまま置くと化けたり弾かれたりするので、URL エンコードが要る。

# 例: 検索語に日本語を渡す。--data-urlencode が安全
curl -G "https://example.com/search" --data-urlencode "q=商品名"
# → https://example.com/search?q=%E5%95%86%E5%93%81%E5%90%8D 相当に変換される
  • JavaScript なら encodeURIComponent("商品名") でエンコードできる。
  • 「手で組み立てた URL だと動かないが、ブラウザのアドレスバー経由だと動く」ときは、ブラウザが裏でエンコードしてくれているだけ、というケースが多い。

まとめ

  • 「デプロイしたのに反映されない」の多くは、サーバではなく ブラウザのキャッシュ が原因。
  • Cache-Control: no-store を返していても、対象範囲のズレや手前のキャッシュ層で古いまま残ることがある。
  • 切り分けは レスポンスの実体を直接見る（DevTools の Response / curl）。新しい内容が入っていればサーバは正しく、犯人はブラウザ側。
  • 手元の即時対処は Ctrl+F5（ハードリロード）と DevTools の「Disable cache」。
  • 恒久対策は ファイル名ハッシュによるキャッシュバスティング。更新時に別 URL になり確実に取り直される。
  • URL に日本語など非 ASCII を載せるときは URL エンコードを忘れない。
