インフラ

コンテナからホスト/別コンテナの処理を呼ぶ手段の分類

背景

コンテナの中で動いているプロセスから、「コンテナの外にある処理」を呼びたくなる場面は多い。たとえば次のようなケースだ。

  • ホスト側にしかないツールやスクリプトを実行したい
  • 依存ライブラリが重すぎるので、その処理だけ別コンテナに分離して呼び出したい
  • ホスト上の別サービスに仕事を依頼したい

こういうとき、まず思いつくのが SSH でホストに入って叩く方法だが、実は SSH は数ある手段の「一実装」にすぎない。手段を体系的に整理しておかないと、「とりあえず SSH」のように反射的に選んでしまい、後で権限や結合度の問題に悩むことになる。ここでは選択肢を3系統に分類して整理する。

コンテナ外の処理を呼ぶ3系統

コンテナ内から外の処理を呼ぶ手段は、大きく次の3系統に整理できる。

系統代表的な実装仕組み向いている用途
ネットワーク経由SSH / HTTP API / メッセージキュー相手をネットワーク上のサービスとして扱い、プロトコルで通信する疎結合にしたい、相手が別ホストでもよい、非同期にしたい
Docker socket 経由docker exec / Docker APIホストの Docker デーモンを操作し、兄弟コンテナを起動・実行する依存ライブラリを別コンテナに分離して呼び出す等
マウント経由bind mount + スクリプト実行ホストのパスをコンテナに見せ、そこにあるスクリプトを直接実行するホスト上の既存スクリプトを軽く呼びたい

ポイントは、SSH はネットワーク経由という系統の一実装でしかないということ。「外の処理を呼ぶ = SSH」ではなく、「まずどの系統か」を選び、その中で実装を選ぶ、という順で考えると迷いが減る。

ネットワーク経由

相手をネットワーク上のサービスとみなして通信する。SSH はそのうちの一つで、ほかにも HTTP API を叩く、メッセージキュー（ジョブキュー）にタスクを積むなどがある。

[コンテナ] --HTTP/SSH/MQ--> [ホストや別コンテナ上のサービス]

相手の内部実装を知らなくても、決められたプロトコルさえ守れば呼べる。3系統の中でもっとも疎結合で、相手が同じホストにいる必要すらない。

Docker socket 経由

ホストの /var/run/docker.sock をコンテナにマウントすると、そのコンテナから Docker デーモンを操作できるようになる。これにより、コンテナの中から docker exec で「兄弟コンテナ」を起動・実行できる。

# ホストの docker.sock をコンテナにマウントする例
docker run -v /var/run/docker.sock:/var/run/docker.sock myimage

# コンテナ内から兄弟コンテナのコマンドを実行
docker exec sibling-container python heavy_task.py

たとえば「メイン処理は軽いコンテナで動かしたいが、ある処理だけ重い依存ライブラリを必要とする」ようなとき、その重い処理を別コンテナに分離しておき、docker.sock 経由で呼び出す、という設計ができる。

マウント経由

bind mount でホスト側のディレクトリをコンテナに見せておき、そこに置いたスクリプトをコンテナ内から実行する。

docker run -v /opt/host-scripts:/scripts myimage /scripts/run.sh

一番シンプルだが、コンテナとホストのファイル配置が密結合になりやすく、実行環境（ホスト側にそのスクリプトの依存が揃っているか）にも依存する。

docker.sock マウントの権限に注意

docker.sock 経由は便利だが、セキュリティ上とても重い選択であることを忘れてはいけない。

docker.sock をマウントするということは、そのコンテナに ホストの Docker デーモンを自由に操作する権限を与えるということだ。Docker デーモンは通常 root 権限で動いているため、docker.sock を握ったコンテナは、

  • ホストのファイルシステムを丸ごとマウントした新コンテナを起動する
  • 特権コンテナを立ち上げる

といったことができてしまい、実質的に ほぼ root 相当の権限を持つことになる。つまり「コンテナで隔離しているつもり」が崩れる。

このため docker.sock のマウントは、自分で管理している信頼できるコンテナに限るべきで、外部から持ち込んだイメージや、信頼度の低いコンテナには絶対に渡さない。

補足: コンテナ内の hostname はホストの識別に使えない

コンテナの中で socket.gethostname() を呼ぶと、ホスト名ではなく Container ID（コンテナ起動時に割り振られるランダムな ID）が返ってくる。

import socket
print(socket.gethostname())  # -> 例: 3f7a1c9b2e04 (Container ID)

そのため、「どのホスト上で動いているか」「どの役割のコンテナか」といった意味のあるラベルを hostname から得ようとしても、うまくいかない。ログに識別子を残したい、環境ごとに分岐したい、といった場合は、意味のあるラベルは環境変数で注入するのが定石だ。

docker run -e HOST_ROLE=batch-node -e ENV_NAME=prod myimage

選択軸

3系統のどれを選ぶかは、次のような軸で判断するとよい。

軸内容傾向
疎結合さ相手の内部実装にどれだけ依存するかネットワーク経由がもっとも疎、マウント経由が密
権限の強さ与えてしまう権限の大きさdocker.sock は強すぎる（ほぼ root）。安易に選ばない
レイテンシ呼び出しにかかる時間ネットワーク越しは遅くなりうる、ローカル実行は速い
対話性応答をやり取りしながら進めたいかSSH や HTTP は対話的、メッセージキューは投げっぱなし（非同期）向き

たとえば「相手が別ホストでもよく、疎結合にしたい」ならネットワーク経由、「重い依存だけ切り出したい」なら docker.sock 経由、というように軸に照らして選ぶ。特に権限の軸は見落としやすいので、docker.sock を選ぶときは「本当にこの強さが必要か」を必ず問い直す。

まとめ

  • コンテナ内から外の処理を呼ぶ手段は、ネットワーク経由 / docker.sock 経由 / マウント経由の3系統に整理できる。SSH はネットワーク経由の一実装にすぎない。
  • 迷ったら「まずどの系統か」を選び、その中で実装を選ぶ、という順で考えると反射的な選択を避けられる。
  • docker.sock のマウントはほぼ root 相当の権限を渡すことになるため、信頼できるコンテナに限る。
  • コンテナ内の socket.gethostname() は Container ID を返す。意味のあるラベルは環境変数で注入する。
  • 選択は「疎結合さ・権限・レイテンシ・対話性」の軸で判断する。とくに権限の軸を忘れない。
