Playwright自動化スクレイピング

Playwright ブラウザ自動化 — codegen の限界・壊れにくいセレクタ・iframe・ダウンロード

背景

社内の Web 画面や外部サイトに対して、「毎回同じ画面を開いて条件を入力し、ボタンを押してファイルをダウンロードする」といった定型操作を自動化したい場面は多い。API が提供されていない古い業務システムや、ログインの先にしか目的のデータがない外部サイトが相手だと、結局ブラウザをそのまま操作するしかない。

Playwright はこうした「ブラウザを人間の代わりに動かす」ための自動化ツールで、Python から利用できる。ここでは実際に自動化を組んでみて分かった、codegen（操作記録）の使い方と限界、壊れにくいセレクタの書き方、iframe やダウンロードの扱い、そして実行環境（画面の有無・タイムアウト）の勘所をまとめる。

codegen で雛形を作る — ただし「最終状態」しか残らない

Playwright には、人間がブラウザで行った操作を記録して Python コードに書き起こす codegen 機能がある。

playwright codegen --target python -o out.py https://example.com

このコマンドを実行するとブラウザが立ち上がり、こちらがクリックや入力をするたびに、対応するコードが out.py に追記されていく。ゼロからセレクタを調べて書くより圧倒的に速い、自動化の出発点として非常に便利な機能だ。

ただし、codegen には理解しておくべき重要な限界が二つある。

1. 記録されるのは「操作の最終状態」だけ

codegen は「その操作の結果、最終的にどの要素がどうなったか」を記録するのであって、こちらの意図までは記録できない。

例えば設定画面で「列を新しく追加した」「既存の列を編集した」「列を削除した」という 3 つの異なる操作をしても、最終的に同じセルをクリックして値を入れる形になっていれば、コード上はどれも同じ click + fill として記録されてしまう。後からコードだけを見ても、元がどういう意図の操作だったのかは区別できない。

つまり codegen が吐いたコードは「そのとき画面がその状態だったから、たまたまこの手順で通った操作列」に過ぎない。手順の意味を理解した上で、必要ならこちらで組み直す前提で扱う。

2. 値がベタ書き（固定値）になる

入力した値はそのまま固定値として記録される。

# codegen が吐いたそのままのコード
page.get_by_role("textbox", name="対象年月").fill("202504")

"202504" のような具体的な値がハードコードされているので、これをそのまま定期実行すると毎回同じ年月を入力してしまう。録画で雛形を得たら、固定値を引数や変数に置き換える（引数化・変数化）のが必須の後工程になる。

def run(target_ym: str):
    page.get_by_role("textbox", name="対象年月").fill(target_ym)

セレクタの脆さと堅牢化

自動化が「昨日は動いたのに今日は要素が見つからない」で壊れる原因の大半はセレクタにある。壊れやすいパターンを知っておくと事故を減らせる。

壊れやすいセレクタ

(a) 状態依存のクラスを含むもの。 特に厄介なのが、マウスホバー中にしか付与されないクラスだ。

# ホバー中だけ付く x-tree-node-over を当てにしている → 実行時は掴めない
page.locator(".x-tree-node.x-tree-node-over").click()

codegen で記録した瞬間はマウスがその要素の上にあったのでクラスが付いていたが、自動実行時にはホバーしていないためクラスが存在せず、要素が見つからない。ホバー・フォーカス・選択中といった一時的な状態に依存するクラスは避ける。

(b) 値依存のもの。 表示されている値そのものを名前にしていると、値が変われば壊れる。

# セルの中身 "202504" を頼りにしている → 翌月には存在しない
page.get_by_role("cell", name="202504").click()

壊れにくくする書き方

要素そのものの見た目や値ではなく、変わらない構造や安定したラベルを起点に相対的に辿るのがコツ。

ラベル行を起点に絞り込み、位置で指定する:

# 「対象年月」という見出しを含む行に絞り、その中の n 番目の入力欄を掴む
row = page.locator("tr").filter(has_text="対象年月")
row.get_by_role("textbox").nth(0).fill(target_ym)

安定した名前でロール指定する（値ではなくラベル名を使う）:

page.get_by_role("button", name="ダウンロード").click()

構造で辿る（ラベルのセルを起点に、祖先の行までさかのぼって同じ行の入力欄へ）:

# ラベルセル → 親の行(ancestor) → その中の入力欄、という相対経路
page.locator(
    "//td[text()='対象年月']/ancestor::tr[1]//input"
).fill(target_ym)

いずれも「値が変わっても構造は変わらない」ことを利用している。値そのものを名前にしない、というのが共通の原則だ。

iframe の中の要素

ページの中に別ページを埋め込む iframe がある場合、その中の要素は通常のセレクタでは掴めない。page から直接 locator しても、iframe の内側までは届かないためだ。

一度 iframe をロケータとして取得し、その中に入ってから要素を探す。

# frame_locator で iframe に入り、その内側の要素を掴む
frame = page.frame_locator("iframe#report")
frame.get_by_role("button", name="実行").click()

要素ハンドルから中身のフレームへ入る content_frame を使う書き方もある。

handle = page.query_selector("iframe#report")
frame = handle.content_frame
frame.get_by_role("button", name="実行").click()

「セレクタは合っているはずなのに要素が見つからない」というとき、対象が iframe の中にいないか（別ページが埋め込まれていないか）を疑うとよい。

ダウンロードの受け取り方

ボタンを押すとファイルがダウンロードされる、という操作は専用の待ち受けで扱う。「押したら落ちてくる」ものなので、先にダウンロードの発生を待ち受けてから操作する、という順序が重要になる。

with page.expect_download() as di:
    page.get_by_role("button", name="ダウンロード").click()

download = di.value
download.save_as("C:/tmp/report.xlsx")

with page.expect_download() as di: のブロックの中でダウンロードを引き起こす操作（クリック）を行い、ブロックを抜けたところで di.value からダウンロードオブジェクトを受け取る。あとは save_as(path) で任意の場所に保存する。ダウンロード先は一時領域に落ちるので、save_as で明示的に保存しないと後で参照できない点に注意。

headless とディスプレイの有無

ブラウザを起動するとき、画面を表示するかどうかを選べる。

browser = playwright.chromium.launch(headless=False)  # 実ブラウザ画面を出す
browser = playwright.chromium.launch(headless=True)   # 画面なしで動かす

headless=False は実際のブラウザウィンドウを画面に出して動かすモードで、動作を目で確認したいときに便利だ。ただしこれはディスプレイ（描画先の画面）がある端末でしか動かせない。画面を持たないサーバや、GUI のないヘッドレス環境で headless=False を指定すると、描画先がなく起動に失敗する。

サーバ上で定期実行させる自動化は headless=True で組むのが基本。開発中はローカルの画面付き端末で headless=False にして動きを確認し、本番では headless に切り替える、という使い分けになる。

タイムアウトと明示的な待機

page.goto のナビゲーションには既定で 30 秒のタイムアウトが設定されている。1 回の遷移が 30 秒で切れるという意味だ。

ここで見落としやすいのが、リダイレクトが多発するサイトだ。ログインを挟むと「トップ → 認証 → リダイレクト → 目的ページ」のように内部で何度も遷移が発生することがあり、それぞれで遷移待ちが積み重なると、体感で数分待たされることがある。「なぜか異常に遅い」ときは、裏で遷移が連鎖していないかを疑う。

また、ページ表示後に JavaScript で内容が描画される動的なコンテンツは、goto が完了した時点ではまだ要素が存在しないことがある。固定の sleep で待つのではなく、目的の要素が現れるのを明示的に待つのが確実だ。

# 要素が出現するまで待ってから操作する
page.wait_for_selector("#result-table")
page.locator("#result-table").click()

wait_for_selector は指定した要素が現れるまで待ってくれるので、描画のタイミングに左右されず安定する。適切なタイムアウトを渡しておけば、想定より遅いときにいつまでもぶら下がることも防げる。

まとめ

  • codegen（playwright codegen --target python -o out.py）は雛形作りに便利だが、操作の最終状態しか記録しないため意図は区別できず、固定値もベタ書きになる。録画後の引数化・組み直しが前提。
  • 壊れやすいセレクタは「ホバー時だけ付くクラス」や「値そのものを名前にしたもの」。安定したラベル・ロール・構造を起点に相対的に辿ることで堅牢になる。
  • iframe の中の要素は frame_locator / content_frame を経由しないと掴めない。「合っているのに見つからない」ときは iframe を疑う。
  • ダウンロードは with page.expect_download() as di: で先に待ち受けてから操作し、di.value.save_as(path) で保存する。
  • headless=False はディスプレイのある端末専用。サーバ実行は headless=True が基本。
  • goto の既定タイムアウトは 30 秒。リダイレクト連鎖で総時間が膨らむことがあり、動的コンテンツは wait_for_selector 等で明示的に待つ。
