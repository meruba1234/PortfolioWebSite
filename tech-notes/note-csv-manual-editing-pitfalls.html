プログラミング

CSV を手動で編集するときの落とし穴（詳細版）

背景

業務では「基幹システムが出力した CSV を、取り込み前に少しだけ直す」「分割して届いた CSV を1つにまとめる」といった作業が頻繁に発生する。件数が数十行なら手作業でもできてしまうため、つい Excel やメモ帳で開いて直したくなる。

ところがこの作業は、壊れたことに気づかないまま次工程に流れるという性質の事故を起こしやすい。見た目は正しいのに取込先で弾かれる、あるいは弾かれずに間違った値が登録される、という形で表面化する。

このノートは、CSV を人の手で触るときに何が起きるのか、どうすれば安全かを整理する。要点は次の3つ。

  • CSV は「型のないテキスト」であり、開くアプリが勝手に型を推測する
  • 壊れ方には「値が変わる」「文字コードが変わる」「列がずれる」の3系統がある
  • 手作業そのものより、作業後の検証を省くことが事故の原因

具体的な社名・案件は伏せ、一般的な例（「取引先の発注データ CSV」など）で説明する。

1. CSV というフォーマットの正体

CSV は「カンマ区切りのテキスト」というだけの、非常に緩い取り決めしかない形式である。一応 RFC 4180 という文書はあるが、業務で流通する CSV がそれに従っている保証はどこにもない。

CSV 自体が持っていない情報を並べるとこうなる。

CSV が持っていないもの結果として起きること
列の型（文字列 / 数値 / 日付）開くアプリが勝手に推測する。00123 を数値と見なせばゼロが消える
文字コードの宣言開くアプリが推測する。外すと文字化け
区切り文字の宣言カンマ以外（タブ、セミコロン）のこともある
見出し行の有無1行目がデータなのか見出しなのか、ファイルからは判断できない

つまり CSV ファイル単体は「正解」を知らない。正解を知っているのは、それを出力したシステムと、取り込む側のシステムだけである。手で編集するというのは、その2つの合意の間に人間が割り込む行為になる。

押さえておくべき記法ルール

要素ルール
区切りカンマ。全行で同じ個数でなければ列がずれる
引用符値にカンマ・改行・引用符を含むときは " で囲む
引用符のエスケープ値の中の " は "" と2つ重ねる
フィールド内改行" で囲まれていれば値の中に改行を含められる（1レコード = 1行とは限らない）
空値,, は空文字。NULL という文字列とは別物

フィールド内改行は特に厄介で、「行数 = レコード数」という前提を壊す。テキストエディタで見た行数と、システムが読むレコード数が食い違う原因になる。

2. Excel が CSV を壊す仕組み

CSV を Excel でダブルクリックして開くと、Excel は各セルの中身を見て型を推論する。この推論が業務データと絶望的に相性が悪い。

元の値Excel の解釈保存後
00123数値 123123（先頭ゼロ消失）
1-2 3-5日付2001/1/2（日付に変換）
2026/07/31日付表示形式次第で 2026/7/31 などに揺れる
1234567890123456（16桁）数値1.23457E+15 かつ 16桁目以降が 0 に丸められる
0.50数値 0.50.5（末尾ゼロ消失）
=SUM(A1) +81... -abc数式数式として評価／エラー表示（CSV インジェクションの温床）
TRUE FALSE論理値大文字化・表示変化
１２３（全角）環境により半角化表記揺れ

さらに保存時には、

  • 文字コードが変わる（Shift_JIS → UTF-8、またはその逆）
  • 引用符の付き方が変わる（不要な " が付く／必要な " が消える）
  • 空行・末尾改行の扱いが変わる
  • 数値の桁区切り , が値の中に入り込み、列がずれる

とりわけ16桁の丸めは復旧不能な壊れ方をする。IEEE 754 倍精度浮動小数点数の有効桁が10進で約15〜17桁しかないため、16桁以上の数値 ID（バーコード、GTIN、伝票の内部ID）は下位桁が 0 になって元の値が失われる。ゼロ落ちや日付化は「見れば気づく」が、これは気づきにくい。

「開くだけ」なら安全か

保存しなければファイルは変わらない。しかし、

  • 何かの拍子に上書き保存してしまう
  • 「変更を保存しますか」に反射的に「はい」を押す
  • 開いたまま別作業をして、閉じるときに保存する

という事故が現実には起きる。「見るだけだから」は安全側の判断ではない。

どうしても Excel で確認したいとき

値を保持したまま Excel で見る方法はある。

  1. 空の Excel を先に開く → 「データ」タブ → 「テキストまたは CSV から」
  2. ファイルを選び、文字コードを明示（日本語 (シフト JIS) など）
  3. 「データの変換」→ 全列を選択 → データ型を「テキスト」に指定
  4. 読み込む

これなら型推論が働かない。ただしこの状態から CSV として保存し直さないこと。確認用と割り切り、加工が必要なら xlsx として別名保存する。

3. テキストエディタ（メモ帳）の注意点

値を書き換えない点で、テキストエディタは Excel より圧倒的に安全である。ただし別種の罠がある。

① 文字コードの変換 メモ帳は開くときに文字コードを自動判定し、保存時にその判定結果で書き戻す。判定を外すと、保存した瞬間に別のコードに変換される。Windows のメモ帳はウィンドウ右下に現在の文字コードを表示するので、開いた直後と保存後で同じかを必ず見る。

② BOM の付与 UTF-8 で保存するとき、アプリによっては先頭に BOM（EF BB BF の3バイト）を付ける。BOM 付き UTF-8 を読む側が対応していないと、1列目の見出し名の先頭に見えないゴミが付く（ID が ﻿ID になり、列名の一致判定に失敗する）。原因が見えないので厄介。

③ 末尾改行 最終行の後ろに改行があるかないかで、読み手によっては空レコードが1件増える／2ファイル結合時に行がくっつく、といった差が出る。

④ 巨大ファイル 数十 MB を超えるとメモ帳は実用的でなくなる。VSCode やサクラエディタを使う。

⑤ 目視では列のズレを検出できない これが最大の弱点。53列のデータを目で見て「全行53列ある」ことは確認できない。検証は機械にやらせるしかない。

4. 文字コードと改行コード

日本の業務システムが出す CSV は、実質 CP932（拡張 Shift_JIS） であることが非常に多い。詳細は CP932 と Shift_JIS の違い と 改行コード（CRLF / LF） を参照。

CSV を触るときに関係する要点だけ再掲する。

項目Windows 業務システムの典型外すとどうなるか
文字コードCP932（メモ帳の表示は ANSI）全体が文字化け。取込エラー
改行コードCRLFLF に変わると取込側が1行として読む場合がある
BOMなし付くと1列目の列名が一致しなくなる

Python で読むなら shift_jis ではなく cp932 を指定する（丸数字・全角空白などの拡張文字で例外にならない）。

5. 手動編集の安全手順

手順

1. 原本をコピーして、コピーを編集する（原本は絶対に触らない）
2. テキストエディタで開く（Excel では開かない）
3. 文字コード表示を確認・記録する
4. 編集する
5. 同じ文字コードで保存する
6. 機械で検証する（次章）
7. 検証が通ってから次工程へ渡す

原本を残すことがすべての前提になる。CSV の事故は後から気づくものなので、やり直せる状態を作ってから作業する。

ファイル名の付け方

発注データ_20260731.csv              ← 原本
発注データ_20260731_編集用.csv        ← 作業ファイル
発注データ_20260731_結合.csv          ← 成果物

原本を _orig に改名して成果物を元の名前にする運用は、どれが原本か分からなくなるので避ける。

6. 結合・分割の正しいやり方

結合（2つの CSV を縦につなげる）

必要な操作は「1つ目の全行 + 2つ目の2行目以降」を、文字コードと改行を保ったまま連結すること。

PowerShell（推奨・1行で済む）

$enc = [Text.Encoding]::GetEncoding(932)          # CP932 を維持
$a = [IO.File]::ReadAllLines('A.csv', $enc)
$b = [IO.File]::ReadAllLines('B.csv', $enc)
[IO.File]::WriteAllLines('結合.csv', $a + ($b | Select-Object -Skip 1), $enc)
  • GetEncoding(932) で文字コードを固定（Get-Content/Set-Content の既定エンコーディングに任せない）
  • -Skip 1 で2つ目の見出し行を落とす
  • WriteAllLines の改行は Windows では CRLF
  • 制約: 引用符で囲まれたフィールド内改行があるファイルでは行の解釈がずれる

Python（検証まで一緒にやるなら）

import csv

def read(path):
    with open(path, newline="", encoding="cp932") as f:
        return list(csv.reader(f))

a, b = read("A.csv"), read("B.csv")

assert a[0] == b[0], "見出し行が一致しない"
ncol = len(a[0])
assert all(len(r) == ncol for r in a + b), "列数が揃っていない"

with open("結合.csv", "w", newline="", encoding="cp932") as f:
    w = csv.writer(f, lineterminator="\r\n")
    w.writerow(a[0])
    w.writerows(a[1:])
    w.writerows(b[1:])

csv モジュールを通すと、引用符・フィールド内改行を正しく扱える代わりに、引用符の付き方が原本と変わる可能性がある（QUOTE_MINIMAL は不要な引用符を落とす）。原本とバイト単位で一致させたい場合は、書き出し後に「出力ファイルの先頭 N バイトが1つ目のファイルと完全一致するか」を確認する。

避けたほうがよい方法

方法問題
copy /b A.csv + B.csv 結合.csv2つ目の見出し行がそのまま混入する。手で消す手間が残る
メモ帳でコピー＆ペースト文字コード変換・見出し重複・行の結合事故のリスク。検証もできない
Excel で開いて下に貼り付け値が壊れる。最悪の選択

分割

条件で絞って別ファイルにする作業は、分割の軸（キー）を明示することが重要。「納品日が 8/3 のもの」なのか「単価改定対象の商品」なのかで結果が変わる。分割済みファイルを受け取ったときは、次章の方法で軸を逆算して確認するとよい。

7. 検証 — 手作業の後に必ずやること

手作業そのものより、検証を省くことが事故の原因になる。最低限これだけは機械にやらせる。

import csv, collections

path = "結合.csv"
with open(path, newline="", encoding="cp932") as f:
    rows = list(csv.reader(f))

print("行数:", len(rows))                                        # 期待値と一致するか
print("列数の分布:", collections.Counter(len(r) for r in rows))   # 1種類だけであること
print("見出し:", rows[0][:5])

# 完全重複行
dup = len(rows[1:]) - len(set(map(tuple, rows[1:])))
print("完全重複行:", dup)

# キー項目の重複（例: 3列目が伝票No）
keys = [r[2] for r in rows[1:]]
print("キー重複:", [k for k, c in collections.Counter(keys).items() if c > 1])

チェック項目のまとめ:

観点見るもの合格条件
件数行数A + B − 1（結合の場合）
列ズレ列数の分布1種類だけ
見出し1行目元と同一。データ中に見出しが混ざっていない
重複完全重複行・キー重複想定どおり（通常0件）
文字コードバイト列原本と同じコードでデコードできる
改行末尾バイトCRLF（原本に合わせる）
内容先頭 N バイト原本と一致（バイト連結の場合）

分割されたファイルの軸を逆算する

「なぜ2つに分かれているのか」を確認したいときは、列ごとに値の分布を比べると一発でわかる。

import csv, collections

def load(p):
    with open(p, newline="", encoding="cp932") as f:
        return list(csv.reader(f))

a, b = load("A.csv"), load("B.csv")
header = a[0]

for i in range(len(header)):
    va = collections.Counter(r[i] for r in a[1:])
    vb = collections.Counter(r[i] for r in b[1:])
    if set(va) != set(vb):                      # 値の集合が違う列＝分割の軸候補
        print(i, header[i], "| A:", dict(va), "| B:", dict(vb))

「単価改定のために分けた」と聞いていても、実際の軸は納品日だった、というような食い違いはよくある。聞いた話ではなくデータで確認する。

8. やってはいけないことチェックリスト

  • CSV をダブルクリックで Excel に開く（関連付けを変えておくのが理想）
  • 原本を直接編集する
  • 保存時の文字コードを確認しない
  • 2つ目のファイルの見出し行を消さずに結合する
  • 値の中にカンマや改行を手入力する
  • 目視だけで「大丈夫そう」と判断して次工程へ渡す
  • 桁数の多い ID を数値として扱う
  • 取込先のシステムでエラーが出たとき、エラーを消すためにデータを書き換える（原因が別にあることが多い）

まとめ

  • CSV は型・文字コード・区切りのいずれも自己申告しない、非常に緩いテキスト形式である
  • Excel は開いた瞬間に型を推論し、保存した瞬間に値と文字コードを書き換える。16桁の丸めは復旧できない
  • テキストエディタは値を壊さないが、文字コード変換・BOM・列ズレ未検出という別の穴がある
  • 原本を残す → コピーを編集 → 機械で検証 の3ステップを崩さない
  • 結合は PowerShell の GetEncoding(932) + -Skip 1、または Python の csv モジュールで行う
  • 検証で見るのは「行数・列数の分布・見出し・重複・文字コード・改行」の6点
