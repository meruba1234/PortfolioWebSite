アトミックなファイル書き込み（.tmp に書いて rename）

背景

あるファイルを、書き手のプロセスとは別のプロセスが定期的に読んでいる、という構成はよくある。たとえば片方が状態ファイル（state.json など）を更新し、もう片方がそれをポーリングして表示する、といったケースだ。

このとき、書き手が 本番のファイルを直接開いて上書き すると困ったことが起きる。書き込みは一瞬では終わらない。途中まで書いたところで読み手がファイルを開くと、「前半だけ新しく、後半は古い（あるいは空）」という 中途半端な内容 を掴んでしまう。 JSON なら途中で切れた壊れたテキストになり、パースエラーになる。

この破損を避けるための定石が「一時ファイルに書き切ってから rename する」という手法だ。

なぜ直接書くと危険か

直接上書きが危険なのは、書き込みが「複数の細かい操作の集まり」だからだ。ファイルを truncate（空にする）してから、少しずつバイトを書いていく。この途中の一瞬でも、読み手は同じファイルを開ける。

# 危険な例：本番ファイルを直接書き換える
with open("state.json", "w", encoding="utf-8") as f:
    json.dump(data, f)   # この最中に別プロセスが読むと壊れた内容を掴む

読み手から見ると、ファイルの中身が「完全な状態」から「完全な状態」へ一瞬で切り替わってほしい。ところが直接書きだと、その間に「壊れた状態」という第三の状態が挟まってしまう。

.tmp に書いて rename する

そこで、次の順番にする。

  1. 本番ファイルとは別名の一時ファイル（.tmp）に、内容を 最後まで書き切る
  2. 書き終わってから、一時ファイルを本番名に rename（改名） する
import os, json

def atomic_write_json(path, data):
    tmp = path + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False)
    os.replace(tmp, path)   # ここが原子的な切り替え

ポイントは rename が 原子的（atomic） な操作だということ。同一ボリューム（同じファイルシステム）内の rename は、OS が「一瞬で名前を差し替える」操作として扱う。途中経過がない。だから読み手は、

  • rename 前 → 「古い完全な内容」
  • rename 後 → 「新しい完全な内容」

のどちらかしか見ない。壊れた中間状態は原理的に観測できない。

os.replace と os.rename の違い

Python で上書きを含む rename をするなら os.replace(src, dst) を使う。これは宛先が既存でも上書きし、Windows / POSIX の両方で原子的に動く。

os.rename は少し挙動が違い、Windows では宛先が既に存在すると失敗する（POSIX では上書きできる）。プラットフォームで挙動が割れるので、上書き前提なら os.replace を選ぶのが安全だ。

os.replace(tmp, path)   # 上書きOK・両OSで原子的 → こちらを使う
os.rename(tmp, path)    # Windowsだと既存宛先で失敗する

一時ファイルは「宛先と同じディレクトリ」に作る

原子的なのは 同一ファイルシステム内の rename に限る という点に注意する。別のドライブや別のマウント（別ファイルシステム）へ移動しようとすると、 OS は内部で「コピーしてから元を削除」に切り替える。これはもう原子的ではなく、途中経過が見える。

だから一時ファイルは、/tmp のような別の場所ではなく、 本番ファイルと同じディレクトリ に作るのが鉄則だ。同じディレクトリなら同一ファイルシステムであることが保証されやすい。

tmp = path + ".tmp"          # 宛先と同じフォルダに作る（推奨）
# tmp = "/tmp/state.json.tmp"  # 別FSだと rename が非原子的になりうる

電源断まで守るなら fsync

rename が原子的でも、それは「OS から見た論理的な切り替え」の話だ。書いた内容がまだ OS のキャッシュに乗っているだけで、物理ディスクに届いていない可能性はある。電源断やクラッシュまで耐えたいなら、rename の前にディスクへ書き切らせる。

with open(tmp, "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False)
    f.flush()          # Python内部バッファ → OSへ
    os.fsync(f.fileno())   # OSキャッシュ → 物理ディスクへ
os.replace(tmp, path)

flush() はアプリのバッファを OS に渡すだけで、まだディスクには届いていない。 os.fsync() を呼んで初めて、ディスクまで書き切ったことが保証される。

「成功してから記録する」順序にする

もう一つ、破損に強くする設計上のコツがある。処理の順番を 「保存が成功してから、処理済みを記録する」 にすることだ。

たとえば「データを保存する → 処理済みリストに印をつける」という順にしておくと、保存の途中で落ちても、まだ処理済みの印はついていない。次回の実行で「まだ処理していない」とみなされ、もう一度救済される。

逆に「先に処理済みと記録 → 後で保存」だと、保存前に落ちたときに「処理済みなのに実体がない」という穴が空く。リトライで拾えなくなる。

まとめ

  • 別プロセスが読むかもしれない共有ファイルは、直接上書きしない。書き込み途中の壊れた内容を読まれる。
  • .tmp に書き切ってから rename すれば、読み手は「古い完全」か「新しい完全」のどちらかしか見ない。
  • Python では上書きも原子的な os.replace を使う。os.rename は Windows で既存宛先だと失敗する。
  • 一時ファイルは 宛先と同じディレクトリ に作る。別ファイルシステムへの move は原子的でない。
  • 電源断まで守るなら rename 前に flush() + os.fsync()。
  • 「保存成功 → 処理済み記録」の順序 にすると、途中で失敗しても次回リトライで救える。
