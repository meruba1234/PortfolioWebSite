バッチ設計ETL運用設計

バッチ / ETL の安全設計 — 中間ファイル退避・洗い替え・多重起動防止

背景

毎日決まった時刻に自動で動くバッチ（受信ファイルを取り込んで DB やレポートを更新する ETL）を作るとき、いちばん怖いのは「途中で失敗したときに元データが壊れる」「何が起きたか後から追えない」「スケジューラが二重に発火して同じ処理が重なる」という 3 つの事故だ。

処理そのものが正しく書けていても、こういう 運用時の事故 はコードのロジックとは別の層で起きる。ここでは、失敗しても壊れず・追跡でき・多重起動しないバッチにするための定番パターンをまとめる。ポイントは「原本を守る」「状態をフォルダで表す」「冪等にする」「重複と暴走を止める」の 4 つ。

原本は絶対に直接書き換えない

入力として届いたファイル（受信原本）を、その場で開いて書き換えたり、変換結果で上書きしたりしてはいけない。処理の途中で例外が飛んだ瞬間、原本が中途半端な状態で壊れて、しかも「元々何が届いていたか」も分からなくなる。

対策はシンプルで、処理は必ずコピーに対して行う。

受信原本  ─┬─→ backup/2026-07-09/order_0930.csv   (永久保管・読み取り専用)
           └─→ processing/order_0930.csv           (ここを加工する)
  • backup/ … 届いたそのままを日付フォルダで永久保管する。後から「元は何が来ていたか」を必ず追えるようにするための証拠。ここには二度と書き込まない。
  • processing/ … 実際の変換・整形はこのコピーだけをいじる。途中で落ちても壊れるのはコピーだけなので、原本破壊はゼロになる。

「原本 = 触らない証拠」「コピー = 作業場」と役割を分けるのが肝。原本が無事なら、失敗しても何度でもやり直せる。

段階をフォルダの遷移で表す

処理がどこまで進んだかを、フラグ変数やメモではなく ファイルの置き場所 で表現すると、状態がひと目で分かり復旧もしやすい。

pending/     … これから処理する待ち行列（トリガー）
   │  取り込み開始
   ▼
processing/  … いま処理中
   │  成功 ─────────────→ done/        … 完了
   │  失敗 ─────────────→ failed/2026-07-09/ … 失敗（日付付きで隔離）

ここで 移動と記録の「順序」を設計する ことが重要になる。順序を間違えると、失敗時にトリガーファイルだけ消えて「処理された形跡はないのに待ち行列からも消えた」という不整合が起きる。

たとえば悪い順序と良い順序:

# 悪い例: 先に pending から消してしまう
os.remove(pending_file)      # ← ここで消す
do_heavy_work()              # ← ここで落ちると、待ち行列にもどこにも残らない = 消失

# 良い例: 成功を見届けてから最後に状態を進める
shutil.copy(pending_file, processing_file)  # まずコピー（原本相当は残す）
do_heavy_work(processing_file)              # 加工はコピーに対して
shutil.move(processing_file, done_file)     # 成功して初めて done へ
os.remove(pending_file)                     # 最後にトリガーを消す

原則は「確定してから状態を進める / 消す」。移動（状態遷移）と記録（ログ・DB 反映）のどちらを先にするかを毎回意識し、途中で落ちても必ずどこかのフォルダに証拠が残るようにする。失敗は failed/日付/ に隔離しておけば、後から中身を見て原因調査ができる。

洗い替え（対象期間だけ全消し・全入れ）

集計結果や取り込み済みレコードを更新する方式として、対象ウィンドウ（期間）内のレコードだけをいったん全削除して、作り直す やり方がある。これを洗い替えと呼ぶ。

今日の実行: 対象 = 直近 3 日分
  DELETE  WHERE 日付 BETWEEN 07/07 AND 07/09   ← ウィンドウ内を消して
  INSERT  最新の 07/07〜07/09 を作り直す        ← 入れ直す

利点は 冪等性 だ。同じ実行を何回流しても結果が同じになるので、単発の失敗を気にせず「次回の実行がまた取り直す」で自然に回復できる。差分だけ追記する方式のように「二重登録された」「1 回スキップされた」を悩まなくてよい。

ただし落とし穴がある。削除するのはあくまでウィンドウ「内」だけ なので、ウィンドウの外に出た古い結果が消えずに残り続ける。

ウィンドウを 07/07〜07/09 に狭めた後…
  07/03 の古いレコードは DELETE の条件に入らない → 残ったまま
  → UI やレポートに「もう更新されない古い数字」が見え続ける事故

対策としては、(1) 定期的にウィンドウ全体を広げてフル洗い替えする回を混ぜる、(2) ウィンドウ外の古いレコードを別途パージする掃除処理を入れる、(3) 表示側で「対象期間外は出さない」とフィルタする、といった手を組み合わせる。「消し忘れゾーン」が必ず生まれる ことを設計時に意識しておくのが大事。

多重起動防止（ロックファイル）

スケジューラの多重発火や、前回の実行が長引いて次の実行と重なると、同じ入力を二重に処理してしまう。これを防ぐには ロックファイル を使う。

起動時:
  ロックを取れた？
    ├─ はい → ロックファイルを作成して処理続行
    └─ いいえ（既に誰かが持っている） → 専用の終了コードで即 exit
終了時（成功でも失敗でも）:
  ロックファイルを必ず削除する
  • ロックの取得は「作成できたら勝ち」という原子的な操作にする（すでに在れば失敗する形で作る）。
  • 取れなかったら普通のエラーではなく 専用の終了コード（例: 75 = 一時的に実行できない、など決め打ち）で抜ける。監視側が「これは二重起動でスキップしただけ」と「本当の失敗」を区別できるようにするため。
  • 終了時のロック解放は try / finally に入れて、途中で落ちても必ず消えるようにする（消し忘れると次回以降ずっと起動できなくなる＝デッドロック）。古いロックを時刻で無効化する仕組みを足すとさらに安全。

暴走防止（タイムアウトの二重ガード）

外部コマンドや子プロセスを呼ぶバッチは、相手がハングすると自分も永遠に終わらない。実行側と監視側の両方にタイムアウト を仕込む二重ガードにする。

呼び出し側（実行）:
  subprocess.run([...], timeout=600)   # 子プロセスを 10 分で強制打ち切り
     → TimeoutExpired を捕まえて failed 扱いにする

監視側（オーケストレータ / スケジューラ）:
  この処理全体にも別枠のタイムアウトを設定
     → 実行側のガードをすり抜けても、外側で丸ごと止める

内側（子プロセス単位）だけだと、親のロジックが別の場所で固まったときに止められない。逆に外側だけだと粒度が粗く、どこで詰まったか分かりにくい。内側で細かく打ち切り、外側で最後の砦として全体を止める と、どんな詰まり方でも必ず有限時間で終わる。

まとめ

  • 原本を直接書き換えない: 加工は processing/ のコピーに対して行い、受信原本は backup/日付/ に永久保管する。落ちても壊れるのはコピーだけ、元は必ず追える。
  • 状態はフォルダ遷移で表す: pending → processing → done（失敗は failed/日付/）。移動と記録の 順序 を設計し、「確定してから進める / 消す」を徹底して消失を防ぐ。
  • 洗い替えは冪等で扱いやすいが消し忘れゾーンに注意: ウィンドウ内だけ全消し全入れは回復が楽。一方でウィンドウ外の古い結果が残るので、フル洗い替え / パージ / 表示フィルタで補う。
  • 多重起動はロックファイルで防ぐ: 取れなければ専用終了コードで即 exit、解放は finally で確実に。
  • 暴走はタイムアウトの二重ガードで止める: 子プロセスは subprocess.run(timeout=...)、監視側にも別枠のタイムアウト。内側で細かく、外側で最後の砦。

ロジックが正しいだけでは安全なバッチにはならない。「失敗しても壊れない・追える・重ならない・止まる」を 運用の器（フォルダ構造・ロック・タイムアウト） の側で担保するのが、毎日安心して回るバッチ設計の勘所。
