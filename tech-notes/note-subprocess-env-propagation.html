プログラミング

subprocess と環境変数の伝播 — env を明示指定すると親を継がない

背景

Python から別のプログラム（子プロセス）を起動して処理を任せる場面はよくある。そのとき「親プロセスが持っている設定を、子プロセスにどう渡すか」という問題が出てくる。

一番移植性が高くて確実なのが 環境変数 を経由する方法だが、 subprocess.run(..., env=...) の書き方を一つ間違えると、子プロセス側で「あるはずの設定が空っぽ」になり、原因が分からず悩むことになる。

このノートは、その渡し方と落とし穴、そして「多段で渡ると途中で消える」問題を整理しておくもの。

環境変数とは（前提）

環境変数は、プロセスが持っている 「名前 = 値」の小さなメモ帳 のようなもの。プロセスを起動すると、親のメモ帳が 子にコピーされて引き継がれる（デフォルトの動作）。

これを使うと、コードを書き換えずに外から挙動を切り替えられる。たとえば PATH（実行ファイルの探索先）や PYTHONPATH（Python の import 探索先）も環境変数。

子プロセスに環境変数を渡す

Python では subprocess を使って子プロセスを起動する。子に渡したい設定を env= に辞書で指定し、子は os.environ.get(...) で受け取る。

親プロセス（呼び出す側）:

import subprocess

subprocess.run(
    ["python", "child.py"],
    env={"RUN_SOURCE": "manual"},   # 子に渡したい環境変数
)

子プロセス（child.py、呼ばれる側）:

import os

source = os.environ.get("RUN_SOURCE", "unknown")
print(source)   # → "manual"

親子は別プロセスなので、変数やオブジェクトを直接共有できない。環境変数は どの言語・どの OS でも通用する ので、プロセス間で「ちょっとした状態」を渡す最も移植性の高い手段になる。

落とし穴: env= を明示すると親を引き継がない

ここが最大の罠。

env= を 省略 すると、子は親の環境変数をまるごと引き継ぐ。しかし env= に辞書を 明示指定 すると、その辞書が 子の環境変数のすべて になる。つまり親が持っていた PATH や PYTHONPATH は 引き継がれず消える。

# NG: これだと子の環境変数は RUN_SOURCE だけ。PATH すら無い
subprocess.run(["python", "child.py"], env={"RUN_SOURCE": "manual"})

結果、子プロセスで python が見つからない、ModuleNotFoundError といった一見無関係なエラーが出て、原因が「環境変数を上書きしてしまったこと」だと気づきにくい。

正解は 親の環境をコピーしてから、必要な分だけ足す こと。

import os

# OK: 親の os.environ を展開してマージし、そこに追加・上書きする
subprocess.run(
    ["python", "child.py"],
    env={**os.environ, "RUN_SOURCE": "manual"},
)

{**os.environ, "RUN_SOURCE": "manual"} は「親の環境変数を全部コピーして、そのうえで RUN_SOURCE を追加（同名なら上書き）」という意味。

書き方子が受け取る環境変数
env= を省略親と同じ（全部引き継ぐ）
env={"FOO": "bar"}FOO だけ。PATH 等は消える
env={**os.environ, "FOO": "bar"}親の全部 + FOO（安全）

モード切替に使う（手動実行か定期実行か）

環境変数は「実行モードの伝播」に向いている。

たとえば、同じスクリプトを

  • 人が画面から手で起動したとき → RUN_SOURCE=manual
  • スケジューラが自動で起動したとき → RUN_SOURCE=scheduled

と起動経路ごとに違う値をセットしておけば、スクリプト側は os.environ.get("RUN_SOURCE") を見るだけで「今は手動なのか自動なのか」を判断して振る舞いを変えられる。

if os.environ.get("RUN_SOURCE") == "manual":
    # 手動実行のときだけ確認ダイアログや詳細ログを出す、など
    ...

ここで注意したいのは、起動経路が違うと渡ってくる環境変数も変わる ということ。「手動 UI から起動したときは動くのに、スケジューラ経由だと挙動が違う」という現象は、たいてい「経路ごとにセットされる環境変数が違う」ことが原因。コードは同じでも、入力（環境変数）が違えば結果は変わる。

多段で伝播すると途中で途切れる

環境変数は「親 → 子」でコピーされて伝わるが、 プロセスの連鎖が長くなると、どこか 1 段で途切れると末端に届かない。

ジョブ実行基盤（Prefect のようなワークフローツール）では、実行が次のように何段も受け渡される。

デプロイ定義（この環境変数を渡す、という設定）
  └→ run 生成（実行インスタンスを作る）
       └→ worker 起動（実際にプロセスを立てる）
            └→ subprocess（さらに子プロセスを起動）

このどこか 1 段で環境変数のマージを忘れたり、値を空で渡したりすると、 末端のスクリプトに届く頃には空っぽ になる。

しかも末端だけ見ていると「なぜか設定が来ていない」としか分からない。だから調査は 1 段ずつ「ここでは値が入っているか」を確認して、どの段で消えたかを特定する のが定石。

デプロイ定義  : RUN_SOURCE=manual  ← ここにはある
run          : RUN_SOURCE=manual  ← まだある
worker       : RUN_SOURCE=(空)    ← ★ここで消えた！ 犯人はこの段
subprocess   : RUN_SOURCE=(空)

上の例なら、worker がサブプロセスを起こすときに env= を上書きして親の環境を捨てている、といった原因に絞り込める。

まとめ

  • 子プロセスに設定を渡すなら 環境変数（subprocess の env= → 子は os.environ.get）。言語・OS を問わず使える最も移植性の高い手段。
  • env= を明示指定すると親の環境変数を引き継がない。PATH/PYTHONPATH まで消える。env={**os.environ, "FOO": "bar"} とマージするのが安全。
  • 「手動か定期実行か」などのモード切替も環境変数で渡せる。起動経路が違うと渡る環境変数も変わる ので、経路ごとの挙動差はまずここを疑う。
  • 環境変数は連鎖のどこか 1 段で途切れると末端に届かない。多段（デプロイ → run → worker → subprocess）で渡るときは、どの段で消えたかを 1 段ずつ確認する。
