プログラミング

xlsx/xlsm は ZIP+XML — openpyxl が画像や図形を落とす原理と回避

背景

Excel のテンプレートに会社ロゴやグラフ、注意書きの図形が貼ってある。そのテンプレートを Python の openpyxl でセルの数字だけ書き換えて保存したら、ロゴや図形がきれいさっぱり消えていた——これは openpyxl を使うとよく踏むトラブルだ。原因を理解するには、まず「xlsx とは何者なのか」を知る必要がある。結論を先に言うと、xlsx/xlsm は 1 枚のバイナリファイルではなく、複数の XML を束ねた ZIP アーカイブである。openpyxl は保存時にその中身を作り直すため、扱えないパーツを取りこぼす。以下、内部構造 → なぜ落ちるか → 回避策 → 読み込みオプションの順に整理する。

xlsx/xlsm の正体は ZIP アーカイブ

sample.xlsx の拡張子を sample.zip に変えて展開ソフトで開くと、中からフォルダ構造が出てくる。つまり Excel ブックの実体は、複数のファイルを ZIP 圧縮でまとめた「箱」だ。この形式は OOXML (Office Open XML) と呼ばれる。

展開すると、おおよそ次のような中身が見える。

sample.xlsx  (= ZIP)
├── [Content_Types].xml         各パーツの種類の宣言
├── _rels/
│   └── .rels                   最上位の参照関係
└── xl/
    ├── workbook.xml            ブック全体（シート一覧など）
    ├── sharedStrings.xml       文字列プール（後述）
    ├── styles.xml              フォント・色・罫線などの書式定義
    ├── worksheets/
    │   ├── sheet1.xml          シート1のセルデータ
    │   └── sheet2.xml
    ├── media/
    │   ├── image1.png          画像の本体（バイナリ）
    │   └── image2.jpeg
    ├── drawings/
    │   └── drawing1.xml        図形・画像を「どこに置くか」の配置情報
    └── worksheets/_rels/
        └── sheet1.xml.rels     シート1と drawing1.xml をつなぐ参照

役割を表にまとめる。

パーツ中身役割
xl/worksheets/sheetN.xml各シートのセル値・数式表そのもの
xl/media/png / jpeg などの画像バイナリ画像の本体データ
xl/drawings/配置座標・サイズの XML画像や図形を「どのセル位置にどの大きさで置くか」
xl/sharedStrings.xml文字列の一覧同じ文字列を使い回すためのプール
xl/styles.xmlフォント・色・罫線・表示形式見た目の定義
xl/_rels, *.relsパーツ同士の参照関係「このシートはこの drawing を使う」等の紐付け

ポイントは、画像の本体 (xl/media/) と、画像をどこに置くか (xl/drawings/)、そしてそれらをシートに結びつける参照 (_rels) が別々のパーツに分かれていること。この 3 つが揃って初めて Excel は「シート上のこの位置にロゴを表示する」と解釈できる。

セル値は文字列そのものとは限らない — sharedStrings の罠

シート XML を覗くと、セル 1 個は <c> (cell) タグで表される。中の <v> (value) に値が入る。ところが文字列セルの場合、<v> に入っているのは文字そのものではなく、sharedStrings.xml の何番目かを示す添字であることが多い。

<!-- sheet1.xml のセル。t="s" は「文字列型」の意味 -->
<c r="A1" t="s"><v>0</v></c>
<!-- sharedStrings.xml。上の <v>0</v> は「0 番目 = 得意先名」を指す -->
<sst>
  <si><t>得意先名</t></si>   <!-- インデックス 0 -->
  <si><t>商品名</t></si>     <!-- インデックス 1 -->
</sst>

つまり A1 の中身は「0」という数字ではなく「得意先名」という文字列だ。同じ文字列が何度も出てくるブックでは、実体を 1 か所に集めて番号で参照することでファイルを軽くしている。これが shared（共有）strings という名前の由来。openpyxl のような正規のライブラリを使えばこの変換は自動でやってくれるが、自力で ZIP を開いて XML を直読みするときは、この間接参照を知らないと「セルに 0 が入っている」と誤読する。

もう一つの罠が名前空間 (namespace)。OOXML の XML タグには裏で長い名前空間 URI がぶら下がっている。素朴に //v のような XPath で探すと名前空間が一致せず何もヒットしないことがある。名前空間を無視して要素名だけで拾いたいときは、次のように local-name() を使うのが定石だ。

# 名前空間に依存せず <v> 要素を拾う XPath
values = tree.xpath("//*[local-name()='v']")

なぜ openpyxl は画像や図形を落とすのか

openpyxl は「Excel エンジンを使わずに」ブックを読み書きするライブラリだ。ファイルを開くと ZIP を展開して XML をオブジェクトに読み込み、保存時にはシートの XML を自前で組み立て直して ZIP に書き戻す。

問題はここ。openpyxl が理解して再現できるパーツ（セル値・数式・書式・一部のグラフや画像）は作り直せるが、理解できない・サポート範囲外のパーツ（各種の図形＝shapes、テキストボックス、一部の drawing 参照など）は再生成時に取りこぼす。元の ZIP からそのまま運んでくれるわけではないので、結果として保存後のファイルからロゴや図形が消える。

openpyxl 自身もこれを警告してくる。図形を含むブックを読むと、こんなメッセージが出る。

UserWarning: Wmf image format is not supported so the image is being dropped
UserWarning: Charts and images will be preserved but shapes and drawings
             will be lost when saved.

要するに「グラフと画像は残せることもあるが、図形 (shapes / drawings) は保存で失われる」という自己申告だ。テンプレートを openpyxl で開いて save() した時点で失われるので、「数字を書き換えただけなのに」という体感になる。

回避策 — テンプレートから media/drawings をバイナリコピーで復元する

openpyxl が落とすなら、落ちたパーツを後から ZIP レベルで戻してやればいい。発想はこうだ。

  1. 元のテンプレート xlsx を ZIP として開き、xl/media/ や xl/drawings/ などの画像関連エントリを控えておく。
  2. openpyxl で値を書き換え、別名で保存する（この時点で画像は落ちている）。
  3. 保存後の xlsx（これも ZIP）を開き、控えておいた画像エントリをバイナリのまま書き戻す。

zipfile 標準ライブラリで 2 つの ZIP を同時に開いてエントリを付け替えるイメージだ。

import zipfile, shutil

TEMPLATE = "template.xlsx"   # ロゴ・図形入りの元ファイル
GENERATED = "output.xlsx"    # openpyxl 保存後（画像が落ちている）
RESTORE_PREFIXES = ("xl/media/", "xl/drawings/")  # 戻したいパーツ

# 元テンプレートから、戻すべきエントリ名を集める
with zipfile.ZipFile(TEMPLATE) as z:
    keep = [n for n in z.namelist()
            if n.startswith(RESTORE_PREFIXES)]

# 生成物を作り直し、画像パーツだけ元テンプレートから差し込む
tmp = "output_fixed.xlsx"
with zipfile.ZipFile(GENERATED) as src, \
     zipfile.ZipFile(TEMPLATE) as tpl, \
     zipfile.ZipFile(tmp, "w", zipfile.ZIP_DEFLATED) as dst:
    # openpyxl が書いたパーツはそのまま流用
    for item in src.namelist():
        if item.startswith(RESTORE_PREFIXES):
            continue  # 空っぽの側は捨てる
        dst.writestr(item, src.read(item))
    # 画像・図形は元テンプレートのバイナリを移植
    for item in keep:
        dst.writestr(item, tpl.read(item))

shutil.move(tmp, GENERATED)

コードの流れだけ言葉にすると——「元テンプレートから画像フォルダの中身をそっくり借りてきて、openpyxl が作った新しいファイルの、空になった画像フォルダに貼り直す」。セルの値は新しいファイルのもの、絵は元テンプレートのもの、といいとこ取りをしている。実際には _rels や [Content_Types].xml の参照整合も必要になるケースがあるので、テンプレートの構造を崩さず、書き換えるのはセル値だけに留めるのがコツ。

もう一つの実務メモ。画像が大量にあるブックを扱うとき、すべてを io.BytesIO（メモリ上のファイル）で処理するとメモリを食って不安定になりやすい。物理ファイル（テンポラリファイル）を経由して読み書きする方がメモリ消費が安定する。数枚なら BytesIO で問題ないが、数十〜数百枚の画像を回すバッチではファイル経由を選ぶ。

読み込みオプションの落とし穴

openpyxl で load_workbook() を呼ぶときのオプションも、知らないとデータを失う。

オプション挙動注意点
keep_vba=TrueVBA マクロ（xl/vbaProject.bin）を保持これを外して .xlsm を保存するとマクロが丸ごと消え、Excel で「マクロ有効ブック」として開けなくなる
data_only=True数式ではなく、Excel が最後に計算したキャッシュ値を読むExcel で一度も開いて保存していないファイルは、キャッシュが無く None になることがある
data_only=False（既定）セルに入っている数式そのもの（=SUM(...)）を読む計算結果ではなく式の文字列が返る

data_only の要点は「式が欲しいのか、計算後の数字が欲しいのか」で決めること。True は計算結果、False は式。ただし True のキャッシュ値は「Excel が前回保存時に計算して埋め込んでおいた値」を読んでいるだけで、openpyxl 自身が再計算しているわけではない。

そして最も見落としやすいのが、openpyxl は Excel エンジンを一切使わないという点。ZIP と XML を直接いじっているだけなので、Worksheet_Change のような VBA のイベントは発火しないし、開くだけで動くマクロも走らない。数式の自動再計算も行われない（キャッシュ値を読むだけ）。「Excel で開けば動く仕掛け」を前提にした処理は、openpyxl では動かないと考えておくと事故が減る。

まとめ

  • xlsx/xlsm は 1 枚のバイナリではなく、XML を束ねた ZIP アーカイブ。拡張子を .zip にすれば中を覗ける。画像本体は xl/media/、配置情報は xl/drawings/、文字列プールは xl/sharedStrings.xml、紐付けは _rels。
  • 文字列セルの <v> は sharedStrings への添字のことがあり、名前空間付き XML は local-name() を使わないと拾えない。
  • openpyxl は保存時にシート XML を再生成するため、図形・drawing 参照・非対応の画像を落とす（「shapes and drawings will be lost」警告）。
  • 回避策は、テンプレートと生成後 xlsx を 2 つの ZIP として開き、xl/media/・xl/drawings/ をバイナリコピーで復元すること。大量画像は BytesIO よりも物理ファイル経由がメモリ安定。
  • 読み込みは keep_vba（外すとマクロ消失）、data_only（True=キャッシュ値 / False=数式）に注意。openpyxl は Excel エンジンを使わないので、Worksheet_Change 等のイベントは発火しない。
