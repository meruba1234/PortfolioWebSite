Git改行コードクロスプラットフォーム

改行コード（CRLF / LF）と Git の autocrlf

背景

本番共有フォルダにある Windows 用ソース（VB.NET）を、Git リポジトリ（社内の CodeCommit）でバージョン管理し始めたところ、「本番のソースと Git のソースで改行コードが違う」と言われた。単純にコピーしただけなのになぜ違うのか、を調べて整理したノート。

結論を先に言うと、ファイルコピーが改行を変えたのではなく、Git の設定 core.autocrlf=true がコミット時に改行コードを変換していたのが原因だった。

改行コードとは

テキストファイルの「行の終わり」を表す制御文字。OS によって標準が違う。

記号正式名バイト主なOS
CRLFCarriage Return + Line Feed0D 0A（2バイト）Windows
LFLine Feed0A（1バイト）Linux / macOS

見た目は同じ「改行」でも、中身のバイトが違う。だから中身が同一に見えるファイルでも改行コードが違えば「別物（差分あり）」と判定されることがある。

まず大前提：単純なファイルコピーでは改行は変わらない

Explorer のコピー＆ペースト、copy / xcopy / robocopy、共有フォルダ（SMB）経由のコピーは バイト列をそのまま複製するので、改行コードも BOM も一切変わらない。Windows→Windows でも同じ。

改行コードが変わるのは「コピー」そのものではなく、間に挟まる処理が原因：

  • Git（core.autocrlf の設定による自動変換）← 今回の犯人
  • エディタの保存（メモ帳・VSCode などが別の改行で再保存）
  • テキストのコピペ（ファイルではなく中身をクリップボード／ターミナル経由で移す）
  • PowerShell の Set-Content / Out-File / リダイレクト（CRLF や BOM が付いたり変わる）

Git が改行を変換する仕組み（core.autocrlf）

Git には改行コードを自動変換する設定 core.autocrlf がある。値は3種類。

設定コミット時（add）取り出し時（checkout）リポジトリ内部の保存形
trueCRLF → LF に変換LF → CRLF に戻すLF
inputCRLF → LF に変換変換しないLF
false変換しない変換しない元のまま（CRLF なら CRLF）

ポイント：true は「元が CRLF でも、保存時に LF へ剥がす」。「リポジトリ内部は LF、手元の作業フォルダは CRLF」という振り分けを自動でやる設定。（Windows 開発者が LF リポジトリに参加するための折衷案）

なぜ Git はわざわざ LF に正規化するのか

Git はもともと Linux／複数OSでの共同開発のために作られたツール。

  1. OSが違っても差分が出ないようにするため（最大の理由）

各自が自分のOSの改行で保存すると、Windows の人と Linux の人が同じファイルを触るたびに「中身は同じなのに全行が変更された」巨大な差分が出る。内部を LF に統一すると起きない。

  1. diff / merge / blame をきれいに保つため — 改行が混ざるとマージ衝突や blame 追跡が壊れる。
  2. Unix 系ツールが CRLF で壊れるのを避けるため — シェルスクリプトや Makefile は CRLF で動かなくなる。

→ これは複数OS開発を前提にした汎用的な思想。 Windows 専用プロジェクトでは LF 正規化の恩恵はなく、「リポジトリ ≠ 本番」のズレを生むだけ。

実例：3か所を測ると状態が違った

同じ 1 ファイルを、3つの場所で改行コードを実測した結果：

版改行コード備考
本番共有フォルダ（原本）CRLFVisual Studio 標準
手元の作業フォルダ（clone した物）CRLF本番とバイト単位で完全一致
Git 内部（＝リポジトリの正本）LFここだけ本番と違う
  • 「手元 vs 本番」は一致していた（cmp で完全一致）。
  • 「Git の中身 vs 本番」がズレているのが実態。
  • core.autocrlf=true が checkout 時に LF→CRLF に戻すので、手元は本番と一致して見える。でもリポジトリの正本は LF になっている。

だから「CodeCommit の Web 画面で見る」「autocrlf=false の別PCで clone する」など Git の中身を直接見る経路だと LF で出てきて、本番の CRLF と「改行が違う」と言われる。

確認コマンド（実習）

# ① 手元ファイルの改行を確認（"CRLF line terminators" と出るか）
file 対象.vb

# ② Git 内部（正本）の改行を確認（0 なら LF 保存、1以上なら CRLF 保存）
git show HEAD:パス/対象.vb | grep -c $'\r'

# ③ 自分のPCの autocrlf 設定と、どの設定ファイルで効いているかを確認
git config --show-origin core.autocrlf

# ④ 本番ファイルと手元ファイルをバイト単位で比較（一致なら無出力）
cmp "本番パス/対象.vb" "手元パス/対象.vb"

全員・リポジトリ単位で改行を固定したいなら .gitattributes

改行の扱いを決める方法は2種類あり、置き場所（＝効く範囲）が違う。

方法実体効く範囲clone で伝わるか
core.autocrlfGit の config（.gitconfig / .git/config）そのPC・そのユーザーだけ伝わらない
.gitattributesリポジトリにコミットするファイルリポジトリ全体（全員）伝わる
  • core.autocrlf はローカル設定。clone しても付いてこないし、CodeCommit でも管理されない。 → 人によって挙動が変わる。
  • .gitattributes はリモート（CodeCommit）にコミットで入るので、誰が clone しても同じ改行ルールが強制される。各PCの autocrlf より優先される。

Windows 専用プロジェクトで本番（CRLF）と一致させたいなら .gitattributes で CRLF 固定にする：

* text=auto eol=crlf
*.png binary

既存のリポジトリを揃え直すときは、.gitattributes を追加してから一度だけ：

git add --renormalize .
git commit -m "chore: 改行コードを CRLF に統一（.gitattributes 追加）"

（改行だけの巨大な diff が1回出るが、中身は変わらないので安全）

整理：Git 関連はすべてローカル、共有したい物だけ push

  • .gitattributes を作る／git add --renormalize／commit はすべてローカルで行う。
  • push して初めて CodeCommit（リモート）に反映される。
  • CodeCommit 側で改行の設定をしたり操作したりすることは一切ない。置き場所（リモート）でしかない。

まとめ・覚え方

  • 単純なコピーは改行を変えない。変えるのは Git・エディタ・PowerShell などの「処理」。
  • core.autocrlf=true は「リポジトリは LF、手元は CRLF」に自動で振り分ける（元が CRLF でも LF に剥がす）。
  • だから「手元は本番と一致」「でも Git の正本は LF」という食い違いが起きる。
  • 覚え方：「true = 手元だけ Windows 仕様、中身は Linux 仕様（LF）」。
  • 全員で改行を揃えたいなら、個人設定（autocrlf）ではなく リポジトリに入る .gitattributes で固定する。
