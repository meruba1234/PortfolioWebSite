Windows管理

「文字化け」は表示の問題か実データの問題か切り分ける

背景

コンソールに流した文字列が文字化けして見える。「取」が「蜿悶」のような謎の文字列に化けている。あわてて「保存処理のエンコード指定が間違っているのでは」「DB のカラムの文字コードが壊れたのでは」と疑いたくなるが、いざファイルを開き直すと中身は正常だった…ということがよくある。

そもそも化けているのは何なのか。表示だけの問題なのか、実データが壊れているのか。ここを確定しないままデバッグを始めると、正常なデータをいじって本当に壊してしまう二次被害すら起こしうる。

文字化けには2種類ある

文字化けは大きく2つに分けられる。原因も対処もまったく別物なので、まずどちらかを見極めるのが最優先。

(a) 実データが壊れているケース 保存時にエンコードを取り違えた、UTF-8 のバイト列を cp932 として書き込んだ、といった理由でファイルや DB の中身そのものが化けている。これは本当の障害で、書き込み側を直さないと直らない。放置すると壊れたデータが下流に伝播する。

(b) 表示エンコードだけの問題（データは正常） ファイルや DB の中身は正しい UTF-8 なのに、それを表示する端末・コンソール・ログビューアが別のエンコード（例: cp932）で解釈するため化けて見える。データは無傷で、表示側の設定を直せば（あるいは正しいツールで開き直せば）ちゃんと読める。

この2つを混同すると、正常なデータ相手に無駄なデバッグを延々と続けることになる。

PowerShell の cp932 出力という典型例

Windows で一番ハマりやすいのがこれ。

PowerShell の出力エンコーディングは既定で cp932（日本語 Windows のレガシーコードページ、Shift_JIS 系）。ところがその出力を、UTF-8 前提の bash 端末や、別プロセスのログにそのまま流し込むと、バイト列の解釈がずれて化けて見える。

# PowerShell (cp932 で出力) → UTF-8 前提の端末に流す
PS> python my_script.py    # 「取引先」→「蜿門ｼ募・」のように化けて見える

だが、my_script.py が実際に書き出したファイルを UTF-8 対応エディタで開くと「取引先」と正常に表示される。化けているのはパイプの途中の表示だけで、成果物は壊れていない、というパターン。ここで「スクリプトのエンコード指定がおかしい」と決めつけて open(..., encoding=...) をいじり始めると、正常なコードを壊すことになる。

確実に切り分ける方法

端末の見た目は信用しない。以下の手段で「表示か実データか」を物理的に確定させる。

(1) 一旦 UTF-8 でファイルに書き出して、別ツールで開き直す コンソールを経由せず、プログラムから直接 UTF-8 でファイルに書く。それを別のエディタやブラウザで開いて正常なら、犯人はコンソールの表示（=(b)）。開いても化けていれば実データが壊れている（=(a)）。

with open("check.txt", "w", encoding="utf-8") as f:
    f.write(target_string)
# check.txt を UTF-8 対応エディタで開いて確認する

(2) Python なら repr() で生の姿を見る print(s) は端末のエンコードを通るので化ける可能性があるが、repr(s) はエスケープ表現になるため端末の解釈に左右されにくい。

print(repr(target_string))   # 例: '取引先' がそのまま見えるか、\x?? の羅列になるか

(3) コードポイント（文字番号）を直接確認する 最終手段。文字を1つずつ Unicode のコードポイントに落として、期待する文字かを数値で照合する。表示に一切依存しない、最も確実な方法。

for c in target_string:
    print(c, hex(ord(c)))
# 取 0x53d6  (= U+53D6) なら、その文字は正しく「取」として保持されている

hex(ord("取")) が 0x53d6 を返せば、メモリ上の文字は正しい。表示が化けていても中身は「取」だと断言できる。

端末側の設定を知っておく

表示の問題（b）だと分かったら、直すのは端末側。関係する設定は環境ごとに違う。

  • Windows のコマンドプロンプト: chcp でコードページを確認・変更する。chcp 65001 で UTF-8 に切り替わる（既定は日本語環境で 932 = cp932）。
  • PowerShell: $OutputEncoding が外部プログラムへ渡す際のエンコード。[Console]::OutputEncoding が画面表示のエンコード。両者は別物なので、どちらが効いているか意識する。
  • Python: 環境変数 PYTHONIOENCODING（例 PYTHONIOENCODING=utf-8）で標準出力のエンコードを固定できる。また、リダイレクト先がファイルかパイプか端末かによっても既定の挙動が変わる。
chcp                # 現在のコードページ確認 (例: 932)
chcp 65001          # UTF-8 に変更

いずれも「実データには触っていない」点が重要。表示の色眼鏡を替えているだけ。

鉄則

「コンソールの print が化けている」≠「DB や実ファイルが化けている」。

化けを見つけたら、コードをいじる前にまず切り分ける。

  1. 表示だけの問題か、実データが壊れているかを repr / コードポイント / 別ツールで開き直し により確定する。
  2. 表示だけなら端末側（chcp / OutputEncoding / PYTHONIOENCODING）を直す。書き込み側のコードは触らない。
  3. 実データが壊れていて初めて、保存処理のエンコード指定を修正する。

順番を守れば、正常なデータを壊す事故を防げる。

まとめ

  • 文字化けには「実データが壊れている(a)」と「表示エンコードだけの問題(b)」の2種類がある。混同すると無駄なデバッグにハマる。
  • PowerShell の既定出力は cp932。UTF-8 前提の端末やログに流すと化けて見えるが、成果物ファイルは正常なことが多い。
  • 切り分けは端末の見た目に頼らない。UTF-8 でファイルに書き出して別ツールで開く / repr() / hex(ord(c)) でコードポイントを直接確認する。
  • 表示の問題なら端末側（chcp / $OutputEncoding / PYTHONIOENCODING）を直す。実データは触らない。
  • まず「表示か実データか」を確定してから直す。これが鉄則。
