SQL Server権限設計安全設計

本番 DB を壊さない多層防御 — 権限層で担保する

背景

本番 DB を「読むだけ」で使いたい場面はよくある。売上を集計するツール、外部システムの請求書と社内データを突き合わせる照合ツール、レポート生成バッチなど。これらは SELECT しかしないはずだが、コードにバグがあって誤って UPDATE や DELETE を投げてしまえば、本番データが壊れる。壊れたら業務が止まるし、復旧も簡単ではない。

このとき「アプリのコードはバグらない」という前提だけに賭けるのは弱い。人間もコードもいつか間違える。大事なのは、1 つの対策が破れても別の層が止めてくれるように、防御を重ねること。これを defense in depth（多層防御）と呼ぶ。

以下、弱い層から強い層まで整理して、どう重ねるかを見ていく。

防御の層を整理する

読み取り専用ツールで「絶対に書き換えない」を担保する層は、大きく 3 つある。

層仕組み誰が止めるか強さ
運用層接続フラグ・環境変数で「読み取りモード」を明示運用・設計者弱（宣言的、破れる）
アプリ層autocommit=False にして Commit を書かないアプリ中（変更をロールバック）
権限層DB アカウントに UPDATE/INSERT/DELETE を与えないDB エンジン強（物理的に弾く）

ポイントは、下の行ほど「人の注意」に依存せず、機械が強制してくれること。一番下の権限層が最も信頼できる。

権限層 — 最も強い防御

いちばん強いのは DB の権限（GRANT）で縛ること。読み取り専用の DB アカウントを 1 つ用意し、そのアカウントには SELECT だけを許可して UPDATE / INSERT / DELETE を一切与えない。

-- 読み取り専用ユーザーを作り、SELECT だけ許可する例
CREATE USER report_reader WITH PASSWORD '********';

-- 参照だけ許可（UPDATE/INSERT/DELETE は付与しない）
GRANT SELECT ON ALL TABLES IN SCHEMA sales TO report_reader;

-- 将来追加されるテーブルにも自動で SELECT を効かせる
ALTER DEFAULT PRIVILEGES IN SCHEMA sales GRANT SELECT TO report_reader;

この状態なら、アプリのコードがバグで誤って UPDATE を発行しても、DB 側が権限エラーで物理的に弾く。

ERROR: permission denied for table order_detail

アプリのバグに関係なく、DB エンジンそのものが「このアカウントは書けない」と拒否する。だから権限層は、アプリの品質に依存しない一番信頼できる防波堤になる。

ツール側の接続文字列には、この読み取り専用アカウントの資格情報だけを持たせる。書き込み権限のあるアカウントを渡さないことが大前提。

アプリ層 — autocommit=False で明示 Commit を封じる

権限が理想だが、事情があって書き込み権限つきのアカウントしか使えないこともある。そのときのアプリ側の追加防御が autocommit=False。

多くの DB ドライバは、明示的に commit() を呼ばないとトランザクションが確定しない。autocommit=False にしておき、コードのどこにも commit() を書かなければ、万一 UPDATE が実行されても接続終了時にロールバックされて無かったことになる。

# autocommit=False（デフォルト）。commit() を一切書かないポリシー
conn = connect(dsn, autocommit=False)
try:
    cur = conn.execute("SELECT amount FROM order_detail WHERE ...")
    rows = cur.fetchall()
    # ここで commit() は絶対に呼ばない
finally:
    conn.rollback()   # 変更があっても取り消して閉じる
    conn.close()

ただし注意。これは「変更が発生したが確定させない」層であって、権限層ほど強くない。

  • commit() をうっかり書いてしまえば意味がない（人の注意に依存する）。
  • そもそも SELECT しかしないなら確定するものが無いので、効果は限定的。
  • DDL（CREATE / DROP など）は DB によっては暗黙コミットされ、ロールバックできないこともある。

つまりアプリ層は「保険」であって主役ではない。主役はあくまで権限層。

運用層 — 読み取りモードを宣言する

いちばん外側、運用層は「このツールは読み取り専用だ」と分かる形で明示すること。DB エンジンが強制するわけではないので防御としては弱いが、設計意図がコードや設定に残ることで事故を減らせる。

  • 自前の環境フラグ（例: DB_MODE=readonly）を接続時にチェックし、書き込み系の関数を呼べないようにする。
  • SQL Server なら接続文字列に ApplicationIntent=ReadOnly を付けられる。これは可用性グループ構成で読み取りレプリカ側へ振り分ける指定で、参照系の負荷を分散しつつ、書き込みの主系（プライマリ）とは経路が分かれる。
Server=tcp:example-listener,1433;Database=sales_report;
ApplicationIntent=ReadOnly;

ApplicationIntent=ReadOnly は「読み取り経路に流す」という運用・アーキテクチャ上の分離であって、それ単体でテーブルへの書き込みを禁止する権限制御ではない点に注意。あくまで権限層と組み合わせて使う。

多層防御の考え方

まとめると、こう重ねる。

層役割破られたときに拾ってくれる下の層
運用層（read フラグ / ReadOnly intent）意図の宣言・経路分離アプリ層・権限層
アプリ層（autocommit=False）変更をロールバックする保険権限層
権限層（GRANT SELECT のみ）DB が物理的に書き込みを拒否（最終防衛線）

大事なのは 1 つの対策に賭けないこと。運用フラグを付け忘れても、commit() を書き間違えても、最後に権限層が UPDATE を弾いてくれる。逆に権限層があっても、運用・アプリ層で意図を明示しておけば、そもそも危険なコードが書かれにくくなる。層は互いを補い合う。

まとめ

  • 本番 DB を読むだけのツールで「絶対に書き換えない」を担保したいとき、アプリがバグらない前提に頼るのは弱い。層を重ねる（defense in depth）。
  • 最強の層は権限。読み取り専用アカウントに UPDATE/INSERT/DELETE を与えなければ、バグで誤って書き込もうとしても DB が権限エラーで物理的に弾く。
  • アプリ層の保険は autocommit=False ＋ Commit を書かないこと。ただし SELECT only なら効果は限定的で、主役にはならない。
  • 運用層は読み取りモードの宣言。SQL Server の ApplicationIntent=ReadOnly は読み取りレプリカへの経路分離で、負荷分散と書き込み経路の分離に効く（権限制御そのものではない）。
  • 結論: 権限・トランザクション・運用フラグを重ね、どれか 1 つが破れても他が止める設計にする。
