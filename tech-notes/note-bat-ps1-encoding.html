Windows管理

.bat / .ps1 の文字コード・BOM・改行の罠

背景

スクリプトやツールで .bat / .ps1 を自動生成すると、手元では動くのに本番で日本語が化ける・構文エラーで落ちる、という事故が起きやすい。原因はほぼ「文字コードと BOM の選び方を間違えている」こと。cmd.exe と PowerShell では期待するエンコーディングが違うため、同じ「UTF-8 で保存」でも片方が壊れる。どのエンコーディングで書けばいいのか、なぜそうなるのかを整理しておくためのノート。

cmd.exe は CP932（Shift_JIS）+ CRLF が前提

Windows の cmd.exe は、.bat ファイルを CP932（Shift_JIS）+ CRLF として解釈する。ここに UTF-8（BOM なし）+ LF で日本語コメントを書くと、cmd がバイト列を Shift_JIS として読むため盛大に化け、化けた結果が偶然コマンドとして解釈されて '縺ゅ・' は、内部コマンド... のようなエラーになる。

よくある誤解が「冒頭に chcp 65001 を書けば UTF-8 で読んでくれる」というもの。これは間違い。

@echo off
chcp 65001
echo にほんご

chcp 65001 が効くのは、この .bat が起動した後の コンソール出力／入力のコードページだけ。 .bat ファイル自身のバイト列を cmd が読む段階は、chcp 実行より前なので、ファイル本体は依然 CP932 として解釈される。つまり echo にほんご の「にほんご」は化けたまま。

対策は2つ。

対策内容使いどころ
Shift_JIS 保存.bat を CP932 で保存する日本語コメント・日本語 echo をどうしても入れたいとき
ASCII のみにする日本語を一切書かない（コメントも英語）一番事故らない。自動生成なら基本これ

改行も CRLF にしておくのが無難。LF だけだと goto ラベルや行連結でまれに崩れる。

バッチの特殊記号（( ) : 等）で構文が壊れる

.bat は文字コード以外にも地雷がある。REM コメント行や set /p のプロンプト文字列の中に ( ) : & | < > ^ % などのバッチ特殊記号が入っていると、パーサがそれを構文として拾ってしまう。

特に厄介なのが if ( ... ) や for ... do ( ... ) のブロック内。ブロックは ) で閉じるので、コメントやメッセージの中の半角 ) がブロックを途中で閉じてしまい、( が予期されていませんでした。 のような構文エラーになる。

if "%mode%"=="run" (
    rem 実行モード (本番) です   ← この ) でブロックが閉じてしまう
    call :main
)

対策：ブロック内のメッセージに書く括弧などは全角に置換する（（本番））、あるいは特殊記号を ^ でエスケープする。自動生成では「メッセージ中の半角括弧・コロンを全角に寄せる」フィルタを1枚かませておくと安全。

PowerShell（5.x）は BOM なし UTF-8 を Shift_JIS と誤読する

Windows PowerShell 5.x は、BOM のない .ps1 をデフォルトで Shift_JIS（既定の ANSI コードページ）として読む。そのため日本語入りの .ps1 を UTF-8（BOM なし）で保存すると、cmd と同じ理由で化ける。文字列だけならまだしも、日本語がコメントに含まれるだけでもトークナイズがずれて 文字列に終端記号 " がありません のような構文エラーになることがある。

解決策は UTF-8 BOM 付きで保存すること。BOM があると PowerShell は「これは UTF-8 だ」と正しく判定する。 UTF-8 BOM の正体はファイル先頭 3 バイトの EF BB BF。

# BOM 有無をバイトで確認
Format-Hex .\script.ps1 -Count 3
# 先頭が EF BB BF なら BOM 付き UTF-8

PowerShell 7（Core）はデフォルトが BOM なし UTF-8 なので事情が違うが、社内で使うのが Windows PowerShell 5.x なら「日本語 .ps1 は BOM 付き」で統一しておくのが安全。

ただし BOM が邪魔なファイルもある（BOM なしで書く方法）

BOM は万能ではない。BOM を嫌う読み手も多い。代表例が設定ファイル（Web サーバの *.conf など）で、先頭に EF BB BF があるとパーサがそれを設定値の一部として読んでしまい、起動失敗やパースエラーになる。

ここで罠なのが PowerShell の Out-File -Encoding utf8 や Set-Content -Encoding utf8。5.x ではこれらが BOM 付き UTF-8 で書き出す。「utf8 を指定したのに BOM が付く」ので設定ファイル生成で事故る。

BOM なし UTF-8 で確実に書きたいときは、.NET の API を直接叩く。

$path = 'C:\path\to\app.conf'
$text = "server_name example.internal;`n"
# 第3引数の UTF8Encoding($false) が「BOM なし」の意味
[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))

New-Object System.Text.UTF8Encoding($false) の $false が 「BOM を付けない」。ここを $true にすると BOM 付きになる。まとめると：

書きたいもの推奨エンコーディングPowerShell での書き方
日本語入り .ps1UTF-8 BOM 付きWriteAllText + UTF8Encoding($true)
設定ファイル（.conf 等）UTF-8 BOM なしWriteAllText + UTF8Encoding($false)
.batCP932 か ASCII のみ別途 Shift_JIS で保存

日本語を避けるテク：[char]0xXXXX で組み立てる

「そもそも日本語をファイルに埋め込まなければエンコーディング事故は起きない」という発想もある。実行時に必要な日本語メッセージは、ファイル上は ASCII（コードポイント）で書いておき、実行時に文字へ組み立てる。

# 「完了」を Unicode コードポイントから組み立てる
$msg = [char]0x5B8C + [char]0x4E86   # 完 + 了
Write-Host $msg

こうするとファイル本体は ASCII のみなので、BOM の有無やコードページに左右されずどんな環境でも同じ結果になる。多用すると読みにくいが、「1〜2 個の固定メッセージだけ確実に出したい」ときに有効。

定石：.bat は薄いラッパー、中身は .ps1

.bat は CP932 の制約が強く、特殊記号にも弱いので、日本語 UI やまともなロジックを持たせるのに向かない。そこで定石は「.bat は起動役の薄いラッパーに徹し、実処理と日本語表示は .ps1 に寄せる」。

@echo off
rem ASCII only. Just launch the PowerShell script.
powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0main.ps1"
  • .bat … ASCII のみ・特殊記号なし・CRLF。壊れようがない最小限
  • main.ps1 … UTF-8 BOM 付き。日本語メッセージ・分岐・ファイル操作はこちらに全部書く

役割を分けることで、「cmd の CP932 問題」と「PowerShell の BOM 問題」をそれぞれの得意な側だけで完結させられる。

まとめ

対象期待エンコーディングハマりどころ
.bat（cmd.exe）CP932 + CRLFchcp 65001 を書いてもファイル本体は CP932 のまま。日本語は Shift_JIS 保存か ASCII 化
.bat の括弧・コロン—if(...) ブロック内の半角 ) : が構文を壊す。全角化 or ^ エスケープ
.ps1（PowerShell 5.x）UTF-8 BOM 付き（EF BB BF）BOM なしだと Shift_JIS 誤読で化け・構文エラー

覚え方：

  • cmd は Shift_JIS の世界、PowerShell 5.x は BOM で UTF-8 を見分ける世界
  • chcp 65001 は出力のコードページを変えるだけ、ファイル解釈は変えない
  • -Encoding utf8 は 5.x では BOM 付き。BOM なしは WriteAllText + UTF8Encoding($false)
