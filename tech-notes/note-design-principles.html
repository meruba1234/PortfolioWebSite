用語集

設計原則・アーキテクチャ用語

ソフトウェア設計の会話で出てくる「○○結合」「○○度」系の用語をまとめる。

疎結合（そけつごう / loose coupling）

ひとことで言うと

部品どうしが「相手の細かい中身を知らなくても使える」状態のこと。

もう少し詳しく

あるモジュール A が別のモジュール B を呼ぶとき、A が B の内部実装（変数名、データ構造、処理順序）に依存していなければ「疎結合」。

逆に、B の中の特定のテーブル名やプライベートな関数名を A が直接触っていると「密結合（みつけつごう）」になる。

疎結合にしておくと、

  • B の中身を書き換えても A を直さなくていい。
  • A をテストするときに B を偽物（モック）に差し替えやすい。
  • 同じ A を別の B' に繋ぎ替えやすい。

実現する典型的な手段：

  • インターフェース（抽象クラス・プロトコル）を間に挟む。
  • 関数の引数で依存物を受け取る（依存性注入 / DI）。
  • 共通の中間データ形式（JSON、CSV、辞書）でやり取りする。

業務での例

job-repo の common/groupware.py の GroupwareMailSender を、各 flow が直接呼んでいる構成は 疎結合寄り。flow 側は「メールを下書き保存する」というインターフェースだけ知っていて、グループウェア の HTML 構造や Playwright のセレクタは知らなくていい。

もし flow の中に Playwright のセレクタを直接書いていたら、グループウェア の画面が変わったとき全 flow を直す羽目になる。これが密結合。

関連：凝集度、依存性注入

密結合（みつけつごう / tight coupling）

ひとことで言うと

部品どうしが「相手の中身を知っていないと使えない」状態。疎結合の反対。

もう少し詳しく

密結合そのものが悪いわけではなく、「変更頻度が高い部分」と「変更したくない部分」が密結合になっていると壊れやすい、という話。

社内ツールで使い捨てのスクリプトなら密結合のほうが速く書けることもある。長く保守するコードほど疎結合を意識する。

業務での例

昔の VBA で、フォーム上のテキストボックスの Text プロパティを直接 SQL の中に文字列連結していた書き方は密結合の典型。画面を変えると SQL も壊れる。

凝集度（こうしゅうど / cohesion）

ひとことで言うと

1つのモジュール（クラス・ファイル）の中の処理が「どれくらい1つの目的に集中しているか」。

もう少し詳しく

凝集度が高い = そのファイルを見ると「これは○○をやるための部品だ」と一言で言える状態。

凝集度が低い = 1つのファイルにメール送信もExcel処理もDBアクセスも入っていて、何屋なのか分からない状態。

設計の合言葉：「疎結合・高凝集」。

  • モジュール内部の関係は密に（高凝集）。
  • モジュール同士の関係は疎に（疎結合）。

業務での例

job-repo の common/excel.py は「Excel を読み書きする」だけに集中しているので高凝集。ここに 社内チャット 通知のコードを足し始めると凝集度が下がる。

依存性注入（DI / Dependency Injection）

ひとことで言うと

部品が必要なものを「自分で作らず、外から渡してもらう」やり方。

もう少し詳しく

クラス A が中で b = B() と書いて B を作っていると、A は B に縛られる（密結合）。

代わりに def __init__(self, b): self.b = b のように B を引数で受け取れば、テスト時には偽の B を渡せるし、本番では本物の B を渡せる。これが DI。

Python では仰々しい DI フレームワークを入れなくても、コンストラクタや関数の引数で渡すだけで十分なことが多い。

業務での例

PrefectEnvLoader を flow に渡す書き方は DI 的。flow は「環境変数ローダーが来る」とだけ知っていれば、それが Prefect から取ってきたものでも .env から取ってきたものでも動く。

単一責任の原則（SRP / Single Responsibility Principle）

ひとことで言うと

「1つのクラス（関数）には、変更理由が1つだけになるようにする」。

もう少し詳しく

「責任 = 変更を要求してくる人・理由」と考えるのがコツ。

  • 営業部の都合で変えたくなる処理
  • 経理部の都合で変えたくなる処理
  • システム部の都合で変えたくなる処理

この3つが1つのクラスに同居していると、誰かの要望で直したときに他の人の処理が壊れる。

SRP は SOLID 原則の S。

業務での例

異常受注検知で「データを取得するクラス」「異常を判定するクラス」「カードを表示するクラス」を分けているのは SRP の考え方。判定ロジックを変えても表示は壊れない。

関心の分離（SoC / Separation of Concerns）

ひとことで言うと

「種類の違う仕事は、別の場所に書く」。

もう少し詳しく

SRP に似ているが、SoC のほうがもっと大きな粒度の話。例えば、

  • 画面表示の関心
  • 業務ロジックの関心
  • データ保存の関心

を別レイヤーに分けるのが SoC。Web の MVC（Model-View-Controller）も SoC の一例。

業務での例

Flask アプリで、ルーティング（@app.route）と業務ロジック（計算）と DB アクセスを同じ関数にベタ書きすると SoC が崩れている。レイヤーを分けると、画面を変えても計算ロジックは触らずに済む。
