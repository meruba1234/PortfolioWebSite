プログラミング

Unicode 正規化（NFKC）で全角半角・カナの表記揺れを吸収する

背景

システム間でデータを突き合わせるとき、「同じ文字列のはずなのに一致しない」という壁によくぶつかる。原因の多くは表記揺れだ。

  • 全角の ＡＢＣ１２３ と半角の ABC123
  • 半角カナ ｶﾞﾂ と全角カナ ガツ
  • 丸数字 ① と数字 1
  • 単位記号 ㎏ ㍿ と、それを普通の文字で書いたもの

人間の目にはほぼ同じに見えても、コンピュータにとってはコード（文字の背番号）が違うので「別の文字列」と判定される。片方の名簿が全角、もう片方が半角というだけで名寄せ（同じものを結び付ける作業）が失敗する。

これをまとめて解決するのが Unicode 正規化、特に NFKC という形式だ。

NFKC とは

Python なら標準ライブラリだけで使える。

import unicodedata

s = "ＡＢＣ１２３　㍿①ｶﾞ"
normalized = unicodedata.normalize("NFKC", s)

print(normalized)  # "ABC123 株式会社1ガ"

normalize("NFKC", s) に文字列を渡すと、全角英数は半角へ、半角カナは全角カナへ、丸数字や単位記号は普通の文字へ……と、バラバラの表記を1つの決まった形に寄せてくれる。突合の前にこれを1回かけるだけで、上に挙げた揺れの大半が消える。

コードが読めなくても流れはこうだ。「散らかった見た目の文字列を、代表の形に整列させてから比べる」。定規で長さを測る前に、紙の端を揃えるようなものだと思えばよい。

正規化形式の違い

正規化には4種類あり、頭文字で性格が分かる。

形式何を統一するかイメージ
NFC / NFD正準等価（見た目が同一のものを統一）濁点付き文字を「1文字」にまとめる／「文字＋濁点」に分解する
NFKC / NFKD互換等価まで含める① ㍿ Ａ のような特殊表記を普通の文字に潰す
  • C は Composition（合成＝くっつけてまとめる）、D は Decomposition（分解＝バラす）。
  • K が付くと「互換（compatibility）」まで踏み込み、見た目が違っても意味が同じものを普通の文字に変換する。

見た目を保ちたい表示用途なら NFC が無難だが、マッチング（照合）用途では NFKC がよく使われる。丸数字や全角英数まで潰してくれるので、揺れを一番広く吸収できるからだ。

名寄せ・突合の前処理パターン

NFKC は強力だが、それ1発で完璧になるわけではない。実務では次の順で「ノイズ」を段階的に落としてから比較する。

  1. NFKC 正規化 — 全角半角・カナ・互換文字を統一する
  2. 記号・空白の除去 — ・ - 　（全角空白）などを取り除く
  3. ストップワードの除去 — No. Ver. 株式会社 (株) など、比較の役に立たない定型語を落とす
  4. 分割 — 必要に応じて単語や区切りで分ける
import re
import unicodedata

def normalize_for_match(s: str) -> str:
    s = unicodedata.normalize("NFKC", s)      # 1. 表記揺れを統一
    s = re.sub(r"[ \t　・\-_/]", "", s)     # 2. 記号・空白を除去
    for word in ("株式会社", "(株)", "No.", "Ver."):
        s = s.replace(word, "")                # 3. ストップワード除去
    return s.lower()                            # ついでに大文字小文字も統一

# "株式会社 山田製作所" と "ヤマダ製作所（株）" のような揺れを寄せていく

こうして「比較に効く芯の部分」だけを取り出してから照合すると、一致率が大きく上がる。

二段構え：SQL で粗く、Python で精密に

DB に入っている値は、たいてい正規化されていない（全角も半角も混在している）。そのため SQL の LIKE だけで正確にマッチさせようとすると取りこぼす。

そこで二段構えにする。

段階担当役割
一次絞り込みSQL の LIKEざっくり候補を集める（多少余分でもよい）
精密化Python の NFKC ＋ スコアリング正規化して比べ、類似度を点数化して確定する
-- 一次絞り込み: 完璧でなくてよい。候補を広めに拾う
SELECT * FROM customer WHERE name LIKE '%山田%';
# 精密化: 取得した候補を Python 側で正規化して突き合わせる
for row in rows:
    key = normalize_for_match(row["name"])
    score = similarity(key, normalize_for_match(target))  # 類似度を点数化
    ...

DB に大量のデータがあっても、まず LIKE で候補を数十件に減らし、その少数だけを Python で丁寧に判定する。速さ（SQL）と正確さ（Python）を両取りできる。

注意点：正規化は情報を落とす

NFKC は便利な反面、変換すると元の情報が失われる。

  • 全角で入力した「意図」（例：帳票上あえて全角にしていた）は消える
  • ㍿ → 株式会社、① → 1 のように、元の見た目は復元できない

そのため、正規化後の文字列で元データを上書きしてはいけない。安全なのは次の持ち方だ。

  • 原文（表示・保存用）はそのまま残す
  • 正規化後（照合用のキー）は別カラム・別変数として持つ
record = {
    "name": raw_name,                          # 表示はこちら（原文のまま）
    "match_key": normalize_for_match(raw_name),# 照合はこちら（正規化後）
}

「見せる値」と「比べる値」を分けておけば、揺れを吸収しつつ元の情報も守れる。

まとめ

  • unicodedata.normalize("NFKC", s) で全角半角・半角カナ・丸数字・互換文字などの表記揺れを1つの形に寄せられる。
  • 正規化形式は C/D が正準等価、K 付き（NFKC/NFKD）が互換等価まで潰す。マッチング用途では NFKC が定番。
  • 名寄せの前処理は NFKC → 記号空白除去 → ストップワード除去 → 分割 の順でノイズを落とす。
  • 二段構え：DB は LIKE で粗く一次絞り込み、Python 側で NFKC ＋ スコアリングして精密化。
  • NFKC は情報を落とすので、原文（表示用）と正規化後（照合用）を分けて持つのが安全。
