インフラ

Docker のマウント3種（bind / volume / CIFS）とコードを焼き込まない設計

背景

コンテナで動くアプリのコードを直したのに、コンテナに反映されない。あるいは、コンテナの中で作ったつもりのファイルがホストのフォルダに見当たらない。こういう「反映されない」「見えない」系のハマりは、たいてい コンテナの中と外はパスが別空間 であること、そして どこをマウントしているか を正しく把握できていないことが原因です。

Docker には外部とデータをやり取りする仕組みとして大きく3種類のマウントがあり、それぞれ用途が違います。まずここを区別できると、上のようなトラブルが一気に読めるようになります。

マウント3種の違い

Docker 公式でも、これらは別物として区別されています。

種類実体の置き場所主な用途特徴
bind mountホストの任意パス（例 /opt/app）コード・設定・データの共有ホスト側で編集した内容がそのままコンテナに見える
volume（named volume）Docker が管理する領域永続データ（DB のデータ等）ホストのどこにあるか意識しない。Docker が面倒を見る
CIFS mountSMB 共有（例 \\server\share）ネットワーク共有をコンテナから使うファイルサーバ上のフォルダをコンテナにマウント

ざっくり言うと、

  • bind mount = 「ホストのこのフォルダを、コンテナのここに見せて」
  • volume = 「Docker、永続データを預かっておいて。場所は任せる」
  • CIFS mount = 「ネットワーク上の共有フォルダを、コンテナにつないで」

という役割分担です。

コードは Dockerfile に焼き込まず、bind mount で見せる

アプリのコードの扱い方には2通りあります。

  1. Dockerfile に COPY して焼き込む → コードはイメージの中に固定される
  2. bind mount で見せる → コードはホスト側にあり、コンテナはそれを覗くだけ

開発・運用では 2 の bind mount が扱いやすい場面が多いです。理由は、コードがホスト側にあるので、

  • ホストでファイルを編集する
  • ホストで git pull する

だけでコンテナに反映され、イメージの再ビルドもコンテナの再起動も不要（ホットリロード）だからです。焼き込んでしまうと、1行直すたびに再ビルド → 作り直し、という手間がかかります。

compose での書き方のイメージ:

services:
  app:
    image: myapp:latest
    volumes:
      # ホストの /opt/app を、コンテナの /app に bind mount
      - /opt/app:/app

この状態なら、ホストの /opt/app を編集すればコンテナの /app に即反映されます。

例外: 依存ライブラリを追加したときだけは再ビルド

bind mount ならいつでもノータッチ、というわけではありません。新しい依存ライブラリを追加したとき は話が別です。ライブラリはコードと違ってイメージの中（pip install 等の結果）に入っているので、

  • 依存を追加 → Dockerfile（や requirements）を更新 → イメージを再ビルド

が必要になります。「コードを直しただけ = 再ビルド不要 / ライブラリを増やした = 再ビルド必要」と覚えておくと迷いません。

コンテナの中と外は別空間

ここが一番ハマりやすいポイントです。コンテナ内のパス（/tmp やアプリ用のパス）は、ホストとはまったく別の空間 です。マウントしていない限り、コンテナ内に書いたファイルはホストからは見えませんし、その逆もしかりです。

ホスト                          コンテナ
--------                        --------
/opt/app   ── bind mount ──▶    /app        ← ここは共有されている
/tmp       （無関係）           /tmp        ← 名前は同じでも別物
                                /var/log/x  ← マウントしてなければホストから見えない

「コンテナの中で /tmp にファイルを書いたのに、ホストの /tmp に無い」というのは、この別空間を混同しているのが原因です。ホストと共有したいパスは、明示的に bind mount する必要があります。

権限: マウントしていても書けないことがある

ホスト側パスを bind mount していても、そのパスの所有者が root だと、ホストの一般ユーザーからは書けない ことがあります。

  • ホストの一般ユーザー → root 所有フォルダには書き込めない
  • コンテナは root 権限で動いていることが多い → コンテナ経由なら操作できる

なので「マウントはしてあるのにホストから編集できない」ときは、所有者・権限を確認します。ホストで直接いじれない場合は、コンテナの中に入って操作する、という回避になることがあります。

補足: hostname でホストは識別できない

デバッグ時にありがちな落とし穴として、コンテナ内で

import socket
socket.gethostname()   # 例: '3f9a1c2b7d4e'（Container ID の先頭12桁）

を呼んでも、返ってくるのは Container ID の先頭12桁 です。物理ホストの名前ではありません。しかもコンテナを作り直すたびに変わります。

そのため、「どのサーバで動いているか」「どの環境（本番/検証）か」といった 意味のあるラベルは、環境変数で注入する のが定石です。

services:
  app:
    environment:
      - APP_ENV=production
      - HOST_LABEL=main-server

hostname はホスト識別に使えない、と割り切っておきます。

まとめ

  • Docker のマウントは bind（任意パス共有）/ volume（Docker 管理の永続データ）/ CIFS（SMB 共有） の3種。用途で使い分ける。
  • コードは焼き込まず bind mount で見せる と、ホストで編集 / git pull するだけで反映され、再ビルド・再起動が不要。ただし 依存ライブラリの追加時だけは再ビルドが必要。
  • コンテナの中と外はパスが別空間。マウントしていないパスは互いに見えない。「書いたのに反映されない」の典型原因。
  • マウントしていても root 所有のパスは一般ユーザーから書けない。権限を確認する。
  • socket.gethostname() は Container ID を返す。ホスト識別には使えず、意味のあるラベルは 環境変数で注入 する。
