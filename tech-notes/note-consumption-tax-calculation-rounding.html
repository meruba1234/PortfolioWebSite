データベース

消費税の計算・丸めと内税/外税・軽減税率（1円差の追い方）

背景

既存の請求書 PDF の消費税額と、自分で SQL から集計し直した消費税額が 1 円だけ合わない。金額そのものが大きくズレるならロジックの根本ミスだが、「1 円」という微妙な差は原因がわかりにくい。

売上明細から消費税を積み上げる自作集計と、請求書を発行しているシステム側の計算で、なぜ 1 円ズレるのか。この 1 円を追いかける過程で、消費税計算にまつわる論点（内税/外税・税率の持ち方・丸めの方式・丸めの方向）を整理しておく。同じハマり方を次回もするので、ここに残す。

内税（税込）と外税（税抜）

まず「請求対象の金額はどちらの世界の数字か」を最初に確定させる。ここが曖昧なまま計算すると、そもそも比較する土俵が違ってくる。

区分意味消費税額の扱い
外税（税抜）単価・金額は税抜。消費税は別立てで加算税抜金額 × 税率 が消費税額
内税（税込）単価・金額に税が含まれている税込金額 − 税抜相当額 の差額が消費税額

外税なら「税抜金額に税率を掛ける」で素直に出る。内税の場合だけ「税込と税抜の差」を消費税として逆算する必要があり、この逆算で端数処理が入る。

# 外税
消費税 = ROUND(税抜金額 * 税率)

# 内税（税込から税抜を割り戻す）
税抜相当 = ROUND(税込金額 / (1 + 税率))
消費税   = 税込金額 - 税抜相当

内税の割り戻しは割り算が入るぶん端数が出やすく、丸めの影響も受けやすい。設計時に「このデータは内税か外税か」を必ず一次情報（マスタや帳票仕様）で確認しておく。

税率は商品単位で決まる（軽減税率）

税率は「伝票単位」ではなく 商品単位 で決まることが多い。食品などは軽減 8%、それ以外は標準 10%、といった具合に 1 枚の伝票に複数税率が混在する。

税率の判定元は多くの場合、商品マスタの区分フラグである。

フラグ値意味税率
0 / 空標準10%
1軽減8%
def tax_rate(product, sale_date):
    # 商品マスタの区分フラグで軽減/標準を判定
    is_reduced = product.reduced_flag == 1
    # 売上日を引数に取り、税率テーブルを参照する
    return tax_table.rate(reduced=is_reduced, on=sale_date)

ポイントは 売上日を引数にして税率テーブルを引く設計 にしておくこと。税率は過去に何度も改定されている（3% → 5% → 8% → 10%、そこに軽減 8% が追加）。「今は 10%」とハードコードすると、将来の改定や過去分の再計算で破綻する。税率を 売上日 → 税率 の関数として持てば拡張に強い。

丸めの方式で結果が変わる（明細合算 vs 小計方式）

ここが 1 円差の主犯。同じ明細・同じ税率でも、どの単位で丸めるかで合計が変わる。

方式 A: 明細ごとに税を計算して合算

各明細で  税額 = ROUND(明細税抜 × 税率)
合計税額 = Σ 明細税額

方式 B: 小計方式（得意先×期間×税率でまとめてから丸める）

税率ごとに  小計 = Σ 明細税抜
税額        = ROUND(小計 × 税率)
合計税額    = Σ 税率ごとの税額

同じデータでも結果が違う例（税率 10%、円未満四捨五入）:

明細税抜税額（方式A: 明細ごと丸め）
1105ROUND(10.5) = 11
2105ROUND(10.5) = 11
3105ROUND(10.5) = 11
合計31533

方式 B（小計方式）だと ROUND(315 × 0.10) = ROUND(31.5) = 32。

→ 方式 A では 33 円、方式 B では 32 円。1 円ズレる。

明細ごとに丸めると端数（この例では各 0.5）が明細の数だけ積み上がり、まとめてから丸めるより大きくなりやすい。

請求書 PDF は方式 B（小計方式）を採用していることが多い。 インボイス制度でも「1 請求書あたり税率ごとに 1 回の端数処理」が原則とされているため、帳票側は小計方式で組まれている前提で自作集計を合わせにいくのが基本。自作集計を方式 A のままにしていると、明細数が多い得意先ほどズレやすい。

負の金額（リベート等）の丸め方向

リベート・値引き・返品など、金額が 負 になる明細がある場合、丸めの「方向」で 1 円差が出ることがある。

四捨五入（ROUND_HALF_UP）は絶対値ベースで丸めるため、負数だとゼロから遠い側へ動く。一方、システムによっては負数を ROUND_FLOOR（より負側＝小さい側へ切り下げ）で処理していることがある。

元の値ROUND_HALF_UPROUND_FLOOR
-10.5-11-11
-10.4-10-11
-10.6-11-11

Python の decimal で方向を明示する例:

from decimal import Decimal, ROUND_HALF_UP, ROUND_FLOOR

v = Decimal("-10.4")
v.quantize(Decimal("1"), rounding=ROUND_HALF_UP)  # -10
v.quantize(Decimal("1"), rounding=ROUND_FLOOR)     # -11

「正の明細は合うのに、リベートのある得意先だけ 1 円ズレる」ときは、負数の丸め方向を ROUND_FLOOR に変えると解消することがある。

1 円差の追い方（手順）

  1. 内税/外税を確認 — そもそも比較対象の金額が税込か税抜か。土俵を揃える。
  2. 税率の粒度を確認 — 伝票単位ではなく商品単位。軽減/標準が混在していないか。
  3. 丸めの単位を疑う — 自作集計が明細ごと丸め（方式A）になっていないか。帳票は小計方式（方式B）が多い。まず方式Bに合わせる。
  4. 丸めの方向を疑う — 負の明細がある得意先で、ROUND_FLOOR を試す。
  5. どうしても再現できないなら妥協判断 — 桁ごとの特殊な丸めをシステムが内部で行っている場合、完全再現はコストに見合わないことがある。「明細合算で数円以内に収める」で運用を回す判断もあり。ズレる条件（明細数・負数の有無）を記録しておく。

まとめ

  • 消費税計算はまず 内税/外税 を確定させる。内税のときだけ割り戻しの端数が絡む。
  • 税率は 商品単位（軽減8%/標準10%）。売上日を引数に税率テーブルを引く設計にしておくと改定に強い。
  • 「1 円合わない」の犯人はたいてい 丸めの順序（明細ごと丸め vs 小計方式）か 丸めの方向（負数の ROUND_FLOOR）。
  • 請求書 PDF は 小計方式（税率ごとに1回だけ丸め） が主流。自作集計はここに合わせる。
  • 桁ごとの脆い特殊丸めを完全再現するより、明細合算で妥協する 現実的な落としどころもある。追えなくなったら、ズレる条件を記録して撤退ラインを引く。
