ネットワーク

IMAP の仕組み — UID / UIDVALIDITY・readonly 接続・ポート

背景

「特定のアドレスに届いたメールを、プログラムで自動的に読み取って処理したい」という場面は多い。たとえば受信箱に届いた注文メールやレポートを定期的に拾い上げて、後続の処理に流すようなケースだ。

こうした自動処理を安全に作るには、メール受信プロトコルの仕組みを理解しておく必要がある。特に 同じメールを二度処理してしまわないこと（二重取得の防止） と、 人が手で操作している受信箱を壊さないこと の2点が肝になる。ここでは IMAP を題材に、その要点を整理する。

IMAP と POP3 の違い

メール受信には代表的に IMAP と POP3 の2つのプロトコルがある。

観点IMAPPOP3
メールの実体の置き場所サーバ側に置いたまま取得してローカルに落とす（基本サーバから消える）
複数端末での閲覧同じ状態を共有できる端末ごとにバラバラになりやすい
フォルダ・既読状態サーバ側で管理・同期されるローカル依存
自動処理との相性サーバ上の状態を基準にできる「消える」ため取りこぼしや競合が起きやすい

POP3 は「取ってきてサーバから消す」のが基本動作なので、 PC とスマホの両方で同じ箱を見ると片方でメールが消えて見える、といったことが起きる。

IMAP は メールをサーバに置いたまま読む ので、複数端末で同じ状態を見られる。自動処理を組むときも「サーバ上に真実がある」状態を保てるため扱いやすい。

UID と UIDVALIDITY

IMAP では、メールボックス内の各メールに UID（Unique Identifier） という一意の番号が付く。この UID を手がかりにすれば「どのメールか」をピンポイントで指定できる。

ただし UID には落とし穴がある。メールボックスには UIDVALIDITY という値があり、これが変わると UID 空間がリセットされる。つまり UIDVALIDITY が変化した後は、以前と同じ UID が別のメールを指しうる。

UIDVALIDITY = 100 のとき   UID 42 = 「注文メールA」
　　↓ サーバ都合で UIDVALIDITY が 101 に変わる
UIDVALIDITY = 101 のとき   UID 42 = 「まったく別のメールB」かもしれない

そのため、UID を保存して使う側は次のように扱う。

  1. UID だけでなく UIDVALIDITY もセットで保存 しておく。
  2. 接続のたびに現在の UIDVALIDITY を確認する。
  3. 保存していた値と 変化していたら、UID の管理をやり直す（過去の UID は当てにならない）。

「UID は UIDVALIDITY とペアで初めて意味を持つ」と覚えておくとよい。

二重取得の防止

自動処理でいちばん怖いのが、同じメールを二度処理してしまう ことだ。これを防ぐ方法として、次のようなやり方は 安全ではない。

  • 「既読フラグが付いていないもの」を未処理とみなす方式 → 人が先にメールを開いて既読にしただけで、処理対象から漏れてしまう。
  • 「処理したらフォルダを移動する」方式 → 人の操作や他ツールとの競合でフォルダ構成が変わると破綻する。

安全なのは、自分が処理し終えた UID を自前で記録しておく方式 だ。

方式問題点人の操作の影響
既読フラグで判定人が開くと既読になる受ける（漏れる）
フォルダ移動で判定移動の競合・手動整理で崩れる受ける
処理済み UID を自前記録記録の永続化が必要受けない
処理済みUIDの記録（例）: { UIDVALIDITY: 100, done: [40, 41, 42] }

新着チェック時:
  現在の UIDVALIDITY を確認
    → 記録と一致するなら、done に含まれない UID だけ処理する
    → 変わっていたら done をリセットしてやり直す

このやり方なら、人が受信箱を先に開いて既読にしても、自分の「処理済みリスト」は独立しているので 影響を受けない。

readonly（EXAMINE）で開く

IMAP でメールボックスを開くコマンドは SELECT だが、これには2つのモードがある。

コマンドモードメールの状態（既読フラグ等）への影響
SELECT読み書きメールを読むと既読になるなど、状態が変わりうる
EXAMINEreadonly一切変更しない（状態を保ったまま読める）

自動処理では、readonly（EXAMINE）で開く のが安全だ。こうすれば、プログラムがメールを読んでも既読フラグが立たない。人が後から受信箱を見たときに「まだ誰も開いていない」状態を保てる。

多くのライブラリでは SELECT に readonly=True のような指定をすると EXAMINE 相当になる。

ポートと暗号化

IMAP で使うポートと暗号化方式は次のとおり。混同しやすいので整理しておく。

ポート方式暗号化説明
143平文 IMAPなし暗号化されない。中身が見える
993IMAPS（implicit TLS）あり（最初から SSL/TLS）接続した瞬間から暗号化されている
143STARTTLSあり（後から昇格）まず平文で接続し、途中で暗号化に 昇格 する別方式

ポイントは2つ。

  • 993 は「最初から暗号化（implicit TLS）」。接続開始時点で TLS が張られる。
  • STARTTLS は 143 で平文接続した後に暗号化へ昇格する。「143 = 常に平文」ではなく、 STARTTLS で途中から暗号化されるケースがある点に注意。

平文（暗号化なしの 143）は、通信経路が信頼できる 社内 LAN 内などに限る べきで、インターネット越しなら 993 か STARTTLS を使う。

認証

認証は基本的に ID（メールアドレス等）とパスワード で行う。

ただし近年は、通常のパスワードでのログインを許可しないサービスが増えている。

  • アプリパスワード: 自動処理・アプリ専用に発行する別のパスワード。
  • OAuth2（XOAUTH2）: トークンベースの認証。Google 系など一部サービスで必須。

自動処理を組むときは、対象のメールサーバが「普通のパスワードで入れるのか」「アプリパスワードや OAuth2 が要るのか」を先に確認しておくとよい。

接続の流れ（例）:
  1. imap.example.com の 993 番へ SSL/TLS 接続
  2. ID + パスワード（またはアプリパスワード / XOAUTH2）で LOGIN
  3. EXAMINE で受信箱を readonly で開く
  4. UIDVALIDITY を確認 → 処理済みUID記録と照合
  5. 未処理の UID だけ取得して処理

まとめ

  • IMAP は メールをサーバに置いたまま読む プロトコル。POP3 は取得してローカルに落とし基本消すので、複数端末閲覧や自動処理には IMAP が向く。
  • 各メールには UID が付くが、UIDVALIDITY が変わると UID 空間はリセット される。UID は UIDVALIDITY とセットで保存し、変化を検知したら管理をやり直す。
  • 二重取得の防止は「処理済み UID を自前で記録」する方式が安全。既読フラグやフォルダ移動に頼ると、人の操作で簡単に崩れる。
  • メールボックスは readonly（EXAMINE） で開けば、既読フラグ等を一切変えずに読める。
  • ポートは 143 = 平文 / 993 = 最初から SSL/TLS（implicit）/ STARTTLS = 143 接続後に暗号化へ昇格。平文は社内 LAN 内などに限る。
  • 認証は基本 ID/パスワードだが、アプリパスワードや OAuth2（XOAUTH2） が要るサービスもあるので事前確認する。
