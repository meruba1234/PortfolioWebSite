インフラ

ファイルドロップ型トリガー（watcher）で疎結合にジョブを起動する

背景

「処理を実行したいホスト」と「実行をお願いしたい端末」が別、という状況はよくある。たとえば重い処理は Python が入った専用ホストで動かしたいが、起動のきっかけは Python も何も入っていない事務端末や、別システムのバッチから投げたい、というケースだ。

素直に考えると「呼び出し側から実行ホストへリモートでコマンドを叩く」ことになるが、これは Windows 環境だと意外と面倒で、認証・権限・対話プロンプトの壁にぶつかる。そこで ファイルドロップ型トリガー（watcher） という、共有フォルダ（SMB）だけで成立する軽量な疎結合パターンが効いてくる。

起動手段の比較

まず、リモートからジョブを起動する代表的な手段を並べて比較する。

手段認証・前提長所短所
PsExec管理者資格情報を渡す手軽に任意コマンド実行パスワード管理が課題（平文で渡りがち）、AV に誤検知されやすい
OpenSSHWindows 標準搭載、鍵認証可鍵で安全、標準ツール対話プロンプトが苦手、Windows 側のシェル挙動にクセ
管理共有 \\host\C$admin 権限が必須追加ソフト不要でファイル配置admin 前提でハードルが高い、実行トリガーには別途工夫が要る
ファイルドロップ型SMB 共有への読み書きだけポート開放不要・どの端末からでも起動可対話不可・ホスト停止に気づけない・監視間隔の遅延

上3つは「呼び出し側が実行ホストに踏み込んで直接コマンドを走らせる」発想で、どうしても認証や権限の設計が重くなる。ファイルドロップ型は発想を逆転させ、 実行ホスト側が自分から共有フォルダを見に行く（ポーリングする）ことで、呼び出し側は「ファイルを1つ置くだけ」に責務を縮小する。

ファイルドロップ型の仕組み

実行ホストに常駐プロセス（watcher）を1つ置く。役割はシンプルで、共有フォルダの triggers/ を一定間隔でポーリングし、トリガーファイルを見つけたら本処理を起動する、というだけだ。

共有フォルダ（SMB）
  \\host\share\
    triggers/    ← 呼び出し側がトリガーファイルを置く
    processed/   ← 処理済みトリガーの退避先
    done/        ← 完了通知（.done ファイル）

流れは次のとおり。

  1. 呼び出し側：triggers/job_20260709_120000.trigger のようなファイルを置く

（中身に引数を JSON などで書いておくと、パラメータも渡せる）。

  1. watcher：ポーリングでトリガーを検知。
  2. watcher：トリガーを processed/ へ退避してから、本処理を起動。
  3. watcher：本処理が終わったら done/job_20260709_120000.done を生成。
  4. 呼び出し側：対応する .done ファイルが現れるのを待ち、完了を確認する。

呼び出し側は「置く」と「done を待つ」しかしない。ネットワーク的には SMB のファイル読み書きだけで、リモート実行 API もポートも要らない。

利点と欠点

観点内容
利点：ポート開放不要SMB さえ通っていればよく、ファイアウォールに穴を開けない
利点：SMB だけで完結追加のミドルウェア（キュー基盤等）が不要
利点：起動元を選ばないPython すら無い端末・別システムのバッチからでも「ファイルを置く」だけで起動できる
欠点：対話不可実行時にプロンプトで入力を求められない。引数だけで処理が完結する設計が前提
欠点：死活が見えない実行ホストや watcher が停止していても、呼び出し側は「done が来ない」ことしか分からない。タイムアウト設計が必須
欠点：遅延ポーリング間隔ぶんだけ起動が遅れる（数秒〜数十秒）

「対話不可」は特に効いてくる制約で、途中で y/n を聞くようなスクリプトはこの方式に乗らない。すべての入力をトリガーファイルの中身か、固定の引数で与えきる必要がある。

移動順序の注意（不整合を防ぐ）

このパターンでいちばん事故りやすいのが、トリガーファイルの移動・処理・記録の順序だ。順序を誤ると、「処理は失敗したのにトリガーだけ消えた」という不整合が起きる。

たとえば次の順序は危ない。

悪い例:
  1. トリガーを processed/ へ移動  ← 先に消してしまう
  2. 本処理を起動 → 失敗して例外
  → トリガーは既に消えているので、誰も再実行できないし、失敗した記録も残らない

「トリガーを消す＝この仕事は片付いた」という意味を持たせるなら、 片付いたことが確定してから消すのが基本だ。設計の勘どころは以下。

  • トリガーの退避は「処理が成功した後」に行い、失敗時は triggers/ に残す（または failed/ へ）。
  • ただし、残したままだと次のポーリングで同じトリガーを二重起動しかねない。検知した瞬間に「処理中」を示す印（.lock や .processing へのリネーム）を付け、完了・失敗の結果に応じて processed/ か failed/ へ確定移動する、という 2段階にすると安全。
  • ファイル移動は同一ボリューム内ならアトミックに近いので、「コピーしてから消す」より「rename で状態フォルダを移す」ほうが中間状態を作りにくい。

要は 検知（処理中マーク）→ 処理 → 結果に応じた確定移動 → done 生成 の順序を、どこで中断しても不整合が残らないように並べる、という設計問題になる。

一般化

これは要するに、メッセージキューが使えない／導入が大げさな環境における、軽量な疎結合ジョブ起動パターンだ。

本格的にやるなら「呼び出し側がキューにメッセージを積む → 実行側が購読して処理」というメッセージキュー（ジョブキュー）を使う。ファイルドロップ型は、その構図をそっくりファイルシステムで代用したものと見ると理解しやすい。

  • triggers/ = キューにメッセージを積む
  • watcher のポーリング = コンシューマの購読
  • processed/ への退避 = ack（処理済み確認）
  • .done ファイル = 処理結果の返信

小規模な社内自動化のように、専用のキュー基盤を立てるほどでもないが、端末とホストを疎結合にしたい、という場面にちょうど収まる。共有フォルダという「どの環境にもだいたいある」インフラだけで成立するのが最大の強みだ。

まとめ

  • 実行環境を持たない端末からジョブを起動したいとき、PsExec（パスワード管理）・ OpenSSH（対話が苦手）・管理共有（admin 権限）はそれぞれ壁がある。
  • ファイルドロップ型トリガーは、実行ホストに watcher を常駐させ、共有フォルダの triggers/ をポーリング → 検知 → 本処理起動 → processed/ へ退避 → .done で完了通知、という流れで、SMB だけで疎結合な起動を実現する。
  • 利点はポート開放不要・起動元を選ばない。欠点は対話不可・死活が見えない・監視間隔の遅延。
  • 最大の落とし穴は移動順序。検知（処理中マーク）→ 処理 → 結果で確定移動 → done の順に並べ、どこで中断しても「トリガーだけ消える」不整合を残さないよう設計する。
  • 位置づけとしては、メッセージキューの軽量な代替。大げさな基盤なしで疎結合を得たいときの定石。
