PythonSQL Server文字コードLinux移行

pyodbc の setencoding(cp932) が Linux で SQL と結果を壊す

背景

Windows 上で問題なく動いていた pyodbc の DB アクセスコードを、そのまま Linux コンテナ（ODBC Driver 18 for SQL Server）へ移植したところ、クエリの実行時と結果の受け取り時の両方で謎のエラーが出るようになった。コードは一字一句同じで、変えたのは動作環境（OS とドライバ）だけ。原因を突き詰めると、日本語対応のつもりで入れていた conn.setencoding(encoding="cp932") が犯人だった。ここでは「なぜ壊れたのか」と「そもそも要らなかった」という 2 段構えの学びを整理しておく。

setencoding / setdecoding とは

pyodbc では、Python の文字列（Unicode）と DB とのやり取りで使う文字コードを、接続オブジェクトに対して明示的に設定できる。

import pyodbc

conn = pyodbc.connect(conn_str)

# Python str → DB へ送るときのエンコード
conn.setencoding(encoding="cp932")

# DB → Python str へ戻すときのデコード（型系統ごとに指定）
conn.setdecoding(pyodbc.SQL_CHAR, encoding="cp932")   # VARCHAR 系
conn.setdecoding(pyodbc.SQL_WCHAR, encoding="utf-16le")  # NVARCHAR 系

日本語を扱うのだから cp932（Shift_JIS 系）を指定しておけば安全、という発想でこう書きがちだ。ところがこの setencoding は「SQL 文字列そのもの」にも効いてしまう。ここが罠になる。

症状1: パラメータマーカーが消える

setencoding(encoding="cp932") を設定すると、pyodbc はドライバへ渡す SQL クエリ文字列（Unicode）を cp932 バイト列にエンコードしてから送る。問題は、cp932 のような可変長マルチバイト符号化では、ある全角文字の「先頭バイト（リードバイト）」に続く「2 バイト目」として、ASCII 範囲と重なる値が現れうること。

パラメータマーカーの ? は ASCII の 0x3F。もしクエリ内の全角文字のバイト列に 0x3F が含まれると、ドライバはそれを「マルチバイト文字の一部」と解釈してしまい、本来のプレースホルダである ? を ? として認識できなくなる。結果、

('The SQL contains 0 parameter markers, but 1 parameters were supplied', 'HY000')

のような「パラメータマーカーが 0 個しか見つからない」系のエラーが出る。SQL のバインド構文は正しいのに、文字コード設定のせいでマーカーが埋もれて消えているわけだ。Windows のドライバでは内部の扱いが違って表面化していなかったが、Linux + Driver 18 で顕在化した。

症状2: 結果デコードで UnicodeDecodeError

送信側だけでなく受信側も壊れる。setdecoding(SQL_CHAR, encoding="cp932") を設定していると、DB から返ってきたバイト列を cp932 としてデコードしようとする。ところが実データの中に cp932 では未定義のバイト（例: 0x86 など）が混じっていると、

UnicodeDecodeError: 'cp932' codec can't decode byte 0x86 ...

で落ちる。厄介なのは、pyodbc の setdecoding には Python の bytes.decode() にあるような errors="replace" / errors="ignore" 相当の引数が無いこと。つまり「壊れた文字は置換して読み飛ばす」といった逃げが、pyodbc の API レベルでは打てない。codec レベルで握りたくても握れないのだ。

本質: NVARCHAR 主体なら codec 設定は不要

ここで一歩引いて考える。対象の DB が NVARCHAR（列名やリテラルに N プレフィックスが付く Unicode 型）主体なら、そもそも cp932 を設定する理由が無い。Unicode 型は DB 内部で UTF-16 として保持されており、pyodbc も既定で Unicode として素直にやり取りできる。cp932 を割り込ませることは、「わざわざ Unicode を一度 Shift_JIS に落とす」余計な変換を挟むだけで、上記 2 つの事故を自ら招いている。

安全策はシンプルで、codec を一切セットしない（pyodbc の既定に任せる）か、必要なら utf-8 / utf-16 に揃えること。

conn = pyodbc.connect(conn_str)
# 何も setencoding / setdecoding しない ← NVARCHAR 主体ならこれで十分動く

VARCHAR と NVARCHAR は別系統でデコードされる

もう一つ押さえておきたいのが、pyodbc のデコード設定が「型の系統ごと」に分かれている点。

SQL 型pyodbc の系統setdecoding で指定する定数
VARCHAR / CHAR非 Unicode（バイト系）SQL_CHAR
NVARCHAR / NCHARUnicodeSQL_WCHAR

VARCHAR を使う DB なら SQL_CHAR 側のエンコーディングが効き、NVARCHAR を使う DB なら SQL_WCHAR 側が効く。だから「どちらの型を主に使う DB か」で、そもそも設定すべき対象も内容も変わる。両方を混在させている場合は、それぞれの系統に正しいコーデックを当てる必要がある。自分の触る DB がどちらなのかを知らずに、片方の設定だけ入れて満足すると足をすくわれる。

まとめ

  • setencoding は「送信する SQL 文字列そのもの」にも効く。cp932 にすると ?（0x3F）が全角文字のバイトに埋もれ、「パラメータマーカーが 0 個」エラーになりうる。
  • setdecoding(SQL_CHAR, cp932) は未定義バイトで UnicodeDecodeError を起こし、pyodbc には errors 引数が無いので Python の codec レベルでは救えない。
  • NVARCHAR（Unicode）主体の DB なら、cp932 設定はそもそも不要。codec を触らないか utf-8 / utf-16 に任せるのが安全。
  • VARCHAR は SQL_CHAR、NVARCHAR は SQL_WCHAR と別系統。DB がどちらを使うかで設定が変わる。
  • 「Windows で動いた」は「Linux で同じ結果」を保証しない。文字コード設定は OS・ドライバで挙動が変わるので、環境を跨いだら必ず実行して確かめること。
