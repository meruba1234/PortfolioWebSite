データベース

DB の NULL / 0 / 空欄は別物 — 値の読み方と大きなキーの型

背景

「画面では空欄なのに、その列で絞り込もうとしても件数が合わない」——こういう食い違いは、DB の中身を 見た目のまま 想像したときに起きる。

  • 画面の空欄が、DB では NULL なのか、整数 0 なのか、空文字 '' なのかは実物を見ないと分からない。
  • 伝票番号のような大きなキーで結合しようとすると、型の想定違いで桁あふれしたり、結合そのものが空振りしたりする。

この 2 つは別の話に見えて、根っこは同じ「列の値と型を推測で決めず、定義と実データで裏取りする」という一点にある。

NULL / 0 / 空欄 は別物

まず、この 3 つは意味も挙動も違う。

値意味集計での扱い判定方法
NULL値が「未設定・不明」SUM/AVG から除外、COUNT(col) で数えないcol IS NULL
0「ゼロ」という確定した値SUM に 0 として参加、COUNT(col) で数えるcol = 0
'' (空文字)長さ 0 の文字列 (文字列型のみ)数値ではないcol = ''

要注意なのは次の点。

  • NULL は = で比較できない。 col = NULL は常に「不明」となり 1 件もヒットしない。必ず IS NULL / IS NOT NULL を使う。
  • 画面の空欄 = NULL とは限らない。 業務システムでは、未入力を 0 で埋めて保存する設計や、そもそも列に NOT NULL 制約があって NULL が 1 件も存在しない テーブルも珍しくない。
  • だから「NULL のとき〜」という条件分岐を足す前に、その列に本当に NULL があるのか を先に確かめる。

Nz() を通すと空欄と 0 が潰れる

レガシーな VBA / Access 系のコードには、Nz() のような 「NULL や空を 0 に変換する」関数 がよく出てくる。

' 元の値が NULL でも空でも、0 に変換して次へ渡す
qty = Nz(rs!数量, 0)

これを通した後の値を CSV や別テーブルに書き出すと、こうなる。

元データ:  NULL  → Nz → 0
元データ:  (空)  → Nz → 0
元データ:  0     → Nz → 0

つまり 「元が空だったのか、元から 0 だったのか」を後から区別できなくなる。下流でこのデータを見て「0 が多いな」と思っても、それが本当の 0 なのか、Nz で潰れた空欄なのかは追えない。

  • レガシーからの移行・照合作業では、Nz() や類似の変換を どこで通しているか を先に把握しておく。
  • 元の空欄と 0 を区別したいなら、変換前の生データ側で確認するしかない。

値の分布を必ず確認する

推測でなく、実データの件数を見る。1 本のクエリで NULL 件数と 0 件数を並べれば、その列の実態が分かる。

SELECT
    COUNT(*)                                    AS total,
    SUM(CASE WHEN amount IS NULL THEN 1 ELSE 0 END) AS null_count,
    SUM(CASE WHEN amount = 0     THEN 1 ELSE 0 END) AS zero_count,
    SUM(CASE WHEN amount > 0     THEN 1 ELSE 0 END) AS positive_count
FROM order_detail;
  • null_count = 0 なら、この列に NULL 判定を足すのは無駄 (むしろ誤解の元)。
  • zero_count が多ければ、「空欄」の正体は 0 だった可能性が高い。
  • この一手間で、「NULL かつ〜」のような 不要・的外れな条件分岐 を書かずに済む。

大きな整数キーは decimal で定義されることがある

伝票番号などが 18 桁級になると、一般的な 32bit int (上限 約 21 億) はもちろん、64bit bigint の範囲すら意識が要る。実務では、桁数を確実に収めるために decimal(18,0) (小数点以下 0 桁の固定長数値) で定義されているケースがある。

型おおよその上限18 桁キーを入れられるか
int (32bit)約 21 億 (10 桁)不可 (桁あふれ)
bigint (64bit)約 922 京 (19 桁)可
decimal(18,0)18 桁ちょうど可 (桁数を明示的に固定)

ここでハマるのが アプリ側のキャスト。

# NG: decimal(18,0) の 18 桁キーを int に入れて桁あふれ / 精度落ち
denpyou_no = int(row["denpyou_no"])

# OK: 文字列として扱う (計算しないキーなら数値化しない)
denpyou_no = str(row["denpyou_no"])
  • キーは 計算対象ではなく識別子 なので、無理に数値型へ変換しない。文字列のまま扱うのが安全。
  • 突き合わせ (JOIN やマージ) で「合致するはずなのに 0 件」のときは、両側の型・桁・前ゼロ (先頭の 0) の有無 を疑う。

複合主キーと CREATE TABLE で裏取りする

伝票系のテーブルは、1 列では一意にならず、複数列の組み合わせ (複合主キー) で 1 行を特定する設計が多い。例えば次のような組み合わせ。

(営業所コード, 伝票日付, 伝票番号, カード番号, 枝番)

WHERE 句の絞り込みや、テーブル同士の結合キーを推測するとき、この構成を 当てずっぽうで決めない。CREATE TABLE の定義を見れば裏が取れる。

CREATE TABLE order_detail (
    office_cd    CHAR(4)        NOT NULL,   -- 営業所コード
    order_date   DATE           NOT NULL,   -- 伝票日付
    order_no     DECIMAL(18,0)  NOT NULL,   -- 伝票番号 (18 桁 → decimal)
    card_no      CHAR(10)       NOT NULL,   -- カード番号
    branch_no    INT            NOT NULL,   -- 枝番
    amount       DECIMAL(12,0)  NULL,       -- 金額 (NULL 許容)
    PRIMARY KEY (office_cd, order_date, order_no, card_no, branch_no)
);

この定義 1 枚から、次のことが一度に読める。

  • PRIMARY KEY の列並び = 一意化の単位。結合キー・重複判定の候補はまずここ。
  • NOT NULL / NULL = その列に NULL があり得るか (上の例なら amount だけ NULL があり得る、キー列は全て NOT NULL)。
  • 型と桁 = order_no が decimal(18,0) なので、アプリ側で int キャストしてはいけないと分かる。

「この列で結合できるはず」「この列は NULL があるはず」という 推測を、定義で裏取りする のが確実。

まとめ

  • NULL / 0 / 空文字は別物。画面の空欄がどれなのかは実データを見るまで分からない。NULL は = でなく IS NULL で判定する。
  • Nz() 系の変換を通すと、空欄と 0 が同一化して後から区別できなくなる。移行・照合では変換箇所を先に把握する。
  • 条件分岐を足す前に、NULL 件数 vs 0 件数の 分布を 1 本のクエリで確認 し、不要な「NULL かつ〜」を書かない。
  • 18 桁級の大きなキーは decimal(18,0) で定義され得る。int キャストで桁あふれさせず、計算しないキーは文字列で扱う。
  • 伝票系は複合主キーで一意化されることが多い。CREATE TABLE の型・NOT NULL・PRIMARY KEY を読めば、WHERE 句や結合キーの推測を裏取りできる。
