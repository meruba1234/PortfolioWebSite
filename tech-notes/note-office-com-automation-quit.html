Windows管理

Office COM 自動化の鉄則 — Application.Quit() でユーザーの Office ごと閉じない

背景

pywin32 (win32com) を使って Excel や PowerPoint、Word を Python から自動操作する処理を書いていた。ファイルを開いて値を書き換え、最後に後片付けのつもりで Application.Quit() を呼んでいた。

ところが、たまたまユーザーが手動で開いていた別の Excel ブックまで一緒に閉じられてしまい、未保存の作業が消し飛ぶという事故が起きた。自動化スクリプトは自分の開いたファイルだけを閉じたつもりだったのに、なぜユーザーのウィンドウごと落ちたのか。これは COM 自動化で非常に踏みやすい地雷なので、原因と安全な作法を整理しておく。

なぜ起きるのか

Office アプリの COM オブジェクトは、多くの場合プロセス単位で共有される。

win32com.client.Dispatch("Excel.Application") を呼んだとき、すでに Excel が起動していれば、その既存プロセスに接続されることがある。つまり自動化スクリプトが掴んだ Application は、ユーザーが手で開いている Excel と同じインスタンスかもしれない。

その状態で Application.Quit() を呼ぶと、アプリケーション全体が終了する。自分が開いたブックだけでなく、ユーザーが開いていたブックも含めてプロセスごと閉じられる。これが事故の正体。

Quit() は「アプリを終了する」命令であって「自分のドキュメントを閉じる」命令ではない、という点を押さえておく。

安全な作法 — 一時コピーを ReadOnly で開き、Close だけする

鉄則は 2 つ。

  1. 元ファイルを直接触らず、一時コピーを作って ReadOnly で開く
  2. 後片付けはドキュメントを Close するだけ。Application.Quit() は呼ばない
import shutil
import tempfile
import os
import win32com.client

src = r"C:\data\report.xlsx"

# 1. 一時コピーを作る（元ファイルを保護）
tmp_dir = tempfile.mkdtemp()
tmp_path = os.path.join(tmp_dir, "work.xlsx")
shutil.copy2(src, tmp_path)

excel = win32com.client.Dispatch("Excel.Application")
excel.DisplayAlerts = False  # 保存確認などのダイアログを抑止

wb = None
try:
    # ReadOnly で開く。UpdateLinks=0 で外部リンク更新も抑止
    wb = excel.Workbooks.Open(tmp_path, ReadOnly=True, UpdateLinks=0)

    # ... ここで読み取り・処理 ...

finally:
    # 2. ドキュメントだけ閉じる。Quit() は呼ばない
    if wb is not None:
        wb.Close(SaveChanges=False)
    # excel.Quit() は書かない！ ユーザーの Excel を巻き込む

PowerPoint も同じ考え方で、Presentation.Close() だけを呼び、Application.Quit() は避ける。

ppt = win32com.client.Dispatch("PowerPoint.Application")
pres = ppt.Presentations.Open(tmp_path, ReadOnly=True, WithWindow=False)
try:
    # ... 処理 ...
finally:
    pres.Close()   # プレゼンだけ閉じる
    # ppt.Quit() は呼ばない

「一時コピー + ReadOnly」にしておくと、万一処理が途中で落ちても元ファイルは無傷。書き換えが必要な場合も、一時コピー側を編集して別名保存し、最後に元へ差し替える方が安全。

DisplayAlerts と Visible の扱い

  • DisplayAlerts = False 上書き確認・保存確認・リンク更新などのモーダルダイアログを抑止する。これを設定しないと、自動処理がダイアログ待ちで固まる（誰も OK を押さないので永久に止まる）。
  • Visible 自動処理では原則 Visible = False（非表示）で動かしたい。ただし既存プロセスに接続している場合、Visible を勝手に切り替えるとユーザーの画面表示に影響することがある。接続方式（次項）とセットで考える。

どのインスタンスに繋ぐか — 影響範囲を決める選択

接続方法によって「ユーザーを巻き込むか」が変わる。

  • Dispatch("Excel.Application") 既存プロセスがあればそれに繋ぐことがある。共有インスタンスなので Quit() は危険。
  • GetActiveObject("Excel.Application") すでに起動中のインスタンスに明示的に接続する。ユーザーが開いているものを操作したいとき用。当然 Quit() は厳禁。
  • DispatchEx("Excel.Application") 専用プロセスを新規に立てる。ユーザーの Office とは別プロセスなので、この場合は Quit() を呼んでもユーザーに影響しない。

DispatchEx は一見「Quit しても安全」で魅力的だが、環境によっては本当に独立した一意のプロセスになっているか確証を持ちにくい場面がある。迷ったら「Quit しない・ドキュメントを Close するだけ」を徹底しておけば、どの接続方式でも事故らない。

COM 参照は使い終わったら解放する

Python 側で COM オブジェクトへの参照が残っていると、アプリを閉じたつもりでもプロセスがメモリに居座る（ゾンビ化する）。

使い終わった参照は明示的に手放す。

wb = None
excel = None
import gc
gc.collect()

try/finally で確実に Close() を通し、ローカル変数を手放してから gc.collect() を呼ぶと、掴んだままのプロセスが残りにくい。長時間動くバッチや繰り返し処理では、この解放を怠るとプロセスが溜まっていくので特に注意する。

まとめ

  • Office の COM はプロセス単位で共有されることがある。Application.Quit() はアプリ全体を終了させ、ユーザーが開いている Office ごと閉じる重大事故になる。
  • 後片付けはドキュメントを Close するだけ。Quit() は原則呼ばない。
  • 対象は一時コピーを ReadOnly で開く。元ファイルを保護し、途中で落ちても無傷にする。
  • DisplayAlerts = False でダイアログ待ちのフリーズを防ぐ。Visible は接続方式とセットで考える。
  • 専用プロセスが要るなら DispatchEx、既存を触るなら GetActiveObject。影響範囲を意識して接続方式を選ぶ。
  • COM 参照は使い終わったら解放する。残すとプロセスが居座る。
