Windows管理

wscript プロセスがたまるとは

背景

移行元PC（タスクスケジューラ運用機）で「wscript プロセスがたまる」「wscript が溜まると異常検知も巻き込まれて落ちる」という話が出る。何が起きているのか、なぜ復旧が PC 再起動なのかを整理しておくためのノート。

wscript.exe とは

Windows 標準の Windows Script Host (WSH)。.vbs (VBScript) や .js (JScript) を実行するための Windows 組み込みのインタプリタ。

  • wscript.exe … GUI 版（ダイアログ表示できる）
  • cscript.exe … コンソール版（標準出力に出る）

タスクスケジューラから .vbs を起動すると、内部で wscript.exe が立ち上がってスクリプトを実行する。

「たまる」とは

タスクスケジューラから .vbs を実行 → 内部で wscript.exe が起動 → 本来は処理が終われば自動で終了するはずが、何らかの理由でプロセスが終了せず残り続ける現象。

スケジューラは設定された間隔で次々と .vbs を起動するので、終わらない wscript.exe がどんどん積み上がっていく。

タスクマネージャーで見ると wscript.exe が 10 個も 20 個も並んでいる、という状態になる。

なぜ起きるか（移行元PC で観測されたパターン）

ハングの典型的な連鎖：

  1. FAX 複合機エラーなどで、.vbs から呼ばれた外部処理（ファイル取得 / 印刷 / ネットワーク I/O）がハング
  2. その .vbs を実行している wscript.exe が I/O 待ちのまま終了できない
  3. スケジューラは時間が来たら次の wscript.exe を起動 → 同じ理由でハング
  4. wscript.exe が大量に溜まる
  5. リソース枯渇 / 同じファイル・リソースのロック競合で 異常受注検知など他のタスクも巻き込まれて失敗し始める

ポイント：wscript.exe 自身がバグっているわけではなく、内部から呼んでいる外部処理がハングしているのが本当の原因。wscript.exe はそれを忠実に待っているだけ。

確認方法

タスクマネージャー

プロセスタブで wscript.exe の数を数える。通常運用なら同時に走っている数（多くて数個）を超えていたら異常。

コマンド

tasklist | findstr wscript

PowerShell なら

Get-Process wscript | Measure-Object | Select-Object Count

対処

復旧

PC 再起動が確実。

個別に taskkill /IM wscript.exe /F で殺すこともできるが、

  • ハング中の .vbs が中途半端な状態でファイルを開いている可能性
  • 殺した直後にスケジューラが次の wscript を起動して同じ状況に戻る
  • 取りこぼしが出やすい

ので タスクスケジューラを止めずに連発 kill しないこと。

予防

  • .vbs から呼ぶ外部処理にタイムアウトを設ける
  • 強制終了オプション（タスクスケジューラの「タスクが指定時間以上実行されたら停止する」）を設定する … ただし業務によっては中断すると状態破壊のリスクがあるので注意（異常受注検知のタスクには設定していない）
  • そもそも .vbs + タスクスケジューラから卒業して Prefect（自動化基盤サーバー） に載せ替える

業務での具体例

  • 移行元PC の FAX 関連 vbs がハング → wscript.exe 溜まり → 異常受注検知も失敗、という連鎖が複数回発生
  • 復旧手順は基本「移行元PC を再起動」
  • 自動化基盤サーバー (Prefect + Docker) に移行した業務はこの問題から解放される。.vbs を使わず Python flow を Worker コンテナで実行するため、プロセス管理は Prefect / Docker が面倒を見てくれる

覚え方

  • wscript.exe = Windows が .vbs を動かすためのランナー
  • たまる = .vbs の中の処理がハングしてランナーが止まれない状態
  • 真犯人は wscript ではなく .vbs から呼ばれている外部 I/O
  • 復旧は 再起動、根本対策は Prefect 移行
