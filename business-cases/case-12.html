取引先プラットフォーム 売上照合システム

取引先の発注プラットフォームから届く PDF 伝票と、自社販売管理 DB の売上を自動で突合し、差異のあるものだけを通知するシステム。営業事務の目視照合を、確認作業だけに置き換えました。

業種
卸売 (取引先の発注プラットフォーム経由)
対象部門
営業事務 (照合作業担当)
実装期間
約2週間で初版稼働、以降も継続改善
本番稼働
2026年6月 (日中の毎時自動実行)
技術スタック
Python, pdfplumber, SQLite, SQL Server (pyodbc), Prefect 3.x, 社内チャット通知

背景・課題

取引先の発注プラットフォームから届く PDF 伝票と、自社の販売管理 DB に登録された売上を突き合わせる作業を、営業事務が手作業で行っていました。

  • PDF を一件ずつ開いて、DB の売上と目視で照合する
  • 金額が合わないとき、どちらが正しいのかを後から追う手段がない
  • 月次の照合作業に長時間かかる

「照合する」こと自体よりも、「不一致が出たときに原因を追えない」ことのほうが業務上の負担でした。過去のデータが手元に残らないためです。

実装した解決策

1. PDF の自動取得とパース

伝票 PDF を自動取得し、pdfplumber でテキストとして解析します。テキスト情報を持つ PDF だったため OCR は使わず、レイアウトベースで明細を抽出しました。

2. SQLite への蓄積 (差分更新)

  • PDF から読んだ明細を SQLite に蓄積し、過去データを保持
  • 主キーを (伝票番号, 納品日, 自社コード, 金額) の複合キーに変更し、同一伝票内の重複行を正しく区別
  • 差分更新方式にすることで、遡及調査ができる状態を作る

3. 3層の照合ロジック

1つの見方だけでは差異の性質が分かりません。粒度の違う3層で照合しています。

  1. 伝票単位 — 1伝票ごとの金額一致を検算
  2. 得意先 × 納品日 — 日単位の合計で突合
  3. 得意先の期間合計 — 期間トータルで突合

伝票単位では合わないが日合計では合う、といったケースから、代替品への差し替えや納品日のズレを切り分けられます。納品日は1日差まで許容してマッチングしています。

4. 実データの例外パターンへの対応

  • 「(変更)」「(追加)」のプレフィクスが付く明細
  • 小数点を含む単価、100/枚 のような規格表記の行
  • 返品・値引きによるマイナス値
  • 商品マスタ未登録を示す特定コード、仮伝票の取引区分を照合対象から除外
  • 0円明細、未来日付の納品予定を除外

5. 差異のみを通知

照合結果すべてではなく、差異が出たものだけを社内チャットに WARNING として通知します。担当営業・担当事務は担当者マスタから自動で引き当てています。

実装した成果と範囲

月次の照合作業を、目視での全件確認から「差異のみ通知される自動照合」に変更しました。伝票単位の検算ロジックによって、運用開始後に実際の差異を2件検出しています。SQLite への蓄積により、後から「いつの伝票がどうだったか」を追えるようになりました。

得られた学び

  • PDF パースは実データを見るまで終わらない — 正規表現で書けたつもりでも、実データの例外パターンを洗い出すのに2週間かかった。想定でパターンを決めない
  • 片側だけでは照合にならない — 「DB だけ」「PDF だけ」では不足で、両方を蓄積して突き合わせる構造が必要だった
  • 粒度を変えて複数回照合する — 伝票・日次・期間の3層にしたことで、差異の「性質」まで分かるようになった
  • 業務側の「絶対 NG」は明文化する — 触ってはいけない操作を仕様として残し、後任も含めて事故を防げる形にした
