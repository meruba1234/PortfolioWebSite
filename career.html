職務要約

卸売業の事務システム部門で社内SEを担当しました。営業事務・経理・物流・商品部といった各部門にヒアリングを行い、 業務の目的と例外条件を整理したうえで、自動化・システム化の形に落とし込む仕事です。 既存の VB.NET / Excel VBA システムの解析と Python への移植、Docker と Prefect による自動化基盤の構築、 社内 Web ツールの開発、約200台規模の PC 資産管理まで、要件整理から運用後の改善まで一貫して担当しました。

対話 → 課題把握 → 業務改善を検討 → 必要ならシステム開発 → 導入・改善

依頼されたものを作るだけでなく、自分から現場に声をかけて困りごと・使いづらさ・部門間連携の課題を確認し、 適切な改善方法を考えることを大切にしてきました。複数案件を並行するときは、優先順位を付けてスピード感を持って進めます。

1. 業務自動化・システム開発

  • 受発注データの自動処理 — 取引先の EDI / EOS 発注データを販売管理 DB と連携し、単価決定・金額計算・返送までを自動化。ケースを見る
  • Web 画面操作の自動化 — Playwright により、取引先サイトからのデータ取得・入力代行・アップロードを自動化。ケースを見る
  • 照合・検知の仕組み — PDF 伝票と販売管理 DB の突合、受注データの異常検知を実装。差異のみを通知する設計に。ケースを見る
  • 帳票・レポートの自動生成 — 月次請求内訳、出荷目安、日別実績などを Excel / PDF で自動生成。ケースを見る
  • Excel VBA と DB の連携 — 現場が使い慣れた Excel をフロントに、裏で SQL Server と連動する仕組みを実装。ケースを見る

2. 既存システムの解析・移植

  • VB.NET システムのリバースエンジニアリング — 約5,000行の登録プログラムを逐次解読し、業務ルールを仕様書化。
  • Python への段階的移植 — 既存 DB との整合性を検証しながら移行。税抜・税込・軽減税率・割戻を含む金額計算に対応。ケースを見る
  • 移行時の並行検証 — 旧方式と新方式を一定期間並行稼働させ、結果が一致することを確認してから切り替える進め方を徹底。

3. 自動化基盤の構築・運用

  • ジョブ基盤の構築 — Ubuntu Linux + Docker Compose + Prefect でジョブを集中管理する基盤を構築。ケースを見る
  • 運用設計 — ログ、通知、タイムアウト、多重起動防止、リトライの一時／恒久エラー分離、ゾンビ実行の二重ガードを整備。
  • 可観測性 — 失敗時だけでなく成功時も通知し、「動いていないことに気づけない」状態をなくす設計に。

4. 社内 Web ツールの開発

  • Flask / Vue.js による社内ツール — FAX 履歴の検索、商品不足情報の共有、異常受注の確認 UI を実装。ケースを見る
  • Laravel / Filament による社内 Web システム — 管理画面の構築。Livewire / Alpine.js / Tailwind CSS 系の構成。

5. 情報システム運用

  • PC 資産管理 — 約200台規模のセットアップ・交換・棚卸。
  • 問い合わせ・障害対応 — 各部門からの問い合わせ一次対応、原因調査、機器保守。
  • ネットワーク・クラウド — 社内ネットワークの構築・保守、AWS の契約・導入対応、Amazon CodeCommit によるソース管理の導入。

仕事の進め方

  • 業務を理解してから作る — 担当者へのヒアリングで目的・例外・確認手順を整理し、既存コード・DB・実際の挙動と照合して仕様を確定させる。
  • 止める基準を設計する — 1件の不備で全体を止める設計は、一見安全でも業務を止める。致命的なものだけ停止し、要対応は通知で分離する。
  • 切り替えは並行検証してから — 旧方式と新方式を一定期間並行させ、結果が一致することを確認してから切り替える。
  • ドキュメントを同時に更新する — 仕様書・操作マニュアルを実装と並行して更新し、障害時の手動運用手順も用意する。
  • 効果は条件を明らかにして評価する — 処理時間と人の作業時間を区別し、計測条件と算定根拠が確認できるものだけを実績として扱う。

自己PR

強みは、現場との対話から課題を把握し、関係者と調整しながら業務改善を形にすることです。

業務改善の依頼は、必ずしも整理された形で来るわけではありません。「この作業が面倒」という話の背景には、 部門をまたいだ手順の重複や、システムに乗っていない例外処理が隠れていることが多くありました。 まず現場に足を運んで実際の作業を見せてもらい、目的と例外条件を洗い出したうえで、 システム化が最適なのか、手順の見直しで足りるのかを含めて検討するようにしてきました。

実装後も作りっぱなしにせず、稼働後に出てきた不具合や運用上の要望に対応してきました。 たとえば、1件の単価未登録で処理全体が止まる設計が運用に合わないと分かった際は、 致命的なエラーだけを停止対象に変更し、要対応分は通知で分離する形に改めています。 「動くものを作る」ことと「業務が回り続ける」ことは別だと考えています。
